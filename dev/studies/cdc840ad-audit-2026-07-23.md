## 2. Verdict

The deck is reliable where it is structural and unreliable where it is specific.

Every architectural claim about *ownership and design* survived adversarial checking. The two Rust snippets, the plan JSON document, and roughly half the "measured" performance table did not. Nine falsifiable errors, four of which are discoverable in under a minute by anyone with the repository open.

The underlying implementation is better than the deck's weakest claims suggest and worse than its simplicity story implies. **Implementation quality: B+. Maintainability: C+.**

The single most consequential finding is not a number: **"independent holistic PASS" (slide 19) is unsubstantiated by the project's own review protocol.** It is the one claim that, if challenged, undermines the credibility of the completion evidence as a whole.

## 3. Part A — deck fact-check

### A1. Must fix — falsifiable errors

#### A1-1. Slide 7: the `fn derive(...)` signature is fabricated
**talk.html:115.** No function named `derive` exists anywhere in `crates/`.

Real closed entry point:
```rust
// crates/jit/src/repository_state/mod.rs:422-425
pub fn derive_materialization(
    image: &RepositoryImage,
    request: MaterializationRequest<'_>,
) -> Result<MaterializationPlan, RepositoryStateError>
```
Three drifts: the name; the second parameter is a closed 5-variant enum `MaterializationRequest` (`SemanticMutation`, `RenderConfiguredProjections`, `RepairDerivedState`, `Initialize`, `ApplyProfile`) that carries `RepositoryDeclarations` *inside* three of its variants; and the return is fallible. `RepositoryDeclarations<'a>` does exist (`mod.rs:137`) with fields `configuration`/`gates`/`rules`.

#### A1-2. Slide 7: the plan JSON document does not exist
**talk.html:116-121.** Highest credibility risk in the deck, because the slide is titled "inspectable".

- `MaterializationPlan` does not derive `Serialize` — `repository_state/mod.rs:285-286` is `#[derive(Debug, Clone, PartialEq, Eq)]`.
- No command emits this document.
- `plan_hash` carries no `sha256:` prefix — `image.rs:1404` is `Ok(format!("{:x}", hasher.finalize()))`, bare hex.
- The real action vocabulary (`image.rs:1139-1167`) is a 4-variant enum `CreateDirectory | WriteFile | SetMode | DeleteFile`; the write variant is `{ path, owner, expected, bytes, mode }`. There is no `write` field, and `path` is a structured `VirtualPath`, not the string `".jit/rules.toml"`.
- Closest real emitted analogue: `ProfilePlanResult { id, version, status, plan_hash, targets }` (`crates/jit/src/profile/application.rs:139-151`) via `jit profile apply --dry-run`; the field is `targets`, and `ProfileTargetChange { path, action, executable }` (`application.rs:107-114`) has no `expected`/`write`.

So "inspectable" holds only on the profile-apply path.

#### A1-3. Slide 16: "The current repository produced 130 session opens"
**talk.html:303.** False on two independent counts.

- Source: `dev/archive/cdc840ad-progress.json:158` — "Deterministic regression: **64 blocked plus 1 eligible Backlog issue** now opens exactly 2 mutation sessions instead of the predecessor's 130." That is a synthetic `InMemoryStorage` fixture of 65 issues × 2, **not this repository**.
- `dev/archive/cdc840ad-completion-report.md:36` says "**130 predicted**". The slide says *produced*.
- The regression test was added in the same commit as the fix (`3725228e`), so the old path was never executed against that fixture. Only the post-fix `2` was observed.
- It contradicts the bullet directly above it on the same slide: 48 Backlog issues implies 96 session opens, not 130.

The "after: 2" **is** genuinely measured — `crates/jit/src/commands/issue.rs:865-921`, `test_check_auto_transitions_opens_sessions_only_for_eligible_backlog_issues`, asserting `counter == 2`. The counter is a sound proxy: `TransactionFailurePoint::RepositoryRecoveryExternal` is checked exactly once per `open_mutation_session` in both backends (`storage/repository_state_store.rs:327` and `:408`).

Suggested replacement: "A 65-issue deterministic model predicts 130 session opens for the old path; the corrected path opens 2."

## 4. Part B — implementation quality and maintainability

**Implementation quality: B+ · Maintainability: C+**

The transaction kernel and its value vocabulary are genuinely well built, not merely well narrated. Against that, the "one pure planning boundary" the completion report claims is actually seven public plan-producing entry points across five error types; the typed error is repeatedly reached by stringifying `anyhow` and downcasting back; the session protocol is a hand-copied convention rather than an API; and the plan-derivation core — the epic's REQ-01 deliverable — has zero property-based coverage.

### B1. Strengths (concrete)

- `storage/transaction_journal.rs:120-140` — journal carries `version`, `layout_digest` **and** a separate `owner_digest`, with an explicit comment on why the two differ (data root becoming present changes one, not the other). Exactly the durability subtlety that usually goes unwritten.
- `repository_state/path.rs:14-20` — `RootRelativePath::{Root, Descendant}` encodes root-vs-descendant as a type distinction with no sentinel; doc states "The root is never minted as an empty descendant." Parser at `:28-50` rejects absolute, backslash, colon, control-char, `.`, `..`, and empty segments.
- `storage/guard_order.rs:1-63` — lock-order inversion encoded as a typed thread-local guard; reverse acquisition rejected with `ReverseAcquisitionError` before any lock is taken; `#[must_use]` on both guards.
- `storage/repository_state_store.rs:2220-2259` — `test_interruption_boundaries_recover_complete_old_or_new_state` asserts the *coupled* invariant (`note.txt` exists ⟺ `index.json` exists) at 9 boundaries. Semantic and refactor-stable, per `@/inv/semantic-test-assertions`.
- `crates/jit/tests/fast_rules/derived_state_repair_tests.rs:111-197` — injects drift per ownership class, asserts diagnosis determinism (`first == second`), derived bytes return to a real-init baseline, authored prefix/suffix and an unowned schema byte-preserved. No snapshots.
- 35 named failure-injection points, all exercised somewhere in the suite; ~20 interruption tests asserting all-old-or-all-new semantically.
- Documentation coverage exceptional: 10 undocumented `pub` items out of ~200.
- `cargo clippy --workspace --all-targets` exit 0, zero warnings. `cargo fmt --all -- --check` clean.
- Only 14 panic sites in ~15k lines of new production code; 7 are the `unreachable!`s in B2-4, the rest provably total.
- No stale references to any of the 11 deleted modules anywhere in `crates/`, `docs/`, or non-archived `dev/`.
- Layer discipline holds: no production import of storage/commands/validation/profile from `repository_state`, and no filesystem I/O there beyond the injected `MutationClock`.

### B2. Findings by severity

**B2-1 — The capture/plan/apply/retry protocol is copy-paste, not API.**
`for _ in 0..8 { … }` at **29 production sites across 16 command files**: `commands/mod.rs:1782,1821,1908,2141,2353`; `document.rs:122,205,801`; `gate.rs:1078,1357,1477`; `gate_check.rs:743,909`; `profile.rs:98,152,335`; `validate.rs:169,426,478`; `dependency.rs:260,396`; plus init/config/project/archive/migrate/batch_create/issue/claim. With **65 hand-written `Err(RetryableConflict{..}) => continue` arms** and **30 bespoke "did not converge" messages**. Only `commands/template.rs:40` names the bound.
*Why it matters:* a new consumer must remember to loop, match the conflict arm on *every* capture and the apply, bound attempts, and invent a terminal error. A missing arm turns a benign concurrent write into a user-visible failure and nothing catches it.
*Fix:* one `with_mutation_session(layout, |session| …)` combinator in `commands/mod.rs` owning the bound and conflict classification.

**B2-2 — Seven plan-producing entry points, five error types.** Directly contradicts "one planning boundary".

### B4. What the perf fix actually was

Worth stating plainly in any future retelling: the epic **created** this regression. Pre-cutover, `auto_transition_to_ready` short-circuited *before* any mutation (`git show 41d599f0^:crates/jit/src/commands/issue.rs:1092-1111`). Commit `41d599f0` ("feat: cut over captured issue transitions", jit:49adf23b) moved the predicate *inside* the captured mutation (`commands/mod.rs:2653-2655`), i.e. after two full session opens. The fix restored a guard that `commands/validate.rs:2100-2116` (`fix_ready_transitions`) already had. It is correct, minimal, and TOCTOU-safe — the prefilter can only skip work, never authorize a transition, because `commands/mod.rs:2653-2655` still re-tests eligibility inside the captured session. But framing it as an insight rather than "we reinstated a guard the cutover deleted" would overclaim.

The residual cost driver is untouched: a mutation session costs ~1s (two full repository captures per issue mutation, per slide 16's own arithmetic). Only the count of *needless* sessions was reduced.
