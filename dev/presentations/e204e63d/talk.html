Before a package · 3 / 20

A bare init declares nothing

$ jit init
Scaffolded .jit/rules.toml
Initialized jit repository (worktree: wt:f6224909)

$ find .jit -type f | sort
.jit/config.toml           .jit/invariants.toml
.jit/events.jsonl          .jit/rules.toml
.jit/gates.toml            .jit/schemas/default-label-format.json
.jit/index.json            .jit/worktree.json

No type hierarchy, no label namespaces, no item kinds, no gates. gates.toml and invariants.toml are empty registries.

Before a package · 4 / 20

The structural minimum is a working repository

[version]
schema = 2

[project]
name = "demo"          # slugged from the directory; edit freely

That is the whole of config.toml. jit validate passes, and issues can be created. One rule is scaffolded — label-format — and its assertion derives from the registries above, so it emits nothing for registries that declare nothing.

A vocabulary is a declaration, not a default. What the engine cannot derive from your repository, it does not invent.
Applying · 5 / 20

Vocabulary arrives by applying a package

$ jit init --profile jit-dogfood --from packages/jit-dogfood
Scaffolded .jit/rules.toml
Initialized jit repository (worktree: wt:3f8692f9)

$ jit profile list
jit-default 1.0.0 directory packages/jit-default (applied)
jit-dogfood 1.0.0 directory packages/jit-dogfood (applied)

One package was named; two were applied. jit-dogfood declares a dependency on jit-default, which is looked for beside it under its own ID — so an obtained directory of packages applies as a set.

Applying · 6 / 20

What application requires

Needs

  • A directory of bytes, obtained beforehand
  • That directory inside the worktree

Does not need

  • Network access
  • A Git repository
  • A JIT source checkout

Run in an empty directory holding only packages/, with no .git, jit init --profile jit-dogfood --from packages/jit-dogfood initializes and applies both packages.

A package resolving outside the worktree — including under .jit/ — is refused by name, so repair never depends on machine state.
The package · 7 / 20

A package is a directory

packages/jit-dogfood/
  manifest.toml                  # identity, dependencies, every declaration
  assets/install/...             # files that exist only to be installed
  assets/regions/...             # sources for managed regions in your files
  assets/live/...                # files the package mirrors from a repository

No archive format, no index, no lockfile. The manifest is the inventory; jit profile show reads it without applying anything.

The published jit-dogfood package is 64 files, 432,973 bytes, covering 68 targets.
The package · 8 / 20

The manifest states identity and dependencies

dependencies = ["jit-default"]

[profile]
manifest-version = 1
id = "jit-dogfood"
version = "1.0.0"
jit = ">=1.0.0, <2.0.0"

The package version is independent of the JIT version; jit states the range it is built for. v1.0 parses that range and does not match it against the running binary — a package built for a later binary applies cleanly and fails wherever the shape later differs.

The package · 10 / 20

A contribution is typed by how it merges

[[contribution]]
kind = "map-entry"                  # one entry of a map
target = "type-hierarchy-types"
identity = "milestone"
value = 1

Five kinds: map-entry, set-string, scalar, keyed-array, projection. The kind tells the applier how two packages combine on one target, which is what makes a delta package and a self-contained one produce the same repository.

Operating · 12 / 20

Preview the final state, not a best-effort script

$ jit profile apply jit-dogfood --dry-run --json
{ "id": "jit-dogfood",
  "plan_hash": "<64 hex chars>",
  "status": "unchanged",
  "targets": [ { "action": "unchanged", "executable": false,
                 "path": ".agents/skills/jit-breakdown/SKILL.md" }, ... ] }

Every target carries create, update, or unchanged and its executable intent. Nothing is written. Exact reapplication reports unchanged throughout — a successful no-op. The plan hash addresses the plan, so it is stable for one repository state and differs between repositories; the package hash on the next slide addresses the bytes, and is the same everywhere.

Operating · 13 / 20

The repository records where the bytes came from

$ cat .jit/profiles/jit-dogfood.json
{ "id": "jit-dogfood", "version": "1.0.0",
  "origin": { "source": "directory", "location": "packages/jit-dogfood" },
  "package_hash": "db08e61ef0363fca71cb5afed1976bd177f2fe8bdb9a3e0c40b4f0f301c5c45b",
  "target_hashes": { ... 68 entries ... } }

The location is worktree-relative and lives only here — not in config.toml, so there is no second carrier and no precedence question. Leave the package where you applied it from; later commands read it there again.

Operating · 14 / 20

Repair re-resolves the package, or fails loudly

$ rm .agents/skills/jit-breakdown/SKILL.md
$ jit validate --fix
✓ Repaired derived-state target .agents/skills/jit-breakdown/SKILL.md
✓ Applied 1 fixes
✓ Repository is now valid

A drifted target is repaired the same way. With the package moved away, --fix refuses by naming the record, the profile, and the location that no longer holds a readable package — rather than restoring what it can still see.

Operating · 15 / 20

Your content is not collateral

$ printf '\nlocal edit\n' >> .agents/skills/jit-breakdown/SKILL.md
$ jit profile apply jit-dogfood --dry-run --json
{ "error": { "code": "PROFILE_CONFLICT",
    "message": "profile package jit-dogfood asset target
      '.agents/skills/jit-breakdown/SKILL.md' conflicts with package
      jit-dogfood and contains differing bytes" } }

A target holding differing bytes is a conflict reported before anything is written. Application is one recoverable multi-target transaction: it validates the whole final state first, then publishes once.

Authoring · 16 / 20

Declare the roots your package draws from

[[live-source]]
root = ".agents/skills"
exclude = [".agents/skills/*/evals/**",
           ".agents/skills/*/trigger_eval*.json",
           ".agents/skills/*/scripts/test-*.sh",
           ".agents/skills/**/.gitkeep"]

Most of a workflow package's assets are files the source repository also uses at their working paths. Declaring the root you draw from — with glob exclusions rather than a literal file list — turns an omission into a failure instead of a silent gap in what adopters receive.

Authoring · 17 / 20

Omission fails the suite

test_unpackaged_files_under_declared_roots_is_empty_across_the_tracked_repository_tree

The walk goes both directions. Every declared root must claim each live asset exactly once, and no tracked file under a declared root may be left unclaimed unless a declared pattern excludes it.

Add a skill file under a declared root and forget to declare it, and the suite names it — rather than shipping a package that silently lacks it.
Authoring · 18 / 20

The tree is produced, not maintained

$ scripts/assemble-package.sh /tmp/out
assembled: /tmp/out
OK: jit-dogfood carries 64 files drawn from profiles/jit-dogfood
    and the repository files its live assets name

Each run publishes a freshly staged tree, so a source the manifest stops declaring is absent from the next one. Two runs from one repository state produce byte-identical trees and identical digests, so a package can be rebuilt and compared rather than trusted.

Boundary · 19 / 20

v1.0 is apply-only, deliberately

Exists

  • list, show, apply
  • Declared dependencies, resolved
  • Provenance and repair

Deferred

  • Upgrade, removal, detailed diff
  • Variables and sensitive values
  • Reconfiguration, incompatibilities

No search path discovers a package, and nothing is hidden behind the interface: a package is found where the command or the record says it is. For anything beyond applying, edit repository configuration directly.
