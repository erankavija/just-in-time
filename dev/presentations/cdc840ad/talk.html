Feature introduction · 2 / 22

What this feature is

Repository materialization turns JIT's declared semantic state into every coupled persisted file through one captured final view, one pure plan, and one recoverable publication.

Configuration, registries, issues, projections, schemas, managed prose, provenance, and audit state can no longer be updated by unrelated command-specific write paths.

For users, commands become atomic and repairable. For agents, the repository becomes a coherent input rather than a collection of files that may disagree.
Motivation · 3 / 22

Before: valid inputs could leave stale outputs

  • Profile apply validated a merged view without materializing every coupled default.
  • Configuration could persist before schemas, rules, or projections refreshed.
  • project render published targets one at a time.
  • Profile regions and registry projections used separate marker engines.
  • Validation could derive correct behavior while persisted addressable state remained stale.
Each local operation looked reasonable. Their composition was not a transaction.
Why it matters · 4 / 22

What JIT gains

Correctness

Declared and derived state agree after every successful mutation—or nothing changes.

Operations

Crashes, conflicts, and interruption have one recovery story instead of command-specific cleanup.

Agentability

Plans are deterministic, errors are typed, and repository evidence is safe to inspect and retry.

The feature strengthens JIT's core promise: plain JSON in Git, without accepting partially coherent JSON.
Mental model · 5 / 22

The entire contract in one pipeline

CaptureSpec → RepositoryImage → pure MaterializationPlan → validate → recoverable apply
  1. Bound exactly which repository evidence the operation may read.
  2. Capture an immutable, closed image of that evidence.
  3. Derive one deterministic delta without filesystem I/O.
  4. Revalidate preimages and publish the complete delta atomically.
Reads define the plan; the plan owns its captured image; storage publishes but does not invent semantics.

Validation · 11 / 22

Repair derived state—never redefine authority

jit validate          # diagnose missing or stale materializations
jit validate --fix    # recompute from declarations; publish one plan
jit validate          # exact, idempotent clean result
  • Expected bytes are always recomputed from declared configuration and registries.
  • Unrelated content and authored rule prose remain byte-for-byte intact.
  • Malformed or ambiguous ownership fails before publication.
A projection may repair derived assertions. It must not silently become authority over authored semantics.

Performance · 16 / 22

Completion exposed a 100-second lifecycle path

A terminal issue update scanned every Backlog issue, then opened a full repository mutation session for each—even when dependencies still blocked it.

48 Backlog issues × preflight + publication capture ≈ 100 seconds
  • Work scaled with total Backlog count, not eligible transitions.
  • The current repository produced 130 session opens in the deterministic model.
  • jit validate itself took only about 1.5 seconds, ruling out repository size as the explanation.
The epic was deliberately held open. Correctness with pathological lifecycle latency was not accepted as complete.
Performance · 17 / 22

The fix was deliberately small

let issues = self.storage.list_issues()?;
let resolved = build_issue_map(&issues);
let candidates = issues.iter()
    .filter(|issue| issue.should_auto_transition_to_ready(&resolved))
    .map(|issue| issue.id.clone())
    .collect::<Vec<_>>();
for id in candidates { self.auto_transition_to_ready(&id)?; }

Production change: +2 / −1 lines. Existing retry, event, timestamp, and atomic-publication paths remain unchanged. No cache, worker, compatibility path, or second engine was introduced.

Future development · 20 / 22

Next: make performance a maintained contract

  1. Performance budgets: add repository-scale lifecycle benchmarks and session-open telemetry to catch scaling regressions before completion.
  2. Lock hygiene: consolidate or lazily create per-record locks, preserving concurrency tests and advisory semantics.
  3. Incremental work: optimize capture or dependency indexing only when measurements justify it; keep full revalidation at publication.
Measure session opens and elapsed time together: latency alone does not reveal an accidental O(backlog) recapture loop.
Future development · 21 / 22

Next: extend the shared engine, not around it

  1. Explainability: expose plan/delta previews and repair explanations from the existing pure planner.
  2. Profile lifecycle: build safe upgrade and removal on captured ownership and provenance—without a second planner.
  3. Typed integrations: let new consumers contribute typed intent rather than acquire private publication logic.
  4. API cleanup: remove compatibility scars and fix generator/documentation debt while the architecture is still greenfield.
The long-term guardrail: one image, one planner, one transaction boundary—even as the product surface grows.
