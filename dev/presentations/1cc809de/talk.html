Feature introduction

What repository materialization is

JIT turns its declared semantic state into every coupled persisted file through one captured final view, one pure plan, and one recoverable publication.

The boundary is tracked semantic state under .jit/: configuration, registries, issues, projections, schemas, managed prose, provenance, and audit state are planned and published together.

Machine-local files that .gitignore excludes keep their own writers: .jit/**/*.lock, .jit/server.log, .jit/server.pid.json, .jit/worktree.json, .jit/tmp/.

For users, commands are atomic and repairable. For agents, the repository is a coherent input rather than a set of files that may disagree.
Motivation

Why coherence needs a single owner

  • One semantic edit implies coupled derived outputs: schemas, projections, managed regions, provenance, audit records.
  • Independent write paths are each locally reasonable. Their composition is not a transaction.
  • Validation can compute the right answer while the persisted addressable state disagrees with it.
  • Recovery written per command multiplies the number of ways a repository can be left half-updated.
Coherence is a property of the whole publication, so it has to be owned in one place.
Why it matters

What JIT gains

Correctness

Declared and derived state agree after every successful mutation, or nothing changes.

Operations

Crashes, conflicts, and interruption share one recovery story instead of command-specific cleanup.

Agentability

Plans are deterministic, errors are typed, and repository evidence is safe to inspect and retry.

The feature strengthens JIT's core promise: plain JSON in Git, without accepting partially coherent JSON.
Mental model

The entire contract in one pipeline

CaptureSpec -> RepositoryImage -> MaterializationPlan -> revalidate preimages -> recoverable apply
  1. Bound exactly which repository evidence the operation may read.
  2. Capture an immutable, closed image of that evidence.
  3. Derive one deterministic delta without filesystem access.
  4. Revalidate every preimage and publish the complete delta atomically.

Reads define the plan; the plan owns its captured image; storage publishes but does not invent semantics. Types: CaptureSpec and RepositoryImage in repository_state/image.rs; MaterializationPlan in repository_state/mod.rs; the session boundary capture and apply in storage/repository_state_store.rs.

Capture

A closed final repository view

pub struct RepositoryImage {
    layout: RepositoryLayout,
    spec: CaptureSpec,
    entries: BTreeMap<VirtualPath, RepositoryEntry>,
    listings: BTreeMap<VirtualPath, ListingFingerprint>,
    pinned: BTreeMap<(String, String), PinnedDocumentEvidence>,
    linked_worktree: BTreeMap<VirtualPath, LinkedWorktreeEvidence>,
}

Verbatim from crates/jit/src/repository_state/image.rs. Root evidence is not a field here: RepositoryLayout holds it, recording the worktree root and the data root separately (repository_state/path.rs).

Capture

What the image closes over

  • Virtual paths separate semantic identity from physical layout and custom data roots.
  • Directory listings, pinned documents, and linked worktrees are captured explicitly, not re-read during planning.
  • An undiscovered read is a capture error rather than a fallback to ambient filesystem access.
One declaration reads absence as empty rather than as an error: an absent templates.toml yields an empty template registry (repository_state/mod.rs).
Planning

One closed, fallible planning entry point

pub fn derive_materialization(
    image: &RepositoryImage,
    request: MaterializationRequest<'_>,
) -> Result<MaterializationPlan, RepositoryStateError>
  • MaterializationRequest is closed with five variants: SemanticMutation, RenderConfiguredProjections, RepairDerivedState, Initialize, ApplyProfile.
  • Three of them carry RepositoryDeclarations parsed from the captured image, so derivation reads nothing the image does not already hold.

The signature above is exact, from crates/jit/src/repository_state/mod.rs, with only its opening brace elided. Derivation is fallible and performs no filesystem access.

Planning

Determinism is a tested property

  • Plan identity is a SHA-256 digest over the layout, capture spec, entries, listings, pinned evidence, linked worktrees, semantic seed, intent, and normalized delta, emitted as bare lowercase hex with no algorithm prefix.
  • Reordering a delta's actions does not change plan identity, and equal plan identity tracks equal normalized deltas.
  • Rendering a managed document against a claim set is idempotent, and every byte outside a claimed region survives unchanged and in order.

Properties: prop_plan_hash_invariant_under_action_reorder, prop_plan_hash_equality_matches_normalized_delta_equality (repository_state/image_plan_hash_property_tests.rs); prop_render_managed_document_round_trips (repository_state/managed_document_property_tests.rs).

Planning

What you can actually inspect

  • The plan is an in-memory value. MaterializationPlan derives Debug, Clone, PartialEq, Eq and no serializer, and no command emits it.
  • The emitted preview is jit profile apply --dry-run --json, which reports the same plan identity alongside every package target.
  • Its target vocabulary is path, action, executable; the underlying delta vocabulary is CreateDirectory, WriteFile, SetMode, DeleteFile, each carrying the preimage it expects.

Types: MaterializationPlan in repository_state/mod.rs; ProfilePlanResult and ProfileTargetChange in crates/jit/src/profile/application.rs; RepositoryAction in repository_state/image.rs.

Publication

Publication has one failure model

Narrative stepResponsibilityFailure result
capturerecord exact preimages and root identityno writes
preparestage every target and a durable journalrecover the old state
publishreplace the complete validated file setroll forward or roll back
commitmake publication irreversible, clean the journalcomplete new state
The observable contract is all-old or all-new, across interruption and process restart: every mutation session opens by recovering any pending journal first.

Those four words are this deck's labels, not a code enum. The journal records RepositoryActionProgress (Planned, Prepared, BackupReady, Published, Restored) per action and TransactionDecision (Prepared, Committed, RolledBack) per transaction, in storage/transaction_journal.rs.

Adoption

One path serves the mutation surface

ConsumerCoupled state planned together
init / re-initconfig, rules, schemas, attributes, projections
profile applycontributions, assets, regions, provenance, audit
config / gate / template editsdeclaration plus every affected materialization
project renderall selected targets, including shared targets
issue / dependency / docsrecords, index, events, and coupled outputs
export to an in-repository targetsource mutation and the published target

Two neighbours sit outside it by design. Claims and leases live under .git/jit, outside both repository roots (@/charter/D-4): the claims log appends and the claims index publishes by temp file plus rename (storage/claim_coordinator.rs, storage/worktree_paths.rs). An export to a path outside the repository publishes through the external atomic-write path, and snapshot staging writes into a temporary directory first (repository_state/export.rs, commands/snapshot.rs).

Managed prose

One marker engine, multiple policies

Mechanics are shared

  • strict marker parsing
  • nested-region support
  • crossing and duplicate rejection
  • byte-preserving splice

Semantics stay separate

  • profile ownership
  • projection ownership
  • placement policy
  • rendering policy
Sharing the primitive removes duplicate marker logic without pretending every producer owns prose in the same way.

Engine: compose_managed_documents and render_managed_document in repository_state/managed_document.rs. Both producers call it: projections in repository_state/materialize.rs, profile regions in repository_state/profile_apply.rs.

Validation

Repair derived state, never redefine authority

jit validate          # diagnose missing or stale materializations
jit validate --fix    # recompute from declarations; publish one plan
jit validate          # exact, idempotent clean result
  • Expected bytes are recomputed from declared configuration and registries.
  • Unrelated content and authored rule prose stay byte-for-byte intact.
  • Malformed or ambiguous ownership fails before publication.
A projection may repair derived assertions. It must not silently become authority over authored semantics.

Repair routes through MaterializationRequest::RepairDerivedState, the same producer graph as ordinary mutation. Idempotence is asserted in commands/validate.rs.

Authority

The source-of-truth hierarchy is explicit

StateRoleMay override declarations?
config + registriessemantic authorityyes, by authorship
schemas + projections + managed regionsderived materializationno
profile recordsprovenance and ownershipno
transaction journalsrecovery stateno

The project invariant derived-state-coherence states this, and .jit/invariants.toml declares it kind = "advisory": it is documentation, not a checked rule. What mechanically holds the third column is the closed producer graph plus the ExpectedPreimage that every action revalidates at publication (repository_state/image.rs).

Performance

What bounds the work

Automatic readiness transitions open repository mutation sessions only for issues that are actually eligible. Blocked backlog issues cost none.

  • A deterministic model of one eligible Backlog issue, 64 blocked ones, and their open blocker asserts exactly two session opens (test_check_auto_transitions_opens_sessions_only_for_eligible_backlog_issues, crates/jit/src/commands/issue.rs).
  • The same model's 65 Backlog issues predict 130 session opens for a path that opens a session per Backlog issue. The 2 is measured; the 130 is a model prediction.

The 130 is recorded as "130 predicted" in the narrative archives dev/archive/cdc840ad-completion-report.md and dev/archive/cdc840ad-progress.json.

Performance

What bounds the work (cont.)

  • Bulk update carries the same bound: one session per issue that needs a change, plus one shared verification session that confirms the rest are no-ops (test_apply_bulk_update_session_budget_scales_with_issues_needing_change, crates/jit/src/commands/bulk_update.rs).
  • Repository size is not the cost driver. Whole-repository validation recorded duration_ms 1536 and 1538 in two repo-validate gate runs, at commits a12666a2 and 8b02e864.

Gate-run artifacts: .jit/gate-runs/3e8ea1d1-3b40-49d2-9f03-f43ac2284b91/result.json and .jit/gate-runs/b8c84e03-2388-4def-a5ae-ec859229536b/result.json, field duration_ms. Measure session opens and elapsed time together: latency alone does not reveal an accidental per-issue recapture loop.

Future development

Where this goes next

  1. Performance as a maintained contract: regenerate the recorded session-cost profile as the surface grows; keep session-open budgets under test.
  2. Explainability: expose plan and repair previews from the existing pure planner, on the path that already emits a dry run.
  3. Profile lifecycle: build safe upgrade and removal on captured ownership and provenance, without a second planner.
  4. Typed integrations: let new consumers contribute typed intent rather than acquire private publication logic.

Today's baseline for item 1: dev/studies/perf/session-cost-c488ef85.json > machine, method, commands[], plus the two session-open budget tests named in full on the "What bounds the work" slides (crates/jit/src/commands/issue.rs, crates/jit/src/commands/bulk_update.rs).
