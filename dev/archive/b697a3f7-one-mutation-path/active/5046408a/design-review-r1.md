# 5046408a independent design review

Verdict: **FAIL — not ready for implementation.** The plan correctly identifies its bootstrap blocker and respects the data-history guard ruling, but current redo authority cannot resolve that blocker for all permitted invocations. Findings 1–2 require an accepted design before implementation; findings 3–4 need concrete plan corrections.

Reviewed the assigned worktree's `AGENTS.md`, issue brief, `dev/active/5046408a/design.md`, actual shared bootstrap/storage/configuration code, and external plan DEC-04/23/27. This is a design review, not validation of an implementation. No source, plan, tracker, or Git changes; no builds or gates.

## Findings

1. **Blocking: a pending record does not identify the worktree whose files it committed to change.**

   `storage/redo_record.rs:56` carries operation paths, complete *new* file bytes, and an event append. Its serialized header (`:298`) names only root classes and relative paths; it carries neither the writer's worktree root nor the pre-mutation configuration or environment selection. `storage/redo_apply.rs:168` resolves those paths against capabilities supplied by its caller. `storage/repository_state_store.rs:644` takes a finished layout, locks its worktree first, opens its capabilities, and then applies the leftover record. It does not derive the original root from the record.

   Concrete ambiguity: a writer selects code directory A through `JIT_WORKTREE_ROOT`, commits a record containing `Worktree/docs/x.md`, and is interrupted. A later invocation selects directory B with unchanged data/config. The record contains no evidence distinguishing A from B. Reading current config, inspecting the record's config put, or parsing configuration through the existing parser cannot recover the missing fact. A config change from A to B in the same record creates a second ambiguity: the new config bytes name B while the committed worktree operations were planned against A. A partially applied record can already have installed those new config bytes. An explicit override on the recovering invocation is a fresh selection, not proof of the interrupted writer's selection.

   Therefore the existing representation cannot safely complete arbitrary pending worktree writes under the proposed selectable-root contract. Returning retryable conflict is correct for reads but is not a complete mutation/recover solution: repeatedly rejecting a durable record leaves `jit recover` unable to fulfill `@/inv/atomic-writes`. Applying data operations first or interpreting the postimage as the original root silently changes recovery semantics and must not be implemented.

   **Exact steward decision:** authorize a narrowly scoped change to the durable redo representation so a record involving worktree targets binds the target root selected when it was committed, with explicit identity/path validation, recovery lock ordering, and handling when that root is unavailable or a new invocation selects another root; or explicitly amend the recovery/root-selection contract to allow an unresolved record requiring external intervention. Recommend the durable record binding, within the existing single-record authority, subject to a separately reviewed concrete design. This is a recommendation for authorization, not authorization to extend this issue or change the format. A hidden sidecar/global registry, guessed root, or assumption that environment/config never changes is not an acceptable resolution. The plan currently expressly disallows redo-semantic changes (`design.md:35`), so the worker cannot resolve this alone.

2. **High: even the no-pending-record path needs an admitted configuration-to-layout handoff, not two independent reads.**

   The apparent parser cycle is removable: `config.rs:1223` uses a layout only to read declaration bytes, while the authoritative pure parser already exists as `declarations::assemble_configuration` (`declarations/mod.rs:26`). Share that parser; do not add a root-only TOML interpretation. However, the current optimistic session requires a full layout and two-root capabilities (`storage/capability_fs.rs:81`, `storage/repository_state_store.rs:711`). The proposed data-only capture is new factoring of existing mechanisms, not an API that already exists.

   The actual admission token is record presence plus event-log length/tail and root-identity checks (`storage/repository_state_store.rs:407`, `:609`, `:810`), not a standalone generation counter. Keep this same protocol and bounded retry ownership. A safe no-record design can capture data-root declarations through no-follow capabilities, parse through the shared assembler, resolve the candidate root, and retain/revalidate that observation across the handoff. On reads, admission must cover the configuration used to bind the layout together with the consumer's repository capture: admitting config, discarding its observation, and opening a later snapshot can combine root A with config B. On mutations, revalidate the selection after acquiring the correctly ordered session locks **before** applying any newly discovered record or admitting a session; restart on a change. Claim-first session reopening and retained sessions need the same contract.

   Reuse/factor storage's capture, identity, and admission primitives rather than reimplementing their matrix in commands. No reader acquires a writer/bootstrap lock or performs recovery. Pending-record readers return the existing retryable conflict. The minimal clean-state factoring is supportable from existing code; it does **not** resolve finding 1. Specify how it integrates with the steward's recovery decision before calling the bootstrap design accepted.

3. **Medium: the consumer list leaves real split-layout inconsistencies unresolved.**

   The explicit core mapping is sound: checker cwd and evidence (`commands/gate_check.rs:1231`, `:1251`) and explicit drift (`commands/validate.rs:1205`) use code; the registry history guard uses data. `git_repository`, common-dir/claims coordination, linked-store classification and primary-data mapping must keep data authority (`storage/worktree_paths.rs:82`, `:257`, `:349`). An external non-Git data store must not acquire a history guard from the relocated/code checkout. Preserve the existing relocated coordination context independently when it differs from code.

   But `design.md:41` says document history and committed assets retain their current “data/write or coordination role” without assigning that role. Today document content/diff paths use `RepositoryLayout::worktree_root()` (`commands/document.rs:684`, `:756`; `storage/json.rs:1330`), while document history uses `paths.git()` (`commands/document.rs:728`, `:898`) and missing-asset checks use `write_checkout()` (`:1239`). After `git()` is preserved as data authority, blindly retaining those accessors queries tracker history for code-root documents. State the intended document-root authority explicitly and make its read/history/asset views agree; code is the natural existing layout-relative interpretation, unless the steward specifies otherwise.

   Also inventory direct root consumers, not just Git accessors: `storage/json.rs:596` builds a primary fallback layout using the primary *data checkout* as the worktree root. With a repository rooted at `.jit` this can reproduce equal data/worktree roots. `storage/worktree_identity.rs:175` reconstructs a layout for identity reads, and `commands/worktree.rs:101` reports `worktree_root` alongside a coordination branch. Specify projected layout construction and output identities so data checkout facts cannot become code layout roots by accident. Keep claims/identity branches and lease validation on their existing data/relocated coordination authority (`commands/claim.rs`, `storage/claim_coordinator.rs:678`, `commands/validate.rs:1347`). `commands/init.rs:302` and `commands/profile.rs:1170` need explicit data/write roles, not a global `write_checkout()` repurposing.

4. **Medium: correct unsupported or ambiguous preservation claims.**

   - `design.md:41` says the committed-issue fallback reads code HEAD. That fallback is already removed: `storage/json.rs:1116` uses local/primary storage, and `:2448` owns the property that a committed issue deleted locally is absent from every read. Delete the obsolete statement; preserve absence of the HEAD tier and the existing primary-store fallback. Do not reintroduce either a code or data HEAD fallback.
   - `design.md:31` says to physically resolve symlink aliases while preserving current protections. Current root discovery rejects symlinks anywhere in root ancestry (`storage/repository_state_store.rs:1941`, `:1976`); `repository_state/path.rs` is the pure evidence/containment layer. Specify no-follow rejection and source-aware error wrapping. Canonicalizing a supplied symlink first and then validating only its destination would bypass the current policy. Alias reuse for Git observations (`storage/worktree_paths.rs:37`) is not permission to accept a symlinked storage root.

## Steward follow-up: concrete recovery options

The steward agrees that D-17/atomic-writes requires the original committed targets and will resolve this contained storage decision without user escalation. The design verdict remains FAIL until the resolution is incorporated and reviewed. The following options are proposals, not implemented behavior.

**Option A — recommended: bind the worktree root once in the redo record.** Add a typed optional worktree-target binding to the existing record header: the normalized absolute, no-follow worktree root selected by the committing session plus the root's existing filesystem identity evidence. Require it exactly when any operation addresses `RepositoryRootClass::Worktree`; data-only records need no code root. Construct the binding from the authoritative session layout during record production, never from a second config/env lookup. Parsing validates the binding's structure and its correspondence to the operation root classes. Before any replay write, recovery opens the recorded root without following links and verifies its identity, then uses it for every worktree operation. This makes root authority part of the same durable commit point; it adds no sidecar and duplicates no per-operation absolute paths. The existing statement that no process-local information enters the record (`storage/redo_record.rs:143`) must deliberately change: scratch records are local recovery state, not portable repository configuration. No compatibility shim is justified in this greenfield project; the canonical format version/fixtures must change together, with an explicit failure for unsupported records.

**Option B — less attractive: bind physical targets per operation.** Store each worktree operation's absolute target and containing-root identity in the same redo record. It can preserve original targets, but repeats authority across operations, expands validation and overlap rules, and undermines the existing root-relative representation. It offers no benefit for a record that has exactly one worktree root. Reject in favor of A under D-18.

Keeping the current format while demanding that operators reproduce the original environment is not a safe third option: the record cannot verify that they did. A fingerprint alone can detect some mismatches but cannot locate the original root. New config bytes alone do neither. Both fail automatic recovery of the original committed worktree targets.

### Recovery and movement behavior for option A

- Read commands retain lock-free admission and never apply records. Any pending record yields Busy/retryable conflict under the existing bounded policy; no Git process is needed to inspect it.
- A mutation/recover operation reads the record through data-root no-follow capabilities to learn its binding. Treat this initial peek only as a lock-selection candidate. Acquire the recorded worktree bootstrap lock before data bootstrap/repository/events locks in the existing order, then reopen/revalidate the record and both root capabilities under serialization before applying anything. If the record/binding changed, release and restart; never replay a new record using the peek's old root. Avoid a data-lock-then-worktree-lock inversion. Preserve the pre-lock linked-data write refusal and audit contract as part of the revised bootstrap protocol.
- A data-only record can recover through a data-only capability/lock path, without inventing a code root. This path must not acquire a worktree lock while holding data locks. It can apply a config update and then release its recovery guards before final selection. Do not construct a fake two-root layout simply to satisfy today's signatures.
- Replay the whole pending record against its recorded root before using recovered configuration to bind the next operation. If fresh config/env selects another root, release the old recovery session and construct/revalidate the new one in normal lock order. A retained mutation session must never silently change layouts. Startup recovery counts and `jit recover` error classification remain explicit.
- A missing, moved, inaccessible, replaced, or symlink-rebound recorded root produces a typed recovery failure naming the recorded path and reason, leaves the record intact, and performs no replay writes. A different directory at the same path is not the original target. Do not search Git worktrees or substitute the current override/config root. Automatic recovery resumes only when the original root is available at its recorded path with matching identity; otherwise a separate, explicitly designed repair mechanism would be needed and is outside this issue. This conservative behavior prioritizes original-target safety over automatic relocation.
- A newly selected invalid code root remains a typed selection error. Specify that completion of an older committed record precedes final validation of the new invocation root, consistent with recovery-before-validation. This does not authorize the new invalid invocation to publish a mutation.

The data-root protocol must still detect root replacement between the peek and lock acquisition. The new binding supplies missing worktree authority; it does not replace current capability safety, commit admission, event offset, or idempotent application rules.
