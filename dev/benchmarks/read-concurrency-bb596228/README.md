# Concurrent readers beside a continuous writer (jit:bb596228)

Reader and writer throughput of `jit doc check-links --scope issue:<id> --json`
beside one back-to-back `jit issue update <id> --priority` writer, on the binary
before the lock-free read session and on the tip (`@/charter/D-22`,
`@/charter/D-25`). The verdict is **pass**. Every figure below is copied from
`summary.json`, which `validate.py` rederives from `raw/`.

## Harness, builds, and conditions

- **Harness:** [`scripts/benchmark-read-concurrency.sh`](../../../scripts/benchmark-read-concurrency.sh),
  run as `READ_BENCH_WORK_ROOT=/mnt/nvme/jit/bench-bb596228 scripts/benchmark-read-concurrency.sh`.
  Its header states the arms, the order and the exit codes.
- **Before (`base`):** `369d35a42f0ecc5067d930415c44908defdc0e36`, where the link
  check opens a mutation session, built in a detached worktree with
  `cargo build --release --locked -p jit`; binary sha256
  `b5ba9298e54fda902b68858b8e7a930e6b29669df5e2fb11bb5f4420d126da4a`.
- **After (`tip`):** `8070b5bb416484b75417e4b8fd960aa6f5cfc629` (the harness commit;
  its Rust sources equal `ed78166b2`), built the same way; sha256
  `36764622df86307fff42d85fa13b965417992b0454ad5444dca904d3908c14f7`.
- **Fixture:** per binary, the 665-issue session-cost fixture
  (`scripts/benchmark-session-cost.sh` fixture mode, generated by that binary) plus
  one unpinned document on the target issue, so the read opens a session. Each arm
  runs on a fresh copy.
- **Machine:** AMD Ryzen 9 5900X, 24 logical CPUs, Linux 7.2.14-arch1-1, fixtures on
  ext4. The harness waited 90 s for a 1-minute load below 2.0 (1.97 at the start).
  Arms then ran with no process isolation on a shared host; per-arm load averages
  are in `raw/arms/`. The measured loops themselves load nine processes, and other
  sessions raised the 1-minute load to 15 in round 2, where both binaries' writer
  rates halved. The ratios compare arms of one round, which is what the verdict uses.

## Results

Medians over five rounds; rates are successful completions per second inside the
15 s window.

| binary | N | R(N) | W(N) | reader p95, ms |
|---|---|---|---|---|
| base | 0 | – | 16.67 | – |
| base | 1 | 5.67 | 16.60 | 439 |
| base | 8 | 91.8 | 12.0 | 274 |
| tip | 0 | – | 18.13 | – |
| tip | 1 | 59.7 | 16.2 | 29.2 |
| tip | 8 | 531 | 17.4 | 35.5 |

| median per-round ratio | base | tip | tip threshold |
|---|---|---|---|
| R(8)/R(1) | 16.60 | **8.91** | ≥ 4 |
| W(8)/W(0) | 0.72 | **1.006** | ≥ 0.8 |

- The tip passes both thresholds; the per-round values are in `summary.json`.
- The base ratio R(8)/R(1) is not the ≈1 the design expected of a serialized
  reader. One base reader waits behind the back-to-back writer for the exclusive
  lock (p95 439 ms), so R(1) is depressed and eight contending readers win the lock
  more often. In absolute terms the tip's eight readers complete 5.8 times as many
  reads as the base's, and the base's readers cut its writer to 0.72 of W(0).
- Tip readers that exhausted their optimistic attempts exit 12
  (`RETRYABLE_CONFLICT`) instead of waiting, as D-25 decides: 5.1% of N = 1 reads and
  3.2% of N = 8 reads. Of these, 1,356 fail with
  `Failed to read configuration`, 177 in repository root selection and 60 in the
  link check itself (`raw/arms/*-tip-*.json`, `failures`). These do not count as
  completions. No writer invocation and no base reader failed.

## Verification

```console
$ python3 dev/benchmarks/read-concurrency-bb596228/validate.py
$ python3 dev/benchmarks/read-concurrency-bb596228/validate_selftest.py
$ (cd dev/benchmarks/read-concurrency-bb596228 && sha256sum -c SHA256SUMS)
```

`validate.py` rederives every arm's rates and p95, both ratios per round, their
medians and the verdict from `raw/`. It refuses a verdict below 16 logical CPUs and
rejects evidence recorded with smoke-run overrides. `validate_selftest.py`
exercises the derivation on synthetic arms.
