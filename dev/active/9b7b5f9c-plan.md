## 2. Technical soundness and architectural fit

- **Approach:** Build a generic package-and-plan domain subsystem around a single immutable embedded package. Pure code parses and validates the manifest, enumerates declared bytes/modes, computes semantic registry/projection results, constructs a sorted final-state plan, and classifies conflicts without I/O. Storage owns containment checks, snapshot identities, staging, synchronization, publication, rollback, and recovery. Commands resolve the embedded package and orchestrate planning/application. CLI/output/schema own presentation. This follows the repository's declared pure-domain → storage → command → CLI/output layering (`AGENTS.md:134-145`).
- **Package source of truth:** Check in exactly one `profiles/jit-dogfood/manifest.toml` plus its declared `assets/` tree and compile that directory with `include_dir`. The manifest owns identity, compatibility, target paths, semantic contributions, projection operations, and executable semantics; assets own exact bytes. A generic validator rejects missing or undeclared entries and sorts paths before validation, hashing, planning, and output. Generate `ProfileManifest` JSON Schema through schemars, compute per-target SHA-256 and a canonical package digest from the same data, and derive public planning-preset compatibility data/assets instead of maintaining a second inventory. Existing schemars and SHA-256 patterns are at `crates/jit/src/schema.rs:160-202` and `crates/jit/src/snapshot.rs:221-225`.
- **Semantic planning and validation:** Read repository inputs into an I/O-free snapshot and produce exact final bytes/modes for absent files, byte-identical files, keyed registry merges, and managed-region splices. Differing unmanaged targets, structurally different keyed definitions, malformed regions, duplicate ownership, unsafe paths, or incompatible JIT/repository formats are conflicts before staging. The pure projection splice already proves preservation of bytes outside its markers (`crates/jit/src/validation/projection.rs:176-225`). Validate the complete virtual final repository, not each output in isolation, then acquire the one outer `RepoWriteLock` and rebuild or identity-recheck the complete plan under it (`crates/jit/src/storage/repo_lock.rs:57-88`).
- **Durable transaction and recovery:** Add reusable storage machinery under `.jit/tmp/` with a versioned journal. Durable `prepared` state records expected original identity/mode, final identity/mode, stage/backup locations, action order, and deterministic plan hash after all stages have been synced. Replacements rename the original aside before renaming the prepared stage into place; new targets use verified no-replace publication. The installed profile record and an exact replacement image of `events.jsonl` containing one typed event are ordinary participants while the event lock is held after the repository lock. After all targets/directories are synced, persist `committed`; cleanup failures after that point return committed success plus a visible warning. Before later mutation, recover `prepared` by identity-checked reverse rollback and `committed` by verification/roll-forward cleanup. Heartbeat storage demonstrates file and parent-directory synchronization (`crates/jit/src/storage/heartbeat.rs:193-227`); artifact mutation demonstrates no-follow staging and no-replace publication (`crates/jit/src/storage/artifact_mutation.rs:135-297`). Neither is falsely described as a set transaction.
- **Truthful guarantees:** A normal returned pre-commit failure promises tracked targets restored only after compensating rollback succeeds. Rollback that cannot prove restoration returns a distinct recovery-required error and retains the journal. A crash can expose a mixed set until successful recovery; the contract is eventual all-old or all-new, not instantaneous multi-file atomicity. The writer lock excludes cooperating JIT writers but does not give snapshot isolation to unlocked readers or transactional behavior to external writers. Rename-aside preserves original file bytes and inode-backed metadata, but not directory timestamps, `ctime`, ACL/xattr state, or hostile-filesystem behavior. Same-volume/supported-filesystem preflight is mandatory; Unix mode semantics are manifest-derived, while Windows reports executable mode as not applicable. These limits are part of errors, docs, and tests rather than hidden caveats.
- **Profile orchestration and event model:** Treat unchanged reapplication as a zero-action success, based on final bytes/modes and installed hashes, with no journal and no event. Any real application publishes the minimal record and typed profile-applied event atomically with the package targets. The event model is a closed enum/catalog projected into schema (`crates/jit/src/domain/types.rs:1060-1068`; `crates/jit/src/domain/event_catalog.rs:65-193`), so the event addition updates every catalog/schema/sample consumer in one change.
- **Portable methodology:** Extend the generic gate checker enum with data-neutral validation and coverage operations, not dogfood gate keys. Keep review execution configurable; package its prompt and a default structured-warning placeholder. Put `jit-dogfood`, taxonomy names, template roles, gate keys, skill paths, and projection content only in package data, satisfying the domain-agnostic boundary (`AGENTS.md:176-178`). Existing planning preset APIs remain functional but derive their definitions/assets from the package; this plan neither deprecates nor adds lifecycle behavior to them.
- **Consumer sweep:** CLI work updates `crates/jit/src/cli.rs`, `main.rs`, command/domain/output/schema surfaces, init and schema integration tests, plus `mcp-server/curated-tools.json` and MCP tests because MCP generates from live command schema (`mcp-server/index.js:16-23`). Package authority touches gate preset definitions/tests, templates/projections, portable scripts/prompts, all installed skills and their references, adopter examples, and canonical docs listed in the investigation's consumer sweep (`dev/active/9b7b5f9c-investigation.md:310-482`). Historical `.jit/issues`, events, gate runs, and archived reports are evidence, not migration targets.
- **Protected boundaries:** Plain init continues to scaffold empty gates and generic hierarchy/rules (`crates/jit/src/storage/json.rs:595-636`; `crates/jit/src/main.rs:1754-1800`). No engine branch names a dogfood type, gate, template, content path, or workflow. No profile operation uses claim/worktree/hook infrastructure. No post-1.0 lifecycle noun is reserved in the manifest, record, transaction, or CLI.

## 4. Risks and actionability

| Risk / open question | Severity | Mitigation or decision |
|---|---|---|
| “Atomic application” is overstated as instantaneous set atomicity. | Critical | Adopt the prepared/committed journal and publish the exact guarantee boundary in errors, docs, and tests: handled pre-commit failure restores tracked state only after successful rollback; rollback uncertainty requires recovery; crashes converge after recovery; unlocked readers may see a midpoint. |
| A late record or event failure leaves package files committed without provenance. | Critical | Make the installed record and exact next event-log image transaction participants under repository-then-event lock order; no conventional best-effort append is permitted. |
| Crash recovery chooses the wrong side or overwrites an unexpected occupant. | Critical | Journal expected original/final identities and phases durably, identity-check every forward/reverse action, fail closed with the journal retained, and inject failures around every sync/rename/decision/cleanup step on Unix and Windows. |
| Path, symlink, or filesystem behavior escapes the repository or weakens rollback. | Critical | Reject platform-absolute/traversal/overlapping paths and symlink components, preflight same-volume supported rename/no-replace behavior, recheck identities under the repository lock, and test adversarial cross-platform inputs and races. |
| The package becomes a second hardcoded methodology. | High | Keep all type names, gate keys, roles, paths, prompts, and content in the manifest/assets; test the generic planner/checkers with unrelated vocabulary and enforce a one-to-one embedded inventory. |
| Compatibility presets drift from the embedded package. | High | Derive public preset definitions/assets from the manifest/package source and add a repository-wide consumer search plus equivalence tests; do not hand-maintain a compatibility copy. |
| A passing placeholder is mistaken for a completed AI review. | High | Emit a visible warning in human output and a structured warning finding, have repository validation warn while configured, and test both surfaces. |
| The MVP regrows the continuation epic's lifecycle surface. | High | Keep local loading, composition, dependencies/incompatibilities, variables/secrets, shared ownership, reconfiguration/diff, upgrade, and removal absent from all v1 types/APIs/fixtures; the final matrix searches schema and source for accidental exposure. |
| Package assets accidentally include repository-local policy or become too large. | Medium | Maintain an explicit adopter-neutral content review, one-to-one declaration check, and bounded count/size test; exclude charter/glossary/development lifecycle, CI, and language-specific content. |
| Documentation duplicates package facts and drifts. | Medium | Give commands and guarantees one canonical reference, derive volatile schema/registry material, and make other entry pages link to it under mechanical link/citation/projection checks. |
| Executable modes and rename guarantees differ by platform/filesystem. | High | Manifest owns executable semantics; apply modes before publication on Unix, report not-applicable on Windows, reject unsupported/cross-volume publication, state metadata limits, and run platform-specific failure tests rather than inferring parity. |

Every load-bearing choice is resolved below. The decomposition items contain their own outcome, criteria, dependency edges, gate recommendation, consumer sweep, and green landing boundary; no worker must re-derive the architecture or deferred-scope line.

## Decisions

- **D1 — Embedded package representation:** chosen **one authored `profiles/jit-dogfood/` manifest/assets tree recursively compiled with `include_dir`, with no optional features**. Rejected: per-file `include_bytes!` (requires a duplicate Rust inventory), custom `build.rs` generation (bespoke traversal/code-generation complexity), tar/zip embedding (derived archive and extraction/path surface), and `rust-embed` (debug behavior can read the source tree). Pin and review the dependency, derive schema/hashes/modes, and bound package size/count.
- **D2 — Publication and recovery protocol:** chosen **durable prepared/committed journal, rename-aside originals, verified no-replace new files, synchronized decision points, and mandatory identity-checked recovery under `RepoWriteLock`**. Rejected: in-memory backup plus rollback (cannot authoritatively recover after process loss), reuse of single-file atomic write (not a set transaction), and reuse of archive execution (explicitly permits reconcilable partial progress). The guarantee is eventual all-old/all-new after successful recovery, not instantaneous multi-file atomicity or reader isolation.
- **D3 — Provenance/event consistency:** chosen **installed record and exact typed event-log next state as transaction participants, with unchanged reapplication producing neither**. Rejected: append after file publication (late failure splits state) and best-effort telemetry (violates the audit contract).
- **D4 — Package authority and compatibility:** chosen **manifest/assets own all reusable dogfood facts and existing public planning presets derive their definitions/assets from that source**. Rejected: independent preset/package inventories (drift) and removal/deprecation work (not required by the MVP and risks compatibility).
- **D5 — Init integration:** chosen **plain init stays neutral and explicit `init --profile` delegates to the same generic application service after successful minimal initialization**. Rejected: a separate init installer (behavior drift) and implicit/default profile selection (violates methodology neutrality).
- **D6 — Gate portability:** chosen **generic built-in checker operations for deterministic validation/coverage plus an editable external review command with a structured-warning passing placeholder**. Rejected: source-relative scripts that shell back into JIT or require `jq` (not portable), and silent passing placeholders (false confidence).
- **D7 — v1 installed state:** chosen **minimal immutable application provenance only: profile ID, version, embedded origin, and content/package hashes**. Rejected: ownership graphs, resolved variables, dependencies, lifecycle history, or future transaction actions (all belong to continuation epic `c639cfb5`).
- **D8 — Documentation ownership:** chosen **one canonical profile reference with audience-specific pages linking to it**. Rejected: repeated inventories/walkthroughs (staleness) and removing advanced manual customization guidance (loss of legitimate adopter capability).
- **D9 — Deferred-scope boundary:** chosen **no local directories, composition, profile dependency/incompatibility model, variables/secrets, shared ownership, reconfiguration/detailed diff, upgrade, or removal anywhere in the v1 manifest, record, transaction, CLI, schema, fixtures, or tests**. Rejected: placeholder/reserved lifecycle fields (they commit the API prematurely) and opportunistic slices from the original 23-requirement brief (they undo `@/charter/D-8`).
- **Assumptions:** The embedded package remains a bounded text-asset tree suitable for `include_dir`; a count/size guard makes growth visible. Supported storage exposes same-volume rename and directory synchronization sufficient for the documented recovery contract; unsupported environments fail during preflight. The existing public planning-preset commands remain supported for v1 but their authored data becomes derived compatibility output. These assumptions do not reopen an owner decision and do not authorize deferred lifecycle work.
