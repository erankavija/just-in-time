## 2. Technical soundness and architectural fit

- **Approach:** Build a generic package-and-plan domain subsystem around a single immutable embedded package. Pure code parses and validates the manifest, enumerates declared bytes/modes, computes semantic registry/projection results, constructs a sorted final-state plan, and classifies conflicts without I/O. Storage owns containment checks, snapshot identities, staging, synchronization, publication, rollback, and recovery. Commands resolve the embedded package and orchestrate planning/application. CLI/output/schema own presentation. This follows the repository's declared pure-domain → storage → command → CLI/output layering (`AGENTS.md:134-145`).
- **Package source of truth:** Check in exactly one `profiles/jit-dogfood/manifest.toml` plus its declared `assets/` tree and compile that directory with `include_dir`. The manifest owns identity, compatibility, target paths, semantic contributions, projection operations, and executable semantics; assets own exact bytes. A generic validator rejects missing or undeclared entries and sorts paths before validation, hashing, planning, and output. Generate `ProfileManifest` JSON Schema through schemars, compute per-target SHA-256 and a canonical package digest from the same data, and derive public planning-preset compatibility data/assets instead of maintaining a second inventory. Existing schemars and SHA-256 patterns are at `crates/jit/src/schema.rs:160-202` and `crates/jit/src/snapshot.rs:221-225`.
- **Semantic planning and executable final-state validation:** Introduce a read-only `RepositoryView` interface at the storage/validation boundary. A filesystem view preserves current behavior; an overlay view resolves every planned path to final bytes/mode and falls through to the captured base snapshot for untouched paths. Config, effective rules and schemas, gate/template registries, item-kind sources and links, projection drift, issue/event/index records, DAG integrity, namespace/hierarchy rules, and whole-repository integrity all load through that view. The command constructs one overlay from the exact sorted plan and runs the same validation pipeline against it before staging; no validator may reopen the live root. Under `RepoWriteLock`, the command rebuilds the snapshot, overlay, and validation result rather than trusting pre-lock evidence. The pure projection splice remains the byte-preserving merge primitive (`crates/jit/src/validation/projection.rs:176-225`), while the current filesystem-bound reads in `commands/mod.rs` and `commands/validate.rs` are migrated to the injected view.
- **Durable transaction, directories, and universal recovery:** Add reusable storage machinery under `.jit/tmp/` with a versioned journal. `prepared` records file and directory actions, expected original/final identity and mode, stage/backup locations, action order, and plan hash after durable staging. Directory-create actions are shallow-to-deep, reject symlink/unexpected occupants, sync their parents, and are removed deepest-first on rollback only when empty and transaction-created. File replacements rename originals aside; new targets use verified no-replace publication. The installed record and an exact next `events.jsonl` image are participants while the event lock follows the repository lock. The next image preserves the complete repaired existing prefix before appending one typed event. After final sync, persist `committed`; cleanup failure is committed success with warning. The single mutation entry point that acquires `RepoWriteLock` first checks and recovers any journal before yielding its guard; all `IssueStore`, config, gate, rule, document, event, archive, and template writers use that boundary, with a guarded internal variant preventing reentrant recovery and preserving repository-before-event lock order. Tests enumerate every mutation family so no direct writer bypass remains.
- **Truthful guarantees:** Per the approved REQ-04 clarification, conflicts/preflight failures mutate nothing and ordinary handled pre-commit failure is reported only after exact rollback. Rollback uncertainty returns a typed recovery-required error and retains the journal; interruption can expose a mixed set only until the mandatory next mutation recovery converges to all-old or all-new. The writer lock does not promise reader snapshot isolation or transactional external writers. Rename-aside preserves original bytes and inode-backed metadata, not directory timestamps, `ctime`, ACL/xattr state, or hostile-filesystem behavior. Same-volume/supported-filesystem preflight is mandatory; Unix mode semantics are manifest-derived and Windows reports mode as not applicable.
- **Profile orchestration and event model:** Treat unchanged reapplication as a zero-action success, based on final bytes/modes and installed hashes, with no journal and no event. Any real application publishes the minimal record and typed profile-applied event atomically with the package targets. The event model is a closed enum/catalog projected into schema (`crates/jit/src/domain/types.rs:1060-1068`; `crates/jit/src/domain/event_catalog.rs:65-193`), so the event addition updates every catalog/schema/sample consumer in one change.
- **Portable methodology:** Extend the generic gate checker enum with data-neutral validation and coverage operations, not dogfood gate keys. Keep review execution configurable; package its prompt and a default structured-warning placeholder. Put `jit-dogfood`, taxonomy names, template roles, gate keys, skill paths, and projection content only in package data, satisfying the domain-agnostic boundary (`AGENTS.md:176-178`). Existing planning preset APIs remain functional but derive their definitions/assets from the package; this plan neither deprecates nor adds lifecycle behavior to them.
- **Package/live source of truth:** `profiles/jit-dogfood/manifest.toml` and its asset tree are the sole authored reusable package source. A deterministic repository projection command materializes dogfood-consumed `.agents/skills/`, portable prompts/scripts, and the canonical packaged content standard from those assets; a drift checker regenerates into a temporary tree and byte-compares every projected live file. Contributors edit package assets, then render. Existing live paths remain consumers for dogfooding, never a second authored source; unrelated AGENTS prose and adopter docs outside the declared projection remain hand-authored and cite package facts.
- **Consumer sweep:** CLI work updates `crates/jit/src/cli.rs`, `main.rs`, command/domain/output/schema surfaces, init and schema integration tests, plus `mcp-server/curated-tools.json` and MCP tests because MCP generates from live command schema (`mcp-server/index.js:16-23`). Package projection owns preset definitions/tests, templates/projections, portable scripts/prompts, installed skills and their references, while adopter docs cite the manifest-derived reference. Historical `.jit/issues`, events, gate runs, and archived reports are evidence, not migration targets.
- **Protected boundaries:** Plain init continues to scaffold empty gates and generic hierarchy/rules (`crates/jit/src/storage/json.rs:595-636`; `crates/jit/src/main.rs:1754-1800`). No engine branch names a dogfood type, gate, template, content path, or workflow. No profile operation uses claim/worktree/hook infrastructure. No post-1.0 lifecycle noun is reserved in the manifest, record, transaction, or CLI.

## Decisions

- **D1 — Embedded package representation:** chosen **one authored `profiles/jit-dogfood/` manifest/assets tree recursively compiled with `include_dir`, with no optional features**. Rejected: per-file `include_bytes!` (requires a duplicate Rust inventory), custom `build.rs` generation (bespoke traversal/code-generation complexity), tar/zip embedding (derived archive and extraction/path surface), and `rust-embed` (debug behavior can read the source tree). Pin and review the dependency, derive schema/hashes/modes, and bound package size/count.
- **D2 — Publication and recovery protocol:** chosen **the owner-approved recoverable-publication contract implemented by a durable prepared/committed journal, rename-aside originals, journaled directory actions, synchronized decisions, and mandatory identity-checked recovery in the universal repository mutation guard**. Rejected: an unsatisfiable instantaneous set-atomic claim, in-memory rollback without recovery, single-file atomic write, and archive execution. Conflicts/preflight mutate nothing; ordinary handled failure follows exact rollback; uncertainty/interruption retains typed recovery state and converges before later JIT mutation.
- **D3 — Provenance/event consistency:** chosen **installed record and exact typed event-log next state as transaction participants, with unchanged reapplication producing neither**. Rejected: append after file publication (late failure splits state) and best-effort telemetry (violates the audit contract).
- **D4 — Package authority and compatibility:** chosen **manifest/assets own all reusable dogfood facts; a deterministic render projects this repository's live skill/prompt/standard consumers, and public presets derive from the same source under drift checks**. Rejected: independently authored live/package/preset inventories (drift) and removal/deprecation work (outside the MVP).
- **D5 — Init integration:** chosen **plain init stays neutral and explicit `init --profile` delegates to the same generic application service after successful minimal initialization**. Rejected: a separate init installer (behavior drift) and implicit/default profile selection (violates methodology neutrality).
- **D6 — Gate portability:** chosen **generic built-in checker operations for deterministic validation/coverage plus an editable external review command with a structured-warning passing placeholder**. Rejected: source-relative scripts that shell back into JIT or require `jq` (not portable), and silent passing placeholders (false confidence).
- **D7 — v1 installed state:** chosen **minimal immutable application provenance only: profile ID, version, embedded origin, and content/package hashes**. Rejected: ownership graphs, resolved variables, dependencies, lifecycle history, or future transaction actions (all belong to continuation epic `c639cfb5`).
- **D8 — Documentation ownership:** chosen **one canonical profile reference with audience-specific pages linking to it**. Rejected: repeated inventories/walkthroughs (staleness) and removing advanced manual customization guidance (loss of legitimate adopter capability).
- **D9 — Deferred-scope boundary:** chosen **no local directories, composition, profile dependency/incompatibility model, variables/secrets, shared ownership, reconfiguration/detailed diff, upgrade, or removal anywhere in the v1 manifest, record, transaction, CLI, schema, fixtures, or tests**. Rejected: placeholder/reserved lifecycle fields (they commit the API prematurely) and opportunistic slices from the original 23-requirement brief (they undo `@/charter/D-8`).
- **D10 — Final-state validation:** chosen **one read-only repository-view interface with filesystem and planned-overlay implementations, consumed by every repository-dependent validation pass and rebuilt under the write lock**. Rejected: validating only individual outputs (misses cross-file rules) and validating a staged copy through separate code (risks divergence from production validation).
- **D11 — Execution ordering and proof ownership:** chosen **author the real dogfood package before public command exposure, keep component tests in their owning leaves, and reserve the last leaf for a thin public-surface cross-platform journey**. Rejected: exposing a skeletal package between waves and an unbounded catch-all test/fix task.
- **Assumptions:** The embedded package remains a bounded text-asset tree suitable for `include_dir`; a count/size guard makes growth visible. Supported storage exposes same-volume rename and directory synchronization sufficient for the documented recovery contract; unsupported environments fail during preflight. The existing public planning-preset commands remain supported for v1 but their authored data becomes derived compatibility output. These assumptions do not reopen an owner decision and do not authorize deferred lifecycle work.
