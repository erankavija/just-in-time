## 1. Reproducible GitHub release workflow

**Question.** How can one exact source SHA prove tests and security passed, align every product version, create the release tag only after rehearsal, and publish a useful but small Linux release?

- **[VERIFIED]** The current tag workflow builds artifacts but does not depend on normal CI or security. Product manifests currently say CLI `0.2.1`, server `0.1.0`, MCP `0.1.0`, and web `0.0.0`; dual licensing is declared but license-text files are absent.
- **[CITED]** GitHub job `needs` dependencies run only after prerequisites succeed, and a failed/skipped prerequisite prevents the dependent job unless its condition overrides that behavior: [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds). Reusable workflows avoid copying CI into the release file: [reusing workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations).
- **[CITED]** GitHub's artifact-attestation Action can attest file paths and bind an SPDX JSON SBOM to an artifact with `id-token: write` and `attestations: write`; the workflow must still pin the Action itself to a reviewed full commit SHA: [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).
- **[CITED]** `workflow_dispatch` sets `GITHUB_SHA` to the last commit on the selected branch/tag, not an arbitrary `actions/checkout` input. Reusable workflows use the caller's `github` context. GitHub OIDC exposes `sha`, `ref`, `workflow_ref`, `workflow_sha`, `job_workflow_ref`, `job_workflow_sha`, repository IDs, and event identity, while artifact attestations record repository, commit SHA, workflow, and triggering event: [trigger semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch), [reusable workflow context](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#github-context), [OIDC claims](https://docs.github.com/en/actions/reference/security/oidc#oidc-token-claims), and [artifact-attestation identity](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/security/artifact-attestations).
- **[CITED]** With narrow exceptions, pushes made by a repository's `GITHUB_TOKEN` do not create new workflow runs; GitHub directs workflows that must trigger another workflow to use a GitHub App installation token or PAT instead. Installation tokens can be limited to selected repositories and permissions and expire after one hour: [`GITHUB_TOKEN` event behavior](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs) and [GitHub App installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).
- **[CITED]** Repository rulesets select GitHub Apps as bypass actors and can target tag name patterns; environment secrets can be withheld until required reviewers approve the job: [ruleset bypass permissions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#using-ruleset-enforcement-statuses), [rules available for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), and [deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
- **[CITED]** A full-length commit SHA is the only immutable way to reference an external Action. GitHub recommends auditing source and pinning to that SHA rather than a branch or version tag: [secure use of third-party Actions](https://docs.github.com/en/actions/how-tos/security-for-github-actions/security-guides/security-hardening-for-github-actions#using-third-party-actions).
- **[CITED]** With immutable releases enabled, publishing locks the associated tag and release assets against change or deletion. GitHub's required sequence is to create a draft, upload every asset, and publish only after the release is complete: [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).
- **Recommendation [ASSUMED].** Install one repository-only `contents:write` GitHub App as bypass actor for candidate and v1 tag rulesets. Candidate dispatch accepts freeze ID, uploads handoff/prepared, and embeds its exact ID/root digest in the annotated App tag. The App push reads that tag, downloads the handoff by exact ID, writes its own candidate-event-completed record, and passes its ID to producers/root assembly. After exact private tarball rehearsal, final authorization verifies absent public channels, runs live MSRV, uploads final-tag prepared, and embeds its ID/root digest in annotated `v1.0.0`. Exact readback writes completion. Recovery may complete an exact existing tag from the old prepared ID; if absent, that preparation is superseded and authorization restarts from rehearsal with fresh preflight/MSRV and a new prepared ID. After tag completion, reviewer-gated secret-free OIDC directly publishes the retained MCP tarball under its own prepared/completed recovery transition; GHCR/GitHub follow by exact IDs. Untrusted v* push publishing is forbidden, authenticated exact-ID resume is required.
- **Rejected.** Candidate creation with `GITHUB_TOKEN` (no required follow-on run); a durable PAT; a GitHub App installed beyond the exact repository or granted more than contents write; treating a workflow filename as a ruleset bypass actor; persisting installation credentials; `workflow_dispatch` plus checkout of an input SHA; external Actions at branches/major tags; branch-selected reusable workflows; moving candidate/release tags; direct non-draft release publication; or post-publication asset replacement.

## 2. npm trusted publication and package smoke

**Question.** How should the exact MCP tarball be tested and published without a long-lived write token?

- **[VERIFIED]** Release automation currently uses Node 20 and stops at `npm pack`; `mcp-server/package.json` lacks the repository metadata required to bind provenance to this GitHub repository.
- **[CITED]** npm trusted publishing accepts GitHub-hosted Actions through OIDC, requires `id-token: write`, binds the exact repository/workflow/environment, can allow direct `npm publish`, and generates provenance for eligible public packages: [trusted publishers](https://docs.npmjs.com/trusted-publishers/) and [npm provenance](https://docs.npmjs.com/generating-provenance-statements/).
- **[CITED]** Staged publishing can prove OIDC before v1, but npm documents no guaranteed stage retention/expiry schema; v1 correctness must not depend on a pending stage: [staged publishing](https://docs.npmjs.com/staged-publishing/) and [`npm stage` CLI](https://docs.npmjs.com/cli/v11/commands/npm-stage/).
- **[CITED]** Scoped packages default to restricted visibility, so bootstrap and the explicit v1 command use `--access public`: [scoped public packages](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/).
- **Recommendation [ASSUMED].** Bootstrap the absent package at pre-v1 with a temporary credential, verify it publicly, revoke the credential, then bind a protected reviewer-gated secret-free `npm-publish` environment to the exact v1 workflow with direct-publish OIDC. A pre-v1 staged publish/2FA approval may prove stage-only configuration, but it is outside the v1 chain. Build/attest/clean-install/protocol-smoke one v1 tarball and rehearse that retained tarball while public 1.0.0 is absent. After final-tag completion, an exact-ID job uploads npm-publish prepared, runs `npm publish <retained-tarball> --provenance --access public`, reads back exact integrity/provenance, and writes completed. Prepared-only recovery accepts exact public identity or retries the same exact tarball only from confirmed absence under the v1 lock. No long-lived token, repack, stage lifetime, or human v1 package command exists.
- **Rejected.** `npm whoami`/dry-run as OIDC proof; a post-bootstrap token; v1 staged approval or unknown stage lifetime; publication before rehearsal/final tag; source-directory publish; repack; ref/name/listing discovery; or bytes differing from the candidate root.

## 3. GHCR tags and attestations

**Question.** How can consumers distinguish immutable releases from mutable development images while the exact attested candidate survives archive transport, runtime smoke, and later GHCR publication?

- **[VERIFIED]** Docker automation currently emits branch, full/minor/major SemVer, SHA, and `latest` tags across four image topologies, with no attestations.
- **[CITED]** Docker's OCI exporter writes an OCI image-layout tarball; BuildKit attestations are manifests attached to the image index, and all image exporters support them. The default Docker local image store does not preserve attestations, so `load: true`/the Docker exporter must not be the release transport: [OCI exporter](https://docs.docker.com/build/exporters/oci-docker/), [attestation storage](https://docs.docker.com/build/metadata/attestations/#storage), and [GitHub Actions attestation limitation](https://docs.docker.com/build/ci/github-actions/attestations/).
- **[CITED]** Skopeo copies between OCI archives, OCI layouts, containers-storage, and registries. `--all` copies every manifest in an index; `--preserve-digests` fails rather than rewriting a digest; `--digestfile` records the destination digest: [`skopeo copy`](https://github.com/containers/skopeo/blob/main/docs/skopeo-copy.1.md) and [Skopeo transports](https://github.com/containers/skopeo#usage).
- **Recommendation [ASSUMED].** Build only Linux/amd64 with a pinned Buildx/BuildKit and `--output type=oci,dest=jit-v1.0.0.oci.tar,name=ghcr.io/<owner>/<repo>:1.0.0 --provenance=mode=max --sbom=true`. Hash the tar for workflow-artifact transport. Parse its raw OCI index and compute: `D_index`, the top-level digest covering the runnable and attestation descriptors; and `D_run`, the Linux/amd64 runnable-manifest digest referenced by both in-toto subjects. Assert one runnable descriptor plus max-provenance and SPDX-SBOM attestation descriptors whose subjects equal `D_run`. For smoke, copy only the selected Linux/amd64 image with pinned Skopeo using `--preserve-digests` into rootless Podman containers-storage, require the copied digest to equal `D_run`, and run it; the source archive remains byte-identical and retains attestations. Test the full round trip against a disposable OCI Distribution registry using `skopeo copy --all --preserve-digests`, then require the registry tag's raw digest and child descriptor set to equal `D_index` and the archive set. Final GHCR publication uses that same command/contract. A release gets only `:1.0.0`; main may get `:main` and `:sha-<commit>`.
- **Rejected.** Docker `load: true` or a Docker archive (drops or cannot represent the attested index); rebuilding after smoke (changes identity); copy without `--all` (drops attestation manifests); copy without `--preserve-digests` (permits representation changes); and `latest`, `1`, or `1.0` OCI release aliases (movable).

## 4. Server termination and container PID 1

**Question.** Can the consolidated image stop cleanly without retaining a shell supervisor or adding an init shim?

- **[VERIFIED]** `jit-server` currently awaits `axum::serve(listener, app)` directly and installs no Ctrl-C or SIGTERM shutdown future (`crates/server/src/main.rs:135`).
- **[VERIFIED]** `/api/search` searches from `Path::new(".")`, and the built web client calls that route for issue and linked-document results (`crates/server/src/routes.rs:297-299`; `web/src/api/client.ts:41-49`). A container may therefore have a healthy `/repo/.jit` data connection while silently searching the image filesystem if its working directory is not the mounted repository.
- **[CITED]** A process running as container PID 1 ignores signals with a default disposition unless it explicitly handles them, so an exec-form PID-1 server cannot assume ordinary SIGTERM termination behavior: [Docker container run reference](https://docs.docker.com/engine/containers/run/#foreground-and-background).
- **[CITED]** Axum exposes `Serve::with_graceful_shutdown` to stop accepting new connections when a supplied future completes, while Tokio exposes portable Ctrl-C handling and Unix signal streams such as `SignalKind::terminate`: [Axum graceful shutdown](https://docs.rs/axum/latest/axum/serve/struct.Serve.html#method.with_graceful_shutdown), [Tokio Ctrl-C](https://docs.rs/tokio/latest/tokio/signal/fn.ctrl_c.html), and [Tokio Unix signals](https://docs.rs/tokio/latest/tokio/signal/unix/index.html).
- **Recommendation [ASSUMED].** First add a server-owned shutdown future that propagates signal-registration errors, awaits Ctrl-C everywhere and SIGTERM on Unix, and pass it to `with_graceful_shutdown`. Prove the real Unix process exits successfully within a bounded timeout on SIGTERM, closes its socket, leaves the repository valid, and can be restarted. Only then package the server with `WORKDIR /repo` as exec-form container PID 1 and require both default and host-UID/GID runtime fixtures to find seeded issue and linked-document terms through `/api/search`, then stop with exit 0 before timeout without SIGKILL/137.
- **Rejected.** Relying on PID 1's default SIGTERM disposition; retaining the shell-plus-`tail` supervisor; adding an init shim to mask a missing application lifecycle; or accepting forced-kill exit as a successful smoke.

## 5. Rust stable and MSRV recency

**Question.** Is 1.97 current, and how can the repository prove it is no more than one stable release behind immediately before creating the immutable tag, without a second literal?

- **[VERIFIED]** Workspace `rust-version` is declared once as `1.97`; both Rust packages inherit it, `cargo metadata --no-deps --format-version 1` reports `1.97`, and existing CI already installs/tests that derived value.
- **[CITED]** Rust 1.97.0 became stable on 2026-07-09, so the declaration is current on 2026-07-14: [official Rust release](https://blog.rust-lang.org/releases/latest/).
- **Recommendation [ASSUMED].** Implement one tested command that derives the unique `rust_version` from `cargo metadata`, installs/queries `stable`, and parses `rustc +stable --version`. Require major `1`, declared minor <= stable minor, and `stable_minor - declared_minor <= 1`; patch releases do not consume a stable-release interval. Keep the exact-declared-toolchain build as compatibility proof. After candidate rehearsal, run this command as the protected tag-authorizer's final check; its immediately following command writes the successful machine-readable result into an annotated `v1.0.0` tag at the rehearsed SHA and pushes without force. A failure leaves the tag absent.
- **Rejected.** Hard-coding `1.97` or an expected stable number in workflow YAML, which creates a second version source and goes stale at the next Rust release.

## 6. Production dependency audit semantics

**Question.** Which commands make all current production findings release-blocking?

- **[VERIFIED]** Security automation currently suppresses audit-tool installation failure, marks all audits `continue-on-error`, uses `npm audit --production`, and is absent from pull requests and release dependencies.
- **[CITED]** RustSec directs users to install with `cargo install cargo-audit --locked`, run `cargo audit` at the project top level, and prefer upgrading over ignores: [cargo-audit README](https://github.com/rustsec/rustsec/blob/main/cargo-audit/README.md). The current CLI can deny informational warnings such as unmaintained/unsound/yanked dependencies with `-D warnings`.
- **[CITED]** Modern npm accepts `--omit=dev`, omits that dependency class from the audit payload/report, and exits zero only when no vulnerability at the configured threshold is found: [npm audit v11](https://docs.npmjs.com/cli/v11/commands/npm-audit/).
- **Recommendation [ASSUMED].** Fail hard on installing a pinned/locked cargo-audit and run `cargo audit -D warnings` at the workspace root, with no ignore list. In both `web/` and `mcp-server/`, run `npm audit --omit=dev --audit-level=info` against committed lockfiles. Do not use `continue-on-error`, shell fallbacks, or blanket allowlists; registry/database failures are audit failures. Cargo has no equivalent production-only lockfile view, so its whole-lock audit is intentionally stricter.
- **Rejected.** Advisory-only/default-warning execution, including `continue-on-error`, `|| true`, or blanket ignores; those commands can report a gap while still authorizing release.

## 7. Deterministic source release archive

**Question.** How can the documented source installation use the exact source bytes rehearsed and published rather than a later checkout or an untested generated snapshot?

- **[VERIFIED]** The current source procedure installs from a Git checkout with `cargo install --path crates/jit --locked`, while the release workflow publishes no source distribution whose bytes are installed in acceptance.
- **[CITED]** `git archive` creates an archive from a named tree, honors committed `export-ignore` attributes, and records the commit ID in tar-format archives when given a commit: [git-archive](https://git-scm.com/docs/git-archive) and [gitattributes export-ignore](https://git-scm.com/docs/gitattributes#_export_ignore).
- **Recommendation [ASSUMED].** After every source-changing prerequisite is integrated, freeze one clean commit/tree. With pinned Git/config/locale/umask, run `git archive --format=tar --prefix=just-in-time-1.0.0/ <FREEZE_SHA>` under a committed, documented export-ignore list and compress with deterministic no-timestamp settings. Build twice in isolated directories and require byte equality. Retain the exact archive, SHA-256, file/tree inventory, SPDX JSON and exact-subject GitHub provenance. Extract those bytes without `.git`, run `cargo install --path crates/jit --locked` and the frozen canonical source procedure, then publish that retained archive without regeneration.
- **Rejected.** Rehearsing a checkout but publishing different source bytes; relying on an auto-generated GitHub snapshot as the tested artifact; undocumented file removal; non-normalized compression metadata; or rebuilding the source archive after rehearsal.

## 8. Durable cross-run evidence and publication recovery

**Question.** Where do freeze, candidate, rehearsal, tag, and publication records live, and how does a later workflow authenticate or recover them without accepting an arbitrary ref?

- **[VERIFIED]** The current release workflow uses v4 upload/download steps only inside one run and records neither artifact IDs/digests nor retention/root-manifest/transition state (`.github/workflows/release.yml:63,91,123,141`). There is no repository-local release ledger primitive.
- **[CITED]** `upload-artifact@v4+` artifacts are immutable, names must be unique, overwrite is opt-in deletion/recreation, and successful upload exposes a numeric `artifact-id` plus SHA-256 `artifact-digest`. Artifacts expire, and `retention-days` is bounded by repository/organization policy: [official upload-artifact contract](https://github.com/actions/upload-artifact#outputs), [immutability and unique names](https://github.com/actions/upload-artifact#not-uploading-to-the-same-artifact), and [artifact retention](https://docs.github.com/en/actions/tutorials/store-and-share-data#configuring-a-custom-artifact-retention-period).
- **[CITED]** GitHub's artifact REST API lists by repository or workflow run, gets/downloads by exact numeric ID, reports name/digest/expiry plus producer run/repository/SHA, and requires only `Actions: read` for fine-grained access. Cross-run downloads require a token and run identifier: [Actions artifact REST API](https://docs.github.com/en/rest/actions/artifacts), [cross-run downloads](https://docs.github.com/en/actions/tutorials/store-and-share-data#downloading-artifacts-during-a-workflow-run).
- **[CITED]** GitHub artifact attestations bind a subject to repository, workflow, commit, and event identity and can be verified with GitHub CLI; generation uses `contents: read`, `id-token: write`, and `attestations: write`: [artifact attestation generation and verification](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).
- **Recommendation [ASSUMED] — store and identity.** Pin `upload-artifact@v4+`, download/attest, and verification Actions to reviewed full SHAs. Use GitHub Actions artifacts as the sole mutable-run-independent evidence store with `overwrite: false`, `if-no-files-found: error`, and `retention-days: 90`; repository policy must allow at least 90 days before source freeze. Every artifact name is unique and includes record kind, candidate tag, freeze SHA, trusted producer workflow run ID, run attempt, and—where applicable—channel sequence/phase. Producer archives are uploaded once and their IDs, artifact ZIP digests, subject digests, schemas, workflow paths/SHAs, run IDs/attempts, actor/repository/ref/SHA, and attestation identities are captured by a canonical candidate-root manifest. The assembly job attests that manifest, uploads it once, and exposes its numeric root artifact ID/digest as the only later-run pointer; self-identity comes from the REST record plus attestation, not a recursive field inside the manifest.
- **Recommendation [ASSUMED] — lookup and trust.** Exact boundaries accept: freeze ID for candidate creation; handoff ID from the verified candidate tag for candidate execution; candidate-event-completed ID through same-run outputs into root assembly; root ID for rehearsal; rehearsal-completed ID for final authorization; final-tag-prepared ID for exact-existing-tag recovery; final-tag-completed ID for npm publication; npm-publish-prepared ID for npm recovery; and final-tag-completed plus npm-publish-completed IDs for GHCR/GitHub. Readers download by supplied ID and verify digest/schema/parents/run/repository/workflow/ref/SHA/actor/event/attestations. Listings only check consistency. Alternate reruns are non-authoritative unless a new pre-tag chain explicitly selects their IDs; no name/ref/latest selection is authority.
- **Recommendation [ASSUMED] — freeze/candidate handoff.** Freeze uploads/attests its root; candidate dispatch accepts that ID, uploads handoff/prepared, and creates an annotated App tag embedding handoff ID/digest and freeze-root digest. The push run verifies tag/App/peeled SHA, downloads the embedded ID, reconciles the exact existing tag, uploads its own candidate-event-completed/recovery-completed artifact, and passes that exact ID to validation/producers/root assembly through same-run outputs. It never discovers creator completion by listing. A tag without valid embedded handoff produces nothing.
- **Recommendation [ASSUMED] — append-only transitions.** Each external operation uses unique prepared/completed artifacts; prepared precedes mutation and readback precedes completion. Prepared recovery may record exact remote state or retry confirmed absence only where explicitly safe. Final-tag absence is special: live MSRV/channel facts age, so old preparation closes without mutation and a new run reauthenticates rehearsal, repeats full preflight/MSRV, and uploads a new prepared record. After tag creation, mismatch is a same-version incident, never replacement.
- **Recommendation [ASSUMED] — lifetime and abandonment.** Recovery is supported for 60 days from candidate-root creation under 90-day Actions retention. Before final-tag creation, day 60/evidence loss/abandonment closes the candidate and requires a new freeze. Final-tag **creation** starts irreversible publication even if completion upload crashes; thereafter the version cannot be abandoned/replaced and exact-ID npm/GHCR/GitHub recovery is mandatory. Successful release assets/root/checksums/attestations become the long-term record.
- **Rejected.** Job outputs/caches/comments/commits as ledger, name/latest discovery, unsigned/overwritable artifacts, v1 stage lifetime, reusing stale absent-tag authorization, abandoning/replacing v1.0.0 after tag creation, blind retry, or a new external store.
