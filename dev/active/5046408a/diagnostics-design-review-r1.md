## Always-data-only versus fallback

Recommend the always-data-only route. Config validation computes over declarations, and explicitly supplied root checks are value validation rather than code authority. Conditional fallback would retain two bootstrap routes selected by the error under diagnosis, each needing identical initialization, admission, input precedence and reporting. It does not remove the required projection work for repair and offers no compelling simplification. No further semantic choice beyond accepting the proposed amendment is required by this review.

## Advisory pre-existing issue

`ConfigOps::validate` currently gates `JitConfig::load` on raw `config.toml` existence and converts every load failure into a finding (`commands/config.rs:388–394`). This can skip sibling declarations when config is absent and blur authored errors with storage failures. The proposed full admitted assembly and typed error separation should replace that behavior. Interpret the matrix's “config absent” success row as absent config with otherwise valid declaration sources, not permission to ignore invalid templates/invariants. This observation does not require another owner or a separate workstream.
