## Claim classification

### 1. `run_step` has no step timing; gate history measures only the whole run

**Verdict: valid-and-open.** `run_step` redirects a command into a temporary log and emits only a summarized success/failure line; it does not capture a start time, elapsed time, or duration (`scripts/cargo-ci.sh:220-231`). Its test-result helpers parse counts and failure lines but likewise contain no timing (`scripts/cargo-ci.sh:155-217`). The gate executor does capture an `Instant` around the entire child process and writes `duration_ms` to the result (`crates/jit/src/gate_execution.rs:110-111`, `crates/jit/src/gate_execution.rs:157-188`). Therefore persisted history can answer “how long did cargo-ci take?” but not “which cargo-ci step took the time?”

A useful distinction is already available to preserve: the outer script acquires/re-execs under a file lock before executing the inner steps (`scripts/cargo-ci.sh:64-82`), while the gate timer wraps the whole child (`crates/jit/src/gate_execution.rs:110-157`). Timing inside `run_step` would intentionally exclude lock queueing and expose actual step execution; the existing whole-run duration would retain queue-plus-execution latency.

### 2. The journal rewrites a full pretty JSON document repeatedly and is quadratic in action count

**Verdict: valid-and-open, with a scope correction.** A journal is constructed with the complete action vector (`crates/jit/src/storage/file_transaction.rs:718-817`). Every journal write removes `.next`, serializes the entire value with `serde_json::to_vec_pretty`, stages and fsyncs it, renames it, and syncs the transaction directory (`crates/jit/src/storage/file_transaction.rs:819-828`; `crates/jit/src/storage/transaction_staging.rs:6-15`). The normal existing-root success path writes once initially, once after each action is prepared, once after each action is published, and once for `Committed` (`crates/jit/src/storage/file_transaction.rs:874-915`, `crates/jit/src/storage/file_transaction.rs:962-1084`, `crates/jit/src/storage/file_transaction.rs:1291-1317`). That path is exactly `2N + 2` full journal publications and serializes an `N`-action vector on each, hence O(N²) serialized action bytes.

`2N + 2` is not universal. When the data root is initially absent, a separate data-stage journal is written (`crates/jit/src/storage/file_transaction.rs:931-956`), and staged data actions are skipped by the per-action live-publication loop (`crates/jit/src/storage/file_transaction.rs:1291-1298`). An all-data absent-root success is therefore `N + 3`, not `2N + 2`. Rollback adds another full rewrite after each reversed action plus the terminal `RolledBack` decision (`crates/jit/src/storage/file_transaction.rs:1560-1589`). The optimization should state its target paths rather than encode one count as a universal invariant.

### 3. `RepositoryActionProgress` is persisted but not used by recovery

**Verdict: valid-and-open.** The serialized enum has five states—`Planned`, `Prepared`, `BackupReady`, `Published`, and `Restored`—and every journal action carries one (`crates/jit/src/storage/transaction_journal.rs:142-161`). Exhaustive source search found only the definition, construction, and assignments; there is no branch or read of `action.progress` in production recovery (`crates/jit/src/storage/file_transaction.rs:791`, `crates/jit/src/storage/file_transaction.rs:977-1068`, `crates/jit/src/storage/file_transaction.rs:1308`, `crates/jit/src/storage/file_transaction.rs:1577`). Recovery parses the journal and selects forward cleanup or rollback from the journal-level decision (`crates/jit/src/storage/file_transaction.rs:157-177`, `crates/jit/src/storage/file_transaction.rs:1717-1755`); journal validation checks paths, identities, and action shape, not progress (`crates/jit/src/storage/file_transaction.rs:1761-1840`).

Rollback is identity-driven and idempotent: if the current leaf already matches the expected preimage it removes any redundant backup and returns; otherwise it verifies the known final identity before undoing and finally verifies the restored preimage (`crates/jit/src/storage/file_transaction.rs:1592-1669`). Thus recovery safety does not currently depend on progress. Removing the field is a breaking storage-format cutover, which is acceptable for this greenfield repository and aligns with removing superseded representations (`.jit/invariants.toml:94-96`). It does require updating the architecture document that currently describes action progress as a durable recovery progression (`dev/architecture/repository-state-materialization.md:314-335`).

### 4. File and directory fsyncs occur per action and have batchable redundancy

**Verdict: valid-and-open, but fsyncs are load-bearing and may only be moved behind equivalent barriers.** `stage_bytes` writes and `sync_all`s every staged file (`crates/jit/src/storage/transaction_staging.rs:6-12`). Existing-root preparation repeatedly syncs the same stage directory after action staging and the backup authority after backup work (`crates/jit/src/storage/file_transaction.rs:987-1084`, `crates/jit/src/storage/file_transaction.rs:1238-1245`). Live publication syncs the target parent for individual creates, writes, mode changes, and deletes (`crates/jit/src/storage/file_transaction.rs:1405-1484`); absent-root data staging similarly syncs target parents within the stage (`crates/jit/src/storage/file_transaction.rs:1249-1288`). Root publication syncs the data-root parent (`crates/jit/src/storage/file_transaction.rs:1351-1372`).

The safe primitive is phase batching, not fsync deletion: write/fsync every staged file; sync each distinct mutated stage/backup directory once after the phase; publish one complete `Prepared` journal before the first live mutation; perform live mutations; sync every distinct live parent before publishing `Committed`; then publish one terminal decision. The initial journal remains necessary for discoverable cleanup before preparation, and the complete prepared journal plus file/directory durability remains necessary for identity-driven rollback (`crates/jit/src/storage/file_transaction.rs:874-915`, `crates/jit/src/storage/file_transaction.rs:1560-1669`). Because recovery accepts either a matching expected preimage or a verified final identity, a crash before a batched parent sync can still converge from the prepared journal; because `Committed` makes final targets authoritative, every live parent must be durable before that marker (`crates/jit/src/storage/file_transaction.rs:1592-1669`, `crates/jit/src/storage/file_transaction.rs:1717-1755`).

## Primitive verification and required crash boundaries

The minimal verified transaction primitive is:

1. Publish an initial discoverable journal before staging (`crates/jit/src/storage/file_transaction.rs:874-876`).
2. Stage all payloads/backups, fsync file contents, and sync each mutated staging/backup directory before declaring preparation complete (`crates/jit/src/storage/transaction_staging.rs:6-15`; `crates/jit/src/storage/file_transaction.rs:962-1088`).
3. Publish one complete prepared journal containing every action’s expected preimage and final identity before the first live mutation (`crates/jit/src/storage/file_transaction.rs:718-817`, `crates/jit/src/storage/file_transaction.rs:962-1084`).
4. Apply all live mutations, verifying root bindings/target identities at the existing failure/race boundaries, then sync every distinct live parent (`crates/jit/src/storage/file_transaction.rs:1291-1484`).
5. Publish exactly one `Committed` decision only after all live target durability barriers have passed (`crates/jit/src/storage/file_transaction.rs:914-915`).
6. On any pre-commit recovery, use expected/final identities to roll back idempotently; on committed recovery, finalize/clean forward (`crates/jit/src/storage/file_transaction.rs:1560-1669`, `crates/jit/src/storage/file_transaction.rs:1717-1755`).

No recovery decision depends on action progress (`crates/jit/src/storage/file_transaction.rs:1717-1840`). Therefore the per-action `Prepared`/`BackupReady`/`Published`/`Restored` rewrites are not required by the current algorithm, including `RepositoryBeforePublishedJournal`; the complete prepared record already describes both endpoints. Crash tests must remain at all 36 typed boundaries, particularly before/after prepared publication, target mutation, parent sync, root publication, commit decision, reverse action, rollback decision, and cleanup (`crates/jit/src/storage/transaction_recovery.rs:15-62`). Atomic rename/no-replace publication and fsync are load-bearing, not optional performance knobs (`.jit/invariants.toml:42-44`).

One design choice needs to be explicit: either retain the terminal `RolledBack` publication as a durable cleanup marker or prove that prepared-state idempotent rollback plus residue cleanup makes it redundant. Current code writes it and recovery recognizes terminal decisions (`crates/jit/src/storage/file_transaction.rs:1584-1589`, `crates/jit/src/storage/file_transaction.rs:1717-1755`). The evidence supports eliminating per-action progress journals; it does not by itself prove terminal rollback-state removal safe.

## Architecture fit

- Journal schema, recovery decisions, batching, and fsync barriers stay inside storage; domain/graph remain pure (`AGENTS.md:25-36`; `.jit/invariants.toml:99-101`).
- Runner selection, reporter parsing, and concise evidence stay in `scripts/cargo-ci.sh`; gate execution continues to persist the generic result shape (`scripts/cargo-ci.sh:4-18`; `crates/jit/src/gate_execution.rs:157-199`).
- `.jit/gates.toml` should need only configuration/input changes, if any; it must not acquire runner implementation logic (`.jit/gates.toml:25-97`).
- Consolidating stale-binary builders should create one shared fixture rather than a third local helper (`.jit/invariants.toml:78-80`, `.jit/invariants.toml:104-106`).
- A duration threshold needs one canonical definition, with volatile history derived rather than copied (`.jit/invariants.toml:67-70`).
- Preserve all semantic assertions and crash/race scenarios; optimization cannot weaken tests into literal inventory checks or remove backend conformance (`.jit/invariants.toml:73-80`).
- Nextest provision/version behavior is external to the current repository and must be pinned or verified in CI; workstation installation is not architecture evidence (`AGENTS.md:14-18`).

## Surprises and planning consequences

1. The headline `2N + 2` journal count is exact only for the normal existing-root success path; absent-root data staging has a different count (`crates/jit/src/storage/file_transaction.rs:931-956`, `crates/jit/src/storage/file_transaction.rs:1291-1298`). Acceptance should measure both shapes.
2. The architecture document treats progress as semantically durable even though recovery never reads it (`dev/architecture/repository-state-materialization.md:314-335`; `crates/jit/src/storage/file_transaction.rs:1717-1840`). Code and prose must cut over together.
3. Inner step timing and persisted whole-gate timing answer different questions because the latter includes lock wait (`scripts/cargo-ci.sh:64-82`; `crates/jit/src/gate_execution.rs:110-157`). A 30-second budget is ambiguous until its clock is named.
4. The model-limit fixture stresses directory cardinality/shape in addition to the three stated package limits (`crates/jit/src/test_utils.rs:351-409`). Optimizing only JSON serialization may leave directory durability costs dominant.
5. Six stale-binary tests share a Cargo target directory but still launch six nested Cargo processes from duplicated helpers (`crates/jit/tests/scratch_build/stale_binary_child_process_tests.rs:61-91`; `crates/jit/tests/scratch_build/stale_binary_json_exit_tests.rs:80-110`). Sharing the cache is not the same as sharing the built artifact/process result.
6. Existing gate history has already drifted beyond the issue’s numeric snapshot, which demonstrates why history totals are derived evidence rather than planning constants (`docs/reference/storage-records.md:56-139`; `.jit/invariants.toml:67-70`).
7. The repository already has a clean precedent for an explicit slower ignored subset, but only three provenance tests are excluded from the default run (`scripts/cargo-ci.sh:315-330`; `crates/jit/tests/provenance_contract/version_cli_tests.rs:86-106`; `crates/jit/tests/provenance_contract/build_provenance_metadata_stability_tests.rs:78-79`).

## Recommended decomposition constraints

The implementation graph should keep two independent branches until integration: (1) transaction primitive/schema/documentation/crash-conformance work and (2) runner provision/reporting/doctest/stale-fixture/budget work. The journal branch should first add behavior-preserving tests for the one-prepared/one-commit primitive and batched durability boundaries, then remove progress and redundant publications. The runner branch should first pin/provision nextest and capture its reporter contract, then adapt summaries, retain doctests and ignored provenance, consolidate nested-build fixtures, and finally introduce a clock-specific duration budget. Both branches meet only at the full cargo-ci gate and evidence review; neither requires a cross-layer product API.
