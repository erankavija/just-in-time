## Traps — do not repeat these

- **Gate a freshly merged worktree twice and read only the second.** The first run after absorbing a large merge reads ~15 s high and fails the 30 s budget. Observed independently on both worktrees: `cf42d08b` cold 37,761 ms → warm 22,218 ms; `f2389b18` cold failed → warm 22,128 ms. The discriminator is `suite-build`: 36,966 ms cold against 353 ms warm. It keeps compilation outside the clock by design but cannot pre-warm the page cache for artifacts written seconds earlier, so the test step pays first-touch I/O inside the clock. **A suite-duration failure of this shape names a cold worktree, not the change.** Check `uptime` and whether anything else was compiling before diagnosing.
- **Suite wall-clock is a critical path, not a sum. Do not add a test's isolated cost to a baseline.** `cf42d08b`'s three new tests measure 4.56 s in isolation and `f2389b18`'s seven measure 0.643 s; predicted impact by addition ~5.2 s, measured impact ~0.2 s (22,095 → 22,314 ms at 4,497 tests). `cargo nextest` runs process-per-test across 24 workers, so an expensive test lengthens wall-clock only if it lands last. The additive model would impose a false constraint on every remaining wave and lead to shrinking tests to buy margin that is never consumed.
- **Never `git diff main..HEAD` on a worker branch to judge its work.** A branch anchored N commits back reports everything main gained as a deletion. This session's first read of `f2389b18` showed it deleting another epic's benchmark files, progress file, and `scripts/cargo-ci.sh` — none of which it touched. Use `git diff $(git merge-base HEAD main)..HEAD`. Reacting to the first reading would have meant accusing a worker of destroying another epic's work.
- **Merge worker branches into one another and gate the combination BEFORE main takes any of it.** Two green gates plus a clean merge does not mean the result compiles: each gate is honest about a tree that no longer exists. This session's combination failed with `error[E0560]: struct CaptureBudget has no field named max_paths` at two sites `f2389b18` added in regions `cf42d08b` never touched. Merging both to main separately would have left main broken between the two merges.
- **A worker's silence is not evidence about the work, in either direction.** Both workers went idle without reporting. Reading their branches settled every open review item faster than the three messages sent asking, and every correction had already landed. A report is the worker's account of what it did; the diff is what it did. Read the branch, then decide.
- **`CARGO_INCREMENTAL=0` is required on every cargo invocation, and a non-empty `incremental` directory is a precondition of the worker's own gate.** `scripts/cargo-ci.sh` runs `incremental-preflight` before compiling and fails on a non-empty `target/debug/incremental` under the worktree it runs in — which is where the lead evaluates `cargo-ci`. Frame it to workers as "your issue cannot pass its own gate until this is clear", because "do not dirty the host" loses to time pressure.
- **rust-analyzer writes incremental state into every project it indexes, including worktrees, and it is not the worker's doing.** Four instances run with cwd in the primary checkout and invoke `cargo check --workspace --all-targets --manifest-path <worktree>/Cargo.toml` with `-C incremental=<worktree>/target/debug/incremental`. Two workers were wrongly instructed to fix this before the discriminating check was run: **compare the target set across trees** — three separate trees carrying the identical 14-target set, still being written with no build running, has one explanation. A tree never opened in the editor carries none. **Do not tell a worker to `rm -rf target/debug/incremental`; it repopulates within seconds.** Clear it inside the lock immediately before each gate instead.
- **The `find . -type d -name incremental -not -empty` check is retired.** It now fires permanently in every indexed worktree plus the `worker-625cc07f` fossil, so it has become noise. The check that survives is the cross-tree comparison above, not presence in any one tree.
- **`.agents/skills/jit-execution-lead/scripts/check-leak-into-main.sh` is unsafe over `.jit/`.** It snapshots main's `git status` at dispatch and calls anything new a worker leak, then prints `git restore` for every ` M` and `rm` for every `??`. Following that advice on `.jit/events.jsonl` does not restore state — it drops events that already happened, violating `@/inv/event-log`, and a shortened append-only log is undetectable downstream. Treat the check as **advisory over `.jit/` and authoritative only over source paths**; attribute flagged `.jit/` entries by issue ID before touching anything.
- **`flock -c` needs `-o`.** Without it the lock's file descriptor is inherited by everything the command spawns, including `sccache`, a daemon that outlives the build — so the lock stays held after `flock` exits. Observed: two `flock`s queued behind an idle daemon, zero compiler processes, load 0.30, one worker stalled nine minutes. `-o` (`--close`) closes the descriptor before the command runs while `flock` still holds the lock for its full duration. `-o` prevents future inheritance and **cannot revoke one already held** — clearing a stuck lock needs the daemon stopped, which is only safe once nothing is compiling.
- **The check that matters for a lock is not whether it exists or is held, but whether its holder is doing the work the lock stands for.** `ps -o cmd= -p <pid>` on whatever `fuser` names. It distinguishes a live holder from an orphan and from a daemon squatting on an inherited descriptor.
- **An automated remedy outlives the diagnosis that justified it.** A background watcher armed to clear a stuck lock became a booby trap once the lock was cleared by hand: its trigger condition no longer meant what it meant when written, and it would have killed a live `sccache` mid-build. It fired two seconds after the manual fix and was harmless only by luck. Prefer clearing by hand and staying in the loop.
- **`mcp-ci` is unsatisfiable by construction on any branch that changes the CLI surface.** `mcp-server/test-unit.js:18` runs `execFileSync('jit', ['--schema'])`, resolving `jit` **from PATH**, so the gate validates the *installed* binary's schema against the *branch's* curated tool list. They agree only when the installed binary was built from the branch under test. The failure names `curated-tools.json` and reads as though the worker forgot to regenerate it — the next person regenerates it and watches it fail again. Work around it by prepending the worktree's `target/debug` to PATH, **and record that condition in the gate-evidence commit**: a green `mcp-ci` under a non-default PATH is a different fact from a green `mcp-ci`, and the gate record cannot distinguish them.
- **`jit gate evaluate` memoises a verdict over declared inputs.** A reused verdict has all four of: `duration_ms: 0`, `exit_code: null`, empty stdout, `origin.derivation: "reused"` naming a `source_run`. `target/` is not a declared input, so nothing done to the build tree invalidates a stale verdict — only `--force`. Every environmental failure is therefore sticky, and the more thoroughly the environment is fixed the more convincing the stale failure looks. The inverse error also wastes a cycle: a non-zero `duration_ms` under `--force` is a real run, so do not suspect memoisation there.
- **A criterion can become unsatisfiable without its text changing, because another criterion in the same set moved under it.** Epic `4b7c06d0` failed its container review on a REQ-04 that was correct when written; work done for its REQ-01 deleted a feature whose tests REQ-04 protected, and complying literally would have put the suite back near 193 s. Nothing in either criterion's text revealed it, and only the container reviewer surfaced it — three waves late. **This epic has 14 hard criteria and 5 waves left; REQ-12 is exactly that shape.** Re-read the full criterion set against what has actually landed before each checkpoint, not at it.
- **Tests that assert nothing satisfy an enumerated criterion as convincingly as real ones.** Seven `#[ignore]`d tests in this repository cost 0.3 s because their bodies are commented-out TDD placeholders; one passes `assert_eq!(count, 1, ...)` by counting an `if`. This epic's profile suites were checked and are clean (44 tests/299 assertions and 9/104, no placeholder markers), but REQ-11 is an enumerated list and the same failure mode applies. Require every new test to be **verified to fail** when its behaviour is removed, not inferred to from a green run.
- **Do not let a documentation sweep touch `dev/active/**` or `dev/archive/**`.** Those are dated session records, not stale documentation. A prior session's sweep rewrote seven handoffs and deleted concrete facts; it was reverted in full. This session's Tier 2.5 sweep found two `max_paths` hits in `dev/archive/` and correctly left them.
