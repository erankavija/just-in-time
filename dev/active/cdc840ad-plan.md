## 2. Technical soundness and architectural fit

- **Neutral declaration authority:** Create crate-root `declarations` as the pure owner of `GateRegistry`, renamed `GateDefinition`, `RuleSet`, `Rule`, their assertion/checker value types, and authored-registry parsing/preservation structures. Move `GateRegistry` out of storage (`crates/jit/src/storage/mod.rs:85-91`), `Gate` definition semantics out of the broad domain wire bucket, and `RuleSet`/`Rule` out of validation (`crates/jit/src/validation/rules.rs:730-778`) in one consumer-updating change, with no old-name alias or re-export. Commands, profile manifests, gate presets, validation, and storage loaders all import these neutral declarations. Storage reads or persists their declared bytes but does not own the types; validation evaluates them but does not own them.
- **Final neutral state subsystem:** Create crate-root `repository_state`, exported directly from `lib.rs`, and move repository-view plus materialization responsibility out of `validation::repository`. It owns `RepositoryPath`, `RepositoryEntry`, `RepositoryImage`, `RepositorySeed`, `MaterializationIntent`, `TargetClaim`, `RepositoryDelta`, the managed-document engine, default-rule family derivation and generated-fragment serialization, default schema rendering, configured project projection rendering, target composition, and pure derive/compare functions. It imports neutral declarations/config only—never validation, storage, commands, or profile. Validation imports declarations and repository_state; storage captures images and applies deltas; profile parses packages into neutral declarations/claims. Producer composition is a closed, direct pure call graph selected by constrained intent/config, not a provider list, callback registry, or extension seam. The current generic byte-only trait lives at `crates/jit/src/validation/repository.rs:119-298`, while the richer duplicate profile snapshot lives at `crates/jit/src/profile/snapshot.rs:1-100`; the cutover deletes both old definitions/exports rather than re-exporting them.
- **Canonical entry image:** `RepositoryPath` is a validated, normalized, non-empty repository-relative identity with no absolute, parent, platform-prefix, control-character, or alternate-separator form. `RepositoryEntry` records kind and normalized platform mode: regular file with exact bytes; directory with mode/metadata; symlink with link payload and metadata but never followed; or unsupported with stable type metadata/reason. Absence is an explicit expected state, not confused with a directory. Filesystem capture, overlays, profile/package planning, validation, hashing, and in-memory tests all use this one image. The current byte-only `read_file/list_files` abstraction loses directory/mode/symlink distinctions (`crates/jit/src/validation/repository.rs:119-138`), while the profile snapshot already demonstrates why those distinctions matter (`crates/jit/src/profile/snapshot.rs:9-42`).
- **Two-phase bounded capture:** A canonical mutation session captures state in two phases without releasing its guard. Phase one reads fixed declaration roots (`index.json`, config, rules, gates, templates, invariants, profile provenance, exact `events.jsonl` bytes, and the command/profile typed seed) plus exact command-selected issue/gate-run records. Parsing those declarations yields a sorted, bounded `CaptureSpec`: exact files and complete directory listings for `.jit/issues`, referenced gate-run/profile/schema directories, every configured registry/item source, every projection source/target outside `.jit`, profile asset/region targets and parents, and every proposed target preimage. The complete `.jit/issues` listing enqueues every ordinary issue entry needed by whole-repository validation; other complete declared listings likewise enqueue each relevant child rather than recording names without contents. Phase two executes a no-follow work queue to a fixpoint: newly parsed repository-relative declarations may enqueue exact paths or complete listings, but only beneath declared safe paths; a visited set plus explicit path/count/byte/depth budgets returns a typed closure-limit error. It never recursively scans the repository root, `target`, `node_modules`, Git metadata, or any unrelated tree. `RepositoryImage` records exact entry bytes/kind/mode/identity and, for each complete listing, the sorted child-name/kind/identity fingerprint and completeness marker. A pure producer requesting a path absent from `CaptureSpec` fails with `UndiscoveredRepositoryPath`; it cannot perform I/O or silently treat the path as absent. This replaces profile’s selected-path snapshot (`crates/jit/src/storage/json.rs:283-311`) and validation’s independently recursive file listing (`crates/jit/src/validation/repository.rs:193-225`) with one closed image.
- **Document and planning closure:** After issue/config/template parsing, capture enqueues every unpinned `Issue.documents[].path`, the document’s validation-read asset references, their parent entry preimages, and every plan-document path derived for planning nodes from the configured template/documentation root (including a plan path not yet linked into `Issue.documents`). Unpinned documents/assets are ordinary working-tree entries and participate in exact/listing revalidation. Pinned references never enqueue or borrow the same working-tree path. Missing any unpinned document/asset or derived planning path from the closed spec is an `UndiscoveredRepositoryPath` defect, not a graceful absence. Current document inventory walks issue references separately (`crates/jit/src/domain/artifact_inventory.rs:161-265`), and document asset rescan mutates stored asset references (`crates/jit/src/commands/document.rs:689-723`); both consume the canonical closure after cutover.
- **Pinned document evidence:** The capture boundary resolves each pinned document and pinned validation-read asset into typed `PinnedDocumentEvidence`, never through pure Git I/O. Available evidence carries requested revision/path, canonical commit OID, object/tree identity, blob OID, existence, exact bytes, byte size, and SHA-256; unavailable evidence carries the requested identity and a stable Git-unavailable/not-found/read-failed reason. The pure planner reads only this evidence, never equates a pinned blob with the working-tree entry of the same path, and never falls back to that entry. Git remains optional: unavailable evidence reproduces the current typed pinned-read diagnostic rather than making core capture require Git. Evidence requests may expand to pinned asset requests during the same bounded fixpoint; every request/result identity and content hash enters `CaptureSpec` and the plan hash. The existing pinned boundary explicitly forbids working-tree fallback (`crates/jit/src/domain/artifact_inventory.rs:29-67`, `crates/jit/src/domain/artifact_inventory.rs:205-265`).
- **Capture coherence and revalidation:** The canonical plan hash covers normalized `CaptureSpec`, every file/symlink/directory identity, every complete-listing fingerprint, the typed seed, and the exact delta. Immediately before journal preparation, `RepositoryStateStore` revalidates the entire read set while the mutation session remains held; a non-cooperating writer that adds/removes/renames a directory child or changes any discovered source/target yields a typed retryable capture conflict before a durable journal. If a declaration edit changes the closure, the operation discards the image and repeats both phases under the same session until one unchanged bounded fixpoint is planned; it never incrementally grafts an unvalidated path into an old plan. Fresh init uses an absent `.jit` declaration image plus exact existing external profile/projection targets and their parent listings under bootstrap-only serialization. Tests cover configured external sources, declarations that expand/change the closure, symlinked parents, concurrent added/removed entries, unrelated large trees, and absent-root profile init.
- **One-way state pipeline:** `repository_state::derive_materializations(image, declarations, seed, intent)` directly invokes the fixed materialization functions and returns sorted expected claims plus a deterministic exact delta; `repository_state::compare_materializations(image, expected)` returns typed drift; validation then evaluates an overlay of that delta. Derivation/comparison never call validation, and validation owns no alternate default/schema/projection/marker renderer. Semantic-mutation intent always invokes the complete producer set; callers cannot select default schemas but omit rule membership or projections. Render-only and repair intents remain constrained complete operations, not arbitrary producer switches.
- **Exact delta vocabulary:** Every action carries a `RepositoryPath`, producer/ownership identity, normalized expected preimage, and final identity. Actions are `CreateDirectory`, `WriteFile`, `SetMode`, and `DeleteFile`; unchanged targets are report metadata, not storage actions. Expected preimages distinguish absent, file hash/size/mode, directory/mode, symlink payload/mode, and unsupported kind. Planning rejects unsafe symlink/unsupported mutations before publication. Hashing and equality normalize mode exactly once in `repository_state`, so the planner, JSON kernel, journal, and in-memory backend cannot disagree about the precondition.
- **Final storage capability:** Add a separate `RepositoryStateStore` trait used explicitly by affected generic `CommandExecutor<S>` methods alongside `IssueStore`. It has one associated opaque mutation-session type and only the capabilities needed here: acquire the canonical session, capture a `RepositoryImage` through it, and apply one finalized `RepositoryDelta` through it. It exposes no per-file write or command-semantic method. `JsonFileStorage` implements capture and delta application via capability-confined filesystem reads and `FileTransactionKernel`; `InMemoryStorage` implements them by locking one aggregate in-memory repository state, cloning it, applying/validating the whole delta with deterministic failure seams, and swapping the clone only on success. The current in-memory backend splits issues, gates, events, and repository files across independent mutexes (`crates/jit/src/storage/memory.rs:18-52`); affected state moves behind the aggregate clone/swap boundary so its tests prove the same all-or-nothing command contract. No wrapper forwards to old `save_gate_registry` or `write_repo_file` methods.
- **Canonical mutation guards:** For JSON storage, session acquisition takes the repository-sibling bootstrap lock first and determines root presence while that guard is held. If `.jit` is absent, the session retains bootstrap as both repository and event-append serialization authority, plans from an absent image, and publishes through `ExternalBootstrap`; it never creates/acquires `.jit/.repo-write.lock` or an events lock inside the absent root. If `.jit` exists, the session owns locks in the single order bootstrap → repository → events for its full capture/plan/revalidate/publish lifetime and uses `InternalRepository`. Existing recovery already distinguishes external from internal control (`crates/jit/src/storage/file_transaction.rs:51-57`) and conditionally acquires the repository guard only when the root exists (`crates/jit/src/storage/recovery_coordinator.rs:63-102`); current profile code separately acquires the events lock for complete log replacement (`crates/jit/src/storage/json.rs:267-276`). That policy moves into the one session so ordinary appenders cannot race exact event-log publication.
- **Typed mutation identity and time authority:** `repository_state` is the sole typed-to-byte finalizer for issue upserts/deletes, neutral registry declarations, profile provenance, gate-run/audit artifacts, and events. Commands submit timestamp-free and identifier-free semantic intents. A `MutationContext` containing injected `IdAuthority` and `MutationClock` is created exactly once after canonical session acquisition and is reused unchanged when capture closure expansion or conflict recovery rebuilds the operation. Production samples its UUID/random source once into the context and deterministically derives all operation identifiers; memory and tests inject a deterministic seed. Allocation order is frozen: new issue identifiers first in canonical request order, so their expected-absent `.jit/issues/<id>.json` paths enter `CaptureSpec` before closure capture; transaction-visible gate-run/profile/other record identifiers next in `(target, key)` order; event identifiers last, after canonical event ordering. Every allocated identity and the context seed identity enter the semantic plan hash. No retry or backend may resample them.
- **Exact lifecycle timestamp semantics:** For a non-noop mutation the context samples one `MutationTimestamp`, once, and the finalizer uses it only for transitions that occur: creation sets `created_at` and `updated_at`, and also `first_ready_at` when the new issue is initially Ready; later semantic issue changes set `updated_at`; the first transition to Ready sets `first_ready_at`; claim and completion transitions set `claimed_at` and `done_at`; and a created or changed `GateState` sets its `updated_at`. Existing lifecycle values are preserved when their transition does not occur. Every committed audit event uses the mutation timestamp. External checker `started_at`/`completed_at` remain captured checker evidence, lifecycle migration reconstructs historical lifecycle fields only from captured history rather than the current clock, and storage journal timestamps remain machine-local recovery metadata excluded from semantic plans and deltas. No-op operations sample neither IDs nor mutation time and emit no bytes. Delete ID/time-generating `Issue::new`, `Issue::new_with_labels`, and production `Event::new_*` seed use; commands construct semantic intents and tests use explicit deterministic fixture builders, with no compatibility constructors or aliases.
- **Canonical audit append:** The finalizer takes the exact captured `events.jsonl` prefix, owns malformed/torn-tail detection, preserves every prefix byte, adds exactly one newline separator only when a non-empty prefix lacks one, orders semantic event intents by `(mutation phase, event tag, primary identity, secondary identity, command-local ordinal)`, assigns their IDs last through `IdAuthority`, serializes canonically, and appends each with one trailing newline. The finalizer—not init/profile command code—sets `ProfileApplied.isolated_torn_tail` from its inspection of that exact prefix. The exact preimage/final bytes, listing identity, event identities, and torn-tail evidence enter the same plan hash, delta, and transaction as issue/registry/gate-run/provenance changes, preserving `@/inv/event-log`. Delete init’s torn-tail/event-construction helper, `append_profile_event_image` (`crates/jit/src/profile/application.rs:190-214`), and every command-local event JSON/image helper; there is no alternate append path for repository-owned events.
- **Recoverable `DeleteFile`:** Extend `TransactionAction`, `JournalActionKind`, plan normalization, hashing, preparation, publication, rollback, and recovery; the current action/journal enums have only directory, write, and mode variants (`crates/jit/src/storage/transaction_action.rs:7-31`, `crates/jit/src/storage/transaction_action.rs:63-84`). Preparation verifies the normalized expected regular-file identity, creates and synchronizes the rollback backup, and durably records original and final-absent identities before publication. Publication rechecks the preimage, moves/removes the target without following links, synchronizes the parent, and marks action progress. Rollback restores the verified backup with no-replace safety and synchronizes it. Prepared-journal recovery converges to the original file; committed-journal recovery verifies absence and completes cleanup. Tests cover absent/wrong-kind/hash/mode races plus every prepare, backup-sync, publish, parent-sync, rollback, recovery, committed-cleanup, and injected interruption boundary. Delete never targets a directory and is emitted only from explicit generator ownership.
- **Recoverable terminology:** `FileTransactionKernel` already normalizes plans before mutation and preserves a durable recovery authority when rollback cannot be proven (`crates/jit/src/storage/file_transaction.rs:84-176`). Actions publish sequentially and roll back in reverse (`crates/jit/src/storage/file_transaction.rs:492-593`), so documentation and results say “recoverable transaction” and “converges to a complete old/new state,” never filesystem-wide instantaneous atomicity.
- **Managed-document composition:** `repository_state` is the sole owner of a byte-oriented target-claim engine; it does not call back into profile or validation. Replace `profile::render::render_managed_region` and `validation::projection::splice_region` (`crates/jit/src/profile/render.rs:131-181`, `crates/jit/src/validation/projection.rs:279-328`) and remove profile’s special nested-region preservation helper (`crates/jit/src/profile/dogfood.rs:120-185`). Collect all claims before rendering; allow at most one base claim; build a containment tree; apply outer regions before claimed descendants and disjoint siblings deterministically; and reject an outer replacement that removes or duplicates a claimed child. Placement remains canonical claim metadata. The intentionally nested dogfood-guidance/invariants regions remain valid (`profiles/jit-dogfood/assets/live/regions/agents-jit-guidance.md:1-5`, `profiles/jit-dogfood/manifest.toml:575-579`, `AGENTS.md:187-211`).
- **Canonical profile consumers:** `profile::package` retains immutable manifest/source validation but exports semantic contributions as `declarations` edits and assets/regions as `repository_state::TargetClaim` values using canonical `RepositoryPath`, entry mode, and bytes. `profile::drift` and its filesystem traversal disappear; profile drift is `repository_state::compare_materializations` over the storage-captured image. `profile::dogfood` retains the embedded package loader and package-authored declaration queries, but `jit_dogfood_gate` returns `declarations::GateDefinition`, built-in preset derivation reads those declarations directly, and live dogfood assets/regions flow through the same target claims—`jit_dogfood_live_projection` and `preserve_nested_region` disappear. `profile::application` retains public provenance and response envelopes, but `ProfileTargetChange` adapts path/action/executable metadata from `RepositoryDelta`; it imports no profile mode or final-byte type. `profile::preset` no longer owns `PresetProjection`, asset modes, or an independent compatibility inventory: package gates/assets are queried from the canonical declarations/claims. `commands::{profile,init}` use `RepositoryStateStore` capture/derive/apply only. These dispositions cover the current consumers at `crates/jit/src/profile/mod.rs:19-47`, `crates/jit/src/profile/drift.rs:1-71`, `crates/jit/src/profile/dogfood.rs:1-155`, and `crates/jit/src/profile/application.rs:118-150`.
- **Complete typed-mutation cutover and explicit dispositions:** Audit the exhaustive top-level mutating-command classifier (`crates/jit/src/cli.rs:2856-3053`) and migrate every path that publishes repository-owned issues, declaration registries, events, profile provenance, gate-run/audit artifacts, or repository-contained exports to one typed mutation and one `RepositoryStateStore` publication. This includes fresh/re-init and profiles; repository config and project render; issue create/batch/bulk/update/delete/archive and every lifecycle transition; dependency changes; issue gate add/remove/pass/fail/reset/evaluate and gate-run recording; gate definition add/define/update/remove and preset create/apply; template/apply/breakdown fan-out; claim/release; document link/unlink and validation asset rescan; lifecycle migration; and validation fixes. Init also claims the semantic `.gitattributes` line set in that same delta, producing deterministic ordering while preserving unrelated lines; the separate setup writer is deleted. Artifact/document moves participating in the same semantic operation enter the delta. Current gate paths split registry/issue/event writes (`crates/jit/src/commands/gate.rs:232-352`, `crates/jit/src/commands/gate.rs:653-677`, `crates/jit/src/commands/gate.rs:966-1103`); all such producers migrate together.

## Decisions

- **D1 — v1.0 freeze scope:** chosen **complete consolidation before source freeze: shared state derivation, profile and ordinary config adoption, transactional project render, gate-registry consumers, validation repair, and managed-region cleanup**. Rejected: defer one consumer family (ships competing publication), reopen completed core maintenance (wrong container boundary).
- **D2 — final module ownership:** chosen **crate-root `declarations` for GateRegistry/GateDefinition and RuleSet/Rule, plus crate-root `repository_state` for canonical images and all materialization producers, with declarations/config → repository_state → validation and storage only at capture/publication boundaries**. Rejected: `validation::materialization` or validation-owned rule producers (consumer owns state), storage-owned declarations/serialization (persistence owns semantics), profile projections (package-specific duplicate), re-export/provider/callback bridges (compatibility seams).
- **D3 — canonical image:** chosen **one safe path and rich entry image carrying file bytes/kind/mode plus directory, symlink, unsupported, and absence semantics**. Rejected: retain byte-only generic view plus richer profile snapshot (duplicate truth), follow symlinks (escape/race risk), infer kind during publication (planner/kernel disagreement).
- **D4 — storage capability:** chosen **one `RepositoryStateStore` capture/session/apply contract implemented natively by JSON and memory**. Rejected: file-only command specialization (breaks generic testability), wrappers over old publishers (parallel paths), make pure planning depend on `IssueStore` (storage vocabulary inward).
- **D5 — guard policy:** chosen **bootstrap-only event/repository serialization for absent `.jit`; bootstrap → repository → events for existing roots; in-memory aggregate mutation session**. Rejected: require `RepoWriteLock`/events lock for fresh init (creates state inside absent root), acquire events before repository (deadlock order), plan outside then publish later (stale basis), rely only on CLI recovery session (breaks direct callers).
- **D6 — deletion protocol:** chosen **journaled `DeleteFile` with normalized expected regular-file preimage, synchronized backup, no-follow publication, no-replace rollback, and prepared/committed recovery**. Rejected: unjournaled remove (data loss), encode deletion as empty write (wrong semantics), filename-only ownership (unsafe), directory deletion in this scope (unneeded destructive expansion).
- **D7 — semantic authority and repair:** chosen **declared config/registries and applied provenance decide expected state; the ownership matrix limits repair and preserves authored rule content unconditionally**. Rejected: persisted derived bytes as authority (SSOT violation), whole-file rules serialization (authored-content loss), best-effort guessing (unsafe), new ownership compatibility inventory (second truth).
- **D8 — managed regions:** chosen **one strict byte containment engine with explicit placement policies and valid distinct nesting**. Rejected: fixed-order string splices (ambiguous), reject all overlap (breaks live nesting), retain policy-specific parsers (duplicate mechanics).
- **D9 — profile lifecycle:** chosen **neutral current-application provenance only; removal remains beyond v1.1**. Rejected: add removal now (scope expansion), introduce removal-oriented compatibility records (temporary design), omit provenance needed to prove current ownership (unsafe repair).
- **D10 — direct cutover:** chosen **one indivisible green implementation change for declarations, closed capture/image, profile claims/markers, delta/storage, typed audit, every repository-owned mutation consumer, and all predecessor deletion**. Rejected: marker-first/view-first/storage-first landings (parallel architecture), adapters, aliases, wrappers, provider callbacks, dual writes, fallback engines, command-by-command migration, temporary inventories, or later cleanup issues.
- **D11 — transaction guarantee:** chosen **recoverable rollback/journal convergence to a complete old/new state with planner-expected preimages**. Rejected: filesystem-wide instantaneous atomicity claim (not provided), independent atomic writes (split coupled state), unchecked publication preimage (manual-write race).
- **D12 — public contracts:** chosen **one internal delta with command-specific public envelopes**. Rejected: generic public transaction envelope (loses intent/breaks users), separate internal target vocabularies (duplicates correctness), expose bytes/journals (storage leak).
- **D13 — coverage authority:** chosen **only leaf tasks carry `satisfies:` credit and each parent criterion has exactly one accountable leaf in a transitively reduced graph**. Rejected: story credit (grouping masquerades as implementation), duplicate criterion owners (ambiguous accountability), redundant dependency edges (DAG/prose divergence).
- **D14 — capture closure:** chosen **guarded two-phase fixed-root/typed-seed discovery into a bounded CaptureSpec, followed by a no-follow declared-path fixpoint covering every unpinned issue document/validation asset/derived planning-node plan path, separate boundary-acquired pinned evidence, complete listing fingerprints, undiscovered-read rejection, plan-hash inclusion, and full pre-journal revalidation**. Rejected: whole-repository recursion (unbounded large-tree cost), caller-picked partial snapshots (missing source), ambient lazy reads or pure Git I/O (impure/racy), pinned-to-working-tree fallback (identity corruption), target-only preimages (miss directory-entry races), graft a changed closure into an old image (mixed snapshot).
- **D15 — typed state and audit:** chosen **repository_state owns one session-scoped MutationContext with deterministic IdAuthority allocation, exact lifecycle timestamp policy, canonical typed serializers for affected issues/declarations/provenance/gate runs/events, and exact-prefix torn-tail finalization; every repository-owned producer publishes through RepositoryStateStore**. Rejected: resampling IDs on rebuild (unstable paths/hash), storage-side issue stamping (backend divergence), current-time migration history (destroys evidence), command-local JSON/event bytes or compatibility constructors (duplicate serialization), independent append_event/save_issue/save_gate_run calls (split state), normalizing an existing event prefix (history mutation).
- **D16 — implementation granularity:** chosen **two leaf tasks only: one indivisible architecture/cutover task for REQ-01..05/09, then one assurance task for REQ-06..08**. Rejected: separate marker/view/delta/audit/migration leaves (temporary competing paths), separate docs/test cleanup leaves (allows incomplete freeze evidence), redundant dependency edges.
- **D17 — command dispositions:** chosen **init’s semantic `.gitattributes` claim, lifecycle/document migrations, archive/presets, and every repository-contained graph/snapshot export join the same captured recoverable delta; stdout and explicitly external destinations remain outside repository publication; machine-local journals/leases/server state and user-global config are formal exclusions**. Rejected: a second `.gitattributes` writer (split authority), raw repository export overwrite (transaction bypass), treating external output as repository state (scope confusion), or compatibility wrappers around deleted IssueStore publishers.
- **Assumptions:** none are load-bearing. The plan fixes the final modules, document and pinned-evidence capture closure/read set, deterministic identity and exact timestamp/event policy, image, storage trait, guard chain, deletion protocol, export/init/mutator dispositions, ownership boundaries, cutover inventory, public contract policy, and criterion accountability. No decision remains open.
