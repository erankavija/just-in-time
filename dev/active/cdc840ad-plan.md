## 2. Technical soundness and architectural fit

- **Neutral declaration authority:** Create crate-root `declarations` as the pure owner of `GateRegistry`, renamed `GateDefinition`, `RuleSet`, `Rule`, their assertion/checker value types, and authored-registry parsing/preservation structures. Move `GateRegistry` out of storage (`crates/jit/src/storage/mod.rs:85-91`), `Gate` definition semantics out of the broad domain wire bucket, and `RuleSet`/`Rule` out of validation (`crates/jit/src/validation/rules.rs:730-778`) in one consumer-updating change, with no old-name alias or re-export. Commands, profile manifests, gate presets, validation, and storage loaders all import these neutral declarations. Storage reads or persists their declared bytes but does not own the types; validation evaluates them but does not own them. Mutation-path configuration follows the same rule: `declarations` owns the pure configuration parser — a filesystem-free, validation-free function from captured `config.toml` bytes to the typed configuration components (hierarchy, namespaces, item kinds, projections, documentation roots) — and capture, derivation, and validation receive one explicitly passed parse per operation. Validation’s owned ambient fallback load (`crates/jit/src/validation/rules.rs:1229`), every process-cached copy feeding pure derivation, and any validation-resident config parsing are deleted; storage retains only a read-only loader that delegates to the same pure parser for non-mutation query paths.
- **Final neutral state subsystem:** Create crate-root `repository_state`, exported directly from `lib.rs`, and move repository-view plus materialization responsibility out of `validation::repository`. It owns `RepositoryLayout`, `VirtualPath`, `RepositoryEntry`, `RepositoryImage`, `RepositorySeed`, `MaterializationIntent`, `TargetClaim`, `RepositoryDelta`, the managed-document engine, default-rule family derivation and generated-fragment serialization, default schema rendering, configured project projection rendering, target composition, and pure derive/compare functions. It imports neutral declarations/config only—never validation, storage, commands, or profile. Validation imports declarations and repository_state; storage captures images and applies deltas; profile parses packages into neutral declarations/claims. Producer composition is a closed, direct pure call graph selected by constrained intent/config, not a provider list, callback registry, or extension seam. The current generic byte-only trait lives at `crates/jit/src/validation/repository.rs:119-298`, while the richer duplicate profile snapshot lives at `crates/jit/src/profile/snapshot.rs:1-100`; the cutover deletes both old definitions/exports rather than re-exporting them.
- **Final layout, overlap, and virtual-path authority:** `RepositoryLayout` is constructed once from no-follow, lexically normalized worktree and selected data roots (default or arbitrary `JIT_DATA_DIR`) and is passed to every storage/session/kernel boundary. It accepts only disjoint roots or a data root strictly nested beneath the worktree; `data_root == worktree_root` and a data root that contains the worktree fail as typed `OverlappingRepositoryRoots`. Symlinked root components, unresolved lexical escape, and root identities that change during capability acquisition are rejected rather than canonicalized through. `VirtualPath` has only `Worktree(rel)` and `Data(rel)`, where `rel` is `RootRelativePath::{Root, Descendant}`; `Root` represents the selected root itself and descendants are normalized non-empty no-parent/no-prefix/no-control/no-alternate-separator paths. One `RepositoryLayout::classify_and_canonicalize` rule is the only physical/repository-relative conversion: for nested roots, any path beneath the data root maps exclusively to `Data(rel)`; a submitted `Worktree` identity under that subtree is canonicalized before insertion or rejected as `DataRootAlias` at APIs requiring an already-canonical path. Every discovery queue, `CaptureSpec`, claim/target set, delta duplicate check, plan hash, journal action, export classifier, and validation lookup uses the canonical value and verifies that no two virtual paths resolve to one physical identity. Logical `.jit/...` contracts map to `Data(...)`; authored paths outside a nested data subtree map to `Worktree(...)`. The layout reserves the transaction-control namespaces: `Worktree(Descendant(".jit-bootstrap/..."))` and `Data(Descendant("tmp/..."))` are never valid semantic targets, capture entries, claim targets, or projection/export destinations, and a selected data root or configured source/target that lexically enters either reserved namespace is rejected as a typed layout error before capture. No empty-string sentinel, physical `.jit` identity, storage-parent inference, prefix stripping, or `transaction_path` adapter remains.
- **Two-phase bounded capture:** A canonical mutation session captures state in two phases without releasing its guard. Phase one reads fixed `Data(...)` declaration roots (`index.json`, config, rules, gates, templates, invariants, profile provenance, exact `events.jsonl` bytes, and the command/profile typed seed) plus exact command-selected issue/gate-run records. Parsing those declarations yields a sorted, bounded `CaptureSpec`: exact files and complete `Data(...)` listings for issues and referenced gate-run/profile/schema directories; every configured registry/item source and projection source/target as its typed `Data` or `Worktree` path; profile asset/region targets and parents; and every proposed target preimage. The complete `Data(Descendant("issues"))` listing enqueues every ordinary issue entry needed by whole-repository validation; other complete declared listings likewise enqueue each relevant child. Phase two executes a no-follow work queue to a fixpoint under explicit path/count/byte/depth budgets. It never recursively scans either root, build trees, Git metadata, or unrelated paths. `RepositoryImage` records exact entry identity and complete-listing fingerprints keyed by `VirtualPath`. A pure producer requesting an uncaptured path fails with `UndiscoveredRepositoryPath`; it cannot perform I/O or silently treat the path as absent. This replaces profile’s selected-path snapshot (`crates/jit/src/storage/json.rs:283-311`) and validation’s independently recursive file listing (`crates/jit/src/validation/repository.rs:193-225`) with one closed image. When the selected data root is nested inside a recognized Git worktree, the documented linked-worktree resolution fallback (local root, then Git-HEAD, then the main worktree's root — `crates/jit/src/storage/json.rs:462-638`) participates in mutation-time capture as boundary-acquired typed evidence in the pinned-evidence pattern: each fallback index/issue read resolves at the capture boundary into a typed record carrying source class, identity (blob OID for HEAD; no-follow file identity and content hash for the main worktree), and exact bytes or a typed absence; the pure planner reads only that evidence, and every identity enters `CaptureSpec`, the plan hash, and pre-journal revalidation. The HEAD path spelling derives from the layout's worktree-relative data root, never a physical `.jit` literal, and a disjoint data root has no Git-HEAD or main-worktree fallback.
- **Document and planning closure:** After issue/config/template parsing, capture enqueues every unpinned `Issue.documents[].path`, the document’s validation-read asset references, their parent entry preimages, and every plan-document path derived for planning nodes from the configured template/documentation root (including a plan path not yet linked into `Issue.documents`). Unpinned documents/assets are ordinary working-tree entries and participate in exact/listing revalidation. Pinned references never enqueue or borrow the same working-tree path. Missing any unpinned document/asset or derived planning path from the closed spec is an `UndiscoveredRepositoryPath` defect, not a graceful absence. Current document inventory walks issue references separately (`crates/jit/src/domain/artifact_inventory.rs:161-265`), and document asset rescan mutates stored asset references (`crates/jit/src/commands/document.rs:689-723`); both consume the canonical closure after cutover. The command-boundary plan-document resolver likewise stops reading the filesystem on mutation and validation paths: the injected plan-content map (`crates/jit/src/commands/validate.rs:666-693`) is projected from the captured image’s plan-document entries, and its ambient read path is deleted.
- **Pinned document evidence:** The capture boundary resolves each pinned document and pinned validation-read asset into typed `PinnedDocumentEvidence`, never through pure Git I/O. Available evidence carries requested revision/path, canonical commit OID, object/tree identity, blob OID, existence, exact bytes, byte size, and SHA-256; unavailable evidence carries the requested identity and a stable Git-unavailable/not-found/read-failed reason. The pure planner reads only this evidence, never equates a pinned blob with the working-tree entry of the same path, and never falls back to that entry. Git remains optional: unavailable evidence reproduces the current typed pinned-read diagnostic rather than making core capture require Git. Evidence requests may expand to pinned asset requests during the same bounded fixpoint; every request/result identity and content hash enters `CaptureSpec` and the plan hash. The existing pinned boundary explicitly forbids working-tree fallback (`crates/jit/src/domain/artifact_inventory.rs:29-67`, `crates/jit/src/domain/artifact_inventory.rs:205-265`).
- **Capture coherence and revalidation:** The canonical plan hash covers `RepositoryLayout` identity, normalized canonical `CaptureSpec`, the virtual-to-physical uniqueness proof, every entry/listing/pinned-evidence identity, typed seed, and exact delta. Immediately before journal preparation, `RepositoryStateStore` revalidates the entire read set and root identity while the mutation session remains held; content/listing/root/alias change yields a typed retryable conflict before journaling. If declarations change the closure, the operation discards the image and repeats both phases under the same session; it never grafts paths into an old plan. Fresh init uses an absent selected data-root image plus canonical `Worktree` targets under external-bootstrap serialization. Tests cover default nested `.jit`, other nested custom roots, relative and absolute disjoint roots, equal/ancestor overlap rejection, Worktree-under-Data alias attempts across discovery/claims/deltas/validation/exports, symlink/lexical root escape, closure races, and absent-root init/profile/config/recovery.
- **One-way state pipeline:** `repository_state::derive_materializations(image, declarations, seed, intent)` directly invokes the fixed materialization functions and returns sorted expected claims plus a deterministic exact delta; `repository_state::compare_materializations(image, expected)` returns typed drift; validation then evaluates an overlay of that delta. Derivation/comparison never call validation, and validation owns no alternate default/schema/projection/marker renderer. Semantic-mutation intent always invokes the complete producer set; callers cannot select default schemas but omit rule membership or projections. Render-only and repair intents remain constrained complete operations, not arbitrary producer switches.
- **Exact delta and journal vocabulary:** Every action carries a canonical `VirtualPath`, producer/ownership identity, normalized expected preimage, and final identity. Actions are `CreateDirectory`, `WriteFile`, `SetMode`, and `DeleteFile`; unchanged targets are report metadata. Expected preimages distinguish absent, file hash/size/mode, directory/mode, symlink payload/mode, and unsupported kind. Delta normalization rejects duplicate canonical paths and any cross-root pair resolving to one physical identity. Each durable journal action stores canonical root class plus normalized relative path, never an absolute or `.jit`-prefixed surrogate; recovery resolves it through the journal-bound layout identity, rejects layout mismatch/alias, and rechecks physical uniqueness. Planning rejects unsafe symlink/unsupported mutations before publication. Hashing and equality normalize mode and canonical virtual identity once in `repository_state`, so planner, JSON kernel, journal, and memory cannot disagree.
- **Final storage capability and kernel:** Add `RepositoryStateStore::open_mutation_session(layout)` as the only entry to affected storage mutation. The recovered opaque session captures a `RepositoryImage` and applies one finalized `RepositoryDelta`; there is no per-file or command-semantic method. `JsonFileStorage` implements it with root-confined capabilities for both layout roots and a `FileTransactionKernel` constructed from the explicit layout/capability set. Before the selected data root exists, external journals live at repository-root `.jit-bootstrap/transactions`; once it exists, internal journals live at selected `data_root/tmp/transactions`. No other physical `.jit` literal is permitted. `InMemoryStorage` locks one aggregate state, models both virtual roots plus recovery residue/failures, clones/apply-validates/swaps on success, and obeys the same session contract. No wrapper forwards old publishers.
- **Absent data-root publication:** For a selected data root that is absent, fresh publication assembles the complete root in a verified sibling staging directory reached through no-follow capabilities with symlink/unsupported ancestry rejected; all `Data(...)` actions—including `index.json`—target that staging capability while the durable journal remains `Worktree(Descendant(".jit-bootstrap/transactions/..."))`. After all staged content/modes are verified and synchronized, the kernel atomically publishes the staged directory with a no-replace rename, fsyncs the parent, opens the final root no-follow, and verifies its object identity. A lost no-replace rename fails with a typed occupied-destination error and leaves no partial state; a subsequent invocation opens the now-existing root through the ordinary existing-root path. The successful publication rename is the irreversible commit point: recovery never removes or replaces a published root. Prepared-journal recovery removes only a directory still present at the recorded staging path; when the stage is absent it compares the destination's no-follow object identity against the recorded staged-directory identity (preserved by rename) and either completes forward on a match or reports a typed conflict on a mismatch, touching nothing. Other processes therefore see absence or one complete root, never partial content, and a root another worktree has opened is never unpublished. Mixed deltas publish every semantic `Worktree(...)` action as an ordinary recoverable journaled action (verified preimage, synchronized backup) before the data-root rename, and the rename commits the whole operation last: a failed or lost rename rolls the worktree actions back to their verified preimages and removes the stage, converging to the complete old state, while a crash after the rename completes cleanup forward to the complete new state. A worktree preimage conflict therefore surfaces before anything irreversible and aborts as a typed retryable conflict; no ordering exists in which a published root coexists with unappliable worktree actions. Existing-root internal journals remain parameterized at `Data(Descendant("tmp/transactions/..."))`. Failure/concurrency tests cover every stage/write/sync/rename/parent-sync/final-open/identity/recovery boundary, concurrent-creation races, and mixed Worktree-action ordering around the commit point.
- **Mandatory recovered-session boundary:** `open_mutation_session(layout)` acquires repository-root bootstrap serialization, recovers external journals/residue, and—when the selected root exists—acquires data-root repository and event guards, recovers internal journals/residue, and only then permits capture. Claim flows enter already holding coordinator, yielding coordinator → bootstrap → repository → events; the store never acquires coordinator and later-guard holders cannot enter coordination. Recovery/residue/root-alias failure prevents capture. Retained CLI sessions are reentrant only for the same canonical layout; direct executor/checker paths use the same boundary. Memory models the ordered guards, prepared/committed residue, aliases, and failures. Direct tests prove recovery before first read and reverse-order rejection. Current recovery/checker boundaries (`crates/jit/src/storage/recovery_coordinator.rs:59-102`, `crates/jit/src/storage/mod.rs:124-139`) collapse into this contract.
- **Typed mutation identity and time authority:** `repository_state` is the sole typed-to-byte finalizer for issue upserts/deletes, deterministic `index.json` membership (issue creation, deletion, and restore derive exact `all_ids`/`deleted_ids` updates from the captured index preimage inside the same delta, replacing the incidental save-side updater at `crates/jit/src/storage/json.rs:413-421`), neutral registry declarations, profile provenance, gate-run/audit artifacts, and events. Commands submit timestamp-free and identifier-free semantic intents. A `MutationContext` containing injected `IdAuthority` and `MutationClock` is created exactly once after canonical session acquisition and is reused unchanged when capture closure expansion or conflict recovery rebuilds the operation. Production samples its UUID/random source once into the context and deterministically derives all operation identifiers; memory and tests inject a deterministic seed. Allocation order is frozen: new issue identifiers first in canonical request order, so expected-absent `Data(Descendant("issues/<id>.json"))` paths enter `CaptureSpec` before closure capture; transaction-visible gate-run/profile/other record identifiers next in `(target, key)` order; event identifiers last, after canonical event ordering. Every allocated identity and the context seed identity enter the semantic plan hash. No retry or backend may resample them.
- **Exact lifecycle timestamp semantics:** For a non-noop mutation the context samples one `MutationTimestamp`, once, and the finalizer uses it only for transitions that occur: creation sets `created_at` and `updated_at`, and also `first_ready_at` when the new issue is initially Ready; later semantic issue changes set `updated_at`; the first transition to Ready sets `first_ready_at`; claim and completion transitions set `claimed_at` and `done_at`; and a created or changed `GateState` sets its `updated_at`. Existing lifecycle values are preserved when their transition does not occur. Every committed audit event uses the mutation timestamp. External checker `started_at`/`completed_at` remain captured checker evidence, lifecycle migration reconstructs historical lifecycle fields only from captured history rather than the current clock, and storage journal timestamps remain machine-local recovery metadata excluded from semantic plans and deltas. No-op operations sample neither IDs nor mutation time and emit no bytes. Delete ID/time-generating `Issue::new`, `Issue::new_with_labels`, and production `Event::new_*` seed use; commands construct semantic intents and tests use explicit deterministic fixture builders, with no compatibility constructors or aliases.
- **Canonical audit append:** The finalizer takes the exact captured `Data(Descendant("events.jsonl"))` prefix, owns malformed/torn-tail detection, preserves every prefix byte, adds exactly one newline separator only when a non-empty prefix lacks one, orders semantic event intents by `(mutation phase, event tag, primary identity, secondary identity, command-local ordinal)`, assigns their IDs last through `IdAuthority`, serializes canonically, and appends each with one trailing newline. The finalizer—not init/profile command code—sets `ProfileApplied.isolated_torn_tail` from its inspection of that exact prefix. The exact preimage/final bytes, listing identity, event identities, and torn-tail evidence enter the same plan hash, delta, and transaction as issue/registry/gate-run/provenance changes, preserving `@/inv/event-log`. Delete init’s torn-tail/event-construction helper, `append_profile_event_image` (`crates/jit/src/profile/application.rs:190-214`), and every command-local event JSON/image helper; there is no alternate append path for repository-owned events.
- **Recoverable `DeleteFile`:** Extend `TransactionAction`, `JournalActionKind`, plan normalization, hashing, preparation, publication, rollback, and recovery; the current action/journal enums have only directory, write, and mode variants (`crates/jit/src/storage/transaction_action.rs:7-31`, `crates/jit/src/storage/transaction_action.rs:63-84`). Preparation verifies the normalized expected regular-file identity, creates and synchronizes the rollback backup, and durably records original and final-absent identities before publication. Publication rechecks the preimage, moves/removes the target without following links, synchronizes the parent, and marks action progress. Rollback restores the verified backup with no-replace safety and synchronizes it. Prepared-journal recovery converges to the original file; committed-journal recovery verifies absence and completes cleanup. Tests cover absent/wrong-kind/hash/mode races plus every prepare, backup-sync, publish, parent-sync, rollback, recovery, committed-cleanup, and injected interruption boundary. Delete never targets a directory and is emitted only from explicit generator ownership.
- **Recoverable terminology:** `FileTransactionKernel` already normalizes plans before mutation and preserves a durable recovery authority when rollback cannot be proven (`crates/jit/src/storage/file_transaction.rs:84-176`). Actions publish sequentially and roll back in reverse (`crates/jit/src/storage/file_transaction.rs:492-593`), so documentation and results say “recoverable transaction” and “converges to a complete old/new state,” never filesystem-wide instantaneous atomicity.
- **Managed-document composition:** `repository_state` is the sole owner of a byte-oriented target-claim engine; it does not call back into profile or validation. Replace `profile::render::render_managed_region` and `validation::projection::splice_region` (`crates/jit/src/profile/render.rs:131-181`, `crates/jit/src/validation/projection.rs:279-328`) and remove profile’s special nested-region preservation helper (`crates/jit/src/profile/dogfood.rs:120-185`). Placement remains canonical claim metadata. The intentionally nested dogfood-guidance/invariants regions remain valid (`profiles/jit-dogfood/assets/live/regions/agents-jit-guidance.md:1-5`, `profiles/jit-dogfood/manifest.toml:575-579`, `AGENTS.md:187-211`).
- **Canonical profile consumers:** `profile::package` retains immutable manifest/source validation but exports semantic contributions as `declarations` edits and assets/regions as `repository_state::TargetClaim` values using canonical `VirtualPath`, entry mode, and bytes. `profile::drift` and its filesystem traversal disappear; profile drift is `repository_state::compare_materializations` over the layout-keyed captured image. `profile::dogfood` retains the embedded package loader and package-authored declaration queries, but live assets/regions flow through the same claims. `profile::application` retains public provenance/response envelopes adapted from `RepositoryDelta`; it imports no profile mode or final-byte type. `profile::preset` no longer owns projections, asset modes, or an independent compatibility inventory. `commands::{profile,init}` use only the recovered layout-aware state-store session. These dispositions cover current consumers at `crates/jit/src/profile/mod.rs:19-47`, `crates/jit/src/profile/drift.rs:1-71`, `crates/jit/src/profile/dogfood.rs:1-155`, and `crates/jit/src/profile/application.rs:118-150`.

- **Permanent Git-optional attributes contract:** The boundary acquires typed Git evidence before init. The line-set claim is eligible only when Git identifies a containing worktree and the selected data root is inside that same worktree; otherwise status is exactly `not_applicable`, no `Worktree(Descendant(".gitattributes"))` target is captured, and init succeeds. Eligible init claims the canonical Git-escaped worktree-relative selected-data-root path followed by `/events.jsonl merge=union` in the same delta, preserves every unrelated line/byte, and reports exact status `unchanged`, `created`, or `modified` plus the corresponding created/modified path lists. Delete the warning-only post-init `setup_gitattributes` writer (`crates/jit/src/storage/gitattributes.rs:42-79`) and its CLI warning/report merge (`crates/jit/src/main.rs:1938-1947`, `crates/jit/src/main.rs:2009-2017`); Git remains optional for core commands.
- **Git-required claim synchronization:** Lease coordination remains in `.git/jit`, outside the repository transaction, with its existing lease format, credential surface, and command set unchanged. Claim acquire holds coordinator while opening the recovered session and applying the idempotent repository-side issue/event transition (`crates/jit/src/commands/claim.rs:152-153` is the sole production claim-path repository publisher), yielding coordinator → bootstrap → repository → events; lease operations without repository-side effects (release, renew, heartbeat, force-evict) remain coordinator-only; reverse acquisition is rejected. The repository transition is derived from the captured image and is convergent over both the captured issue state and the captured event-log tail: when both already reflect the claim, acquire is a complete no-op; when the current split save-then-append path left the issue assigned but the claim event absent, the retry emits exactly the missing event in the same delta; a duplicate event is never emitted, preserving `@/inv/event-log`. The lease is durably persisted before repository synchronization, and an acquire that finds its own live lease for the same issue, agent, and worktree recognizes a crash-interrupted attempt and re-enters the same coordinator-held synchronization, so a retry converges to lease plus repository state without a second event. Retry recognition operates on canonical identity and durable authority: acquire resolves the issue id to its canonical full id and passes that canonical id to the coordinator — the current path resolves but then hands the unresolved spelling to `acquire_claim_with_reason` (`crates/jit/src/commands/claim.rs:82`, `crates/jit/src/commands/claim.rs:130`), which the cutover corrects — and lease matching canonicalizes the issue identity of persisted lease records during comparison, so an active lease recorded under a short-ID spelling by the current implementation is recognized and never duplicated by a post-cutover full-ID acquire; and under the coordinator lock, acquire reconciles the derived `claims.index.json` against the append-only claims log (the existing derived-view/rebuild relationship, `crates/jit/src/storage/claim_coordinator.rs:9-10`) before lease creation, so a lease durably appended by a crash-interrupted attempt is recognized even when the derived index was never published. Lease credential, claim-log, and claim-command redesign are outside this epic's scope.

## Decisions

- **D1 — v1.0 freeze scope:** chosen **complete consolidation before source freeze: shared state derivation, profile and ordinary config adoption, transactional project render, gate-registry consumers, validation repair, and managed-region cleanup**. Rejected: defer one consumer family (ships competing publication), reopen completed core maintenance (wrong container boundary).
- **D2 — final module ownership:** chosen **crate-root `declarations` for GateRegistry/GateDefinition and RuleSet/Rule, plus crate-root `repository_state` for canonical images and all materialization producers, with declarations/config → repository_state → validation and storage only at capture/publication boundaries**. Rejected: `validation::materialization` or validation-owned rule producers (consumer owns state), storage-owned declarations/serialization (persistence owns semantics), profile projections (package-specific duplicate), re-export/provider/callback bridges (compatibility seams).
- **D3 — canonical layout and image:** chosen **one explicit layout accepting disjoint roots or data strictly nested under worktree, rejecting equal/ancestor/symlink/escape roots, and assigning Data precedence through one canonicalizer with virtual-to-physical injectivity**. Rejected: permit arbitrary overlapping roots (aliases), preserve both Worktree/Data spellings (duplicate truth), silently realpath symlinks (escape/identity race), physical `.jit` identity, parent inference, or path adapters.
- **D4 — storage capability:** chosen **one recovered `RepositoryStateStore::open_mutation_session(layout)` capture/apply contract implemented natively by JSON and memory, with `FileTransactionKernel` accepting the explicit layout/capability set**. Rejected: file-only command specialization (breaks generic testability), capture before recovery (stale state), wrappers over old publishers (parallel paths), or pure planning depending on `IssueStore`.
- **D5 — recovery and global guard policy:** chosen **coordinator → repository bootstrap → repository → events; recovery precedes capture, and claim flows enter with coordinator held**. Rejected: coordinator/repository reverse order, release coordinator mid-attempt, CLI-only recovery, or capture-before-recovery.
- **D6 — deletion protocol:** chosen **journaled `DeleteFile` with normalized expected regular-file preimage, synchronized backup, no-follow publication, no-replace rollback, and prepared/committed recovery**. Rejected: unjournaled remove (data loss), encode deletion as empty write (wrong semantics), filename-only ownership (unsafe), directory deletion in this scope (unneeded destructive expansion).
- **D7 — semantic authority and repair:** chosen **declared config/registries and applied provenance decide expected state; the ownership matrix limits repair and preserves authored rule content unconditionally**.
