## 2. Technical soundness and architectural fit

**Approach.** The epic is one dependency chain rooted at a from-scratch address parser, then two
parallel kind substrates (rule, gate), then link/enforcement wiring and projection, then a repo
migration, with the multi-jit form hanging off the parser independently.

**Reuses / integrates with (verified real):**
- `resolve_item_kinds` / `ItemKind::from_config` (`domain/item.rs`) — domain-agnostic, zero
  kind-name literals; adding `rule`/`gate` is ordinary config once grammar/substrate land
  (investigation §6).
- `resolve_link_label` and the `enforces:`-generalizing validate-time scan (`commands/validate.rs`,
  around `:290-320`) already iterate `item_kinds()…link_namespaces()` generically — REQ-06 needs
  no kind literal, only the parser dependency.
- `storage/ruleset_store.rs` — the atomic-write, "sole source when present" idiom to mirror for a
  new `gates.toml` store; `IssueStore` trait signature is unchanged, only `JsonFileStorage` (and
  the `InMemoryStorage` equivalent) gain the new store (`storage/mod.rs:188,195`).
- `ProjectionMode`/`ProjectionStyle` (`config.rs`), `splice_region` (pure, `projection.rs:223-263`),
  and the `project_invariants` orchestration (`projection.rs:305-344`: render → optional splice →
  atomic `IssueStore::write_repo_file`) — the pattern REQ-07's new renderer follows.

**Layer boundaries respected:** the new address parser (kind-segmented, `@<project>`-aware) lives in
`domain/item.rs` beside `Scope`/`split_qualified_id`, pure and I/O-free per CLAUDE.md; the
kind-aware resolver takes the configured kind list as a parameter, the way `resolve_item_kinds`
receives config, so no kind literal enters engine code and the domain stays I/O-free. The
`gates.toml` store lives behind `IssueStore` exactly as `load_gate_registry` does today
(`storage/json.rs:623-634`). `commands/` orchestrates (issue resolution + item indexing + link
resolution) and does no raw file I/O, as `commands/item.rs` already does. Engine stays
config-driven: `[item_kinds]` carries no domain literals (investigation §6); the fixed default
ruleset in `validation/defaults.rs` is a deliberately hardcoded contract (module docs, MF1), a
separate subsystem from the item-kind engine — REQ-03 must not conflate them.

**Grounding (claim → status, cited):**
- `@` illegal in label values → valid-and-open. `labels.rs:24` value class `[a-zA-Z0-9._/-]` has
  no `@`; `labels.rs` is the sole `validate_label`/`parse_label` source (investigation §1.1).
- `@` already a scope sentinel → already-true-context. `domain/item.rs:62`
  (`PROJECT_SCOPE_SENTINEL`), `:113-119` (`Scope::parse` returns `Project` iff `s == "@"`).
- Qualified-id parser is two-segment, not kind-aware → valid-and-open, larger than it reads.
  `split_qualified_id` (`domain/item.rs:678-680`) splits on the first `/` only; its four callers
  (`commands/item.rs:290-337` `show_item`, `commands/item.rs:402`, `commands/validate.rs:317`,
  `validation/graph.rs:90`) match the second segment by `==` against `AddressableItem.self_id` with
  no kind filter. This is a new resolver, updated in lockstep with all four call sites.
- Colon split unaffected → confirmed. `labels.rs:77` `splitn(2, ':')`; the deeper grammar keeps it.
- `default:` literal dependency is wider than the brief's `defaults.rs` → valid-and-open, broader.
  Builds names at `defaults.rs:104,150,285` (`"default:label-format"`,
  `format!("default:namespace-unique:{name}")`, `format!("<default:{name}>")`); consumed at
  `serialize.rs:561`, `commands/issue.rs:34`, `main.rs:1296`; pinned by contract tests
  `defaults.rs:402-459`. Rule names carry up to three segments (`default:namespace-unique:resolution`
  etc., `.jit/rules.toml:26,32,38`), a dynamically generated open-ended family, so REQ-03's
  origin-extraction handles origin:family:param, not just origin:name.
- Cross-kind collision `bracket:coverage-preview` (rule) vs `coverage-preview` (gate) →
  confirmed data (`.jit/rules.toml:44`, `.jit/gates.json:221-240`). Today's per-scope uniqueness
  (`derive_scope_items`/`DuplicateSelfId`, `domain/item.rs:746-750,777-786`) is enforced across all
  kinds sharing a scope ("kind is not part of the qualified id", comment at `:746`). The kind
  segment resolves the collision only if per-scope uniqueness is rescoped to per-(scope, kind); that
  rescoping is a real decision, not automatic (D2).
- Gates are JSON → valid-and-open. `GATES_FILE = "gates.json"` (`storage/json.rs:21`),
  `write_json`/`read_json` hardcoded to `serde_json` (`storage/json.rs:128-145`),
  `load_gate_registry`/`save_gate_registry` (`storage/json.rs:623-634`). TOML-null gotcha in
  `Gate.reserved: HashMap<String, serde_json::Value>` (`domain/types.rs:760-762`) reproduced
  against `toml 0.8`; all current `reserved` are `{}`, so not a live blocker but a real fragility
  (investigation §1.7, REQ-04). Literal-`gates.json` test/fixture consumers to sweep:
  `tests/init_tests.rs:62`, `gate_update_test.rs:306-310`, `invariant_check_cli_tests.rs:228`,
  `template_apply_tests.rs:823,831`, `commands/snapshot.rs:486-489`; the web-server watcher treats
  `gates.json` as graph-relevant (`crates/server/src/watcher.rs:75` doc comment, `:116` filename
  match, test `test_relevant_gates_json` `:308-310`); stale doc-comments at
  `commands/template.rs:51,276,881`. mcp-server and web/ have zero direct consumers (grepped).
- `enforced-by` surface → confirmed small. Four bindings, three unique targets
  (`.jit/invariants.toml`); `enforced_by: Option<String>` per invariant (`projection.rs:165-169`).
- Toml descriptor has no transform → confirmed. `TomlSourceDescriptor{toml,table,id-field,text-field,
  link-fields}` (`config.rs:589-608`); `id-field`/`text-field` are verbatim string reads
  (`required_toml_str`, `domain/item.rs:1122`). Registry-first kinds bypass `id_pattern` for self-id
  extraction — `load_toml_scope_items`/`project_toml_entry` read the id verbatim via
  `required_toml_str` (`domain/item.rs:1117-1122`); contrast the markdown path `extract_raw_items`,
  which DOES apply `kind.id_pattern.find(text)` (`domain/item.rs:870`). So `id_pattern` is
  coverage-only, not index-time validation — do not assume it validates rule/gate self-ids on
  ingest. A project-scope
  kind must declare a source or `from_config` returns `MissingProjectSource`
  (`domain/item.rs:473-477`).
- REQ-07 renderer premise needs precision → the invariant renderer is `&InvariantRegistry`-typed
  (`projection.rs:143-199`); reuse the mechanism (`splice_region` `:223-263`, `project_invariants`
  `:305-344`, `render_id_anchor` `:184-198`), add a new render function. Do not cite it as calling
  `render_invariants_markdown`.
- REQ-08 live blast radius → confirmed near-zero. `satisfies:` appears 86× in `.jit/issues/*.json`,
  all bare `satisfies:REQ-NN` (zero qualified-form); `per:`/`mitigates:`/`resolves:`/`enforces:`
  appear zero times in live data. CLAUDE.md's projected invariant region uses `id-anchor` style with

  `enforced-by` strings plus doc hygiene.
- `satisfies:`/coverage interaction → confirmed. `label_credits_id` (`validation/graph.rs:73-91`)
  has an unqualified path (`value == id`, what all live labels use, untouched) and a qualified path
  calling the same `split_qualified_id` REQ-01 generalizes; zero qualified `satisfies:` labels exist,
  so it is a forward-looking lockstep update, not a live break.
- Project identity → greenfield. `.jit/index.json` holds only `schema_version`/`all_ids`/
  `deleted_ids`; `JitConfig` (`config.rs:13-43`) has no project section. The only `project_name`
  concept is display-only in `crates/server/src/main.rs:83-90`, not read by `crates/jit`. A concrete

- INV-LABEL-FORMAT dual-source → real REQ-02 risk. The canonical label regex exists twice:
  `labels.rs:24` and `CANONICAL_LABEL_REGEX` (`defaults.rs:55`, a manual-sync comment); the backing

  already declares `link-namespaces = ["enforces"]` (`.jit/config.toml:132`). The namespace-registry

  config, not kind config alone.

## Decisions

Resolves all 12 open points of brief §8. Provisional; premise-shaky ones marked REOPEN.

- **D1 — Value-grammar exact form (point 1):** chosen **extend the value class to admit an optional
  leading `@` followed by an optional project-name and `/`-delimited segments**, keeping `/` (already
  allowed) and the single-colon namespace split unchanged. Concretely the value grammar accepts
  `@`, `@<project-name>`, and `<segment>(/<segment>)*`; the exact regex is finalized in the REQ-02
  item and regenerated into the schema in lockstep. Rejected: widening the value grammar to allow `:`
  in values (parse-safe via `splitn(2,':')` but reads ambiguously and keeps legacy colon ids alive,
  contradicting the colon-reserved decision).

- **D2 — Rule identity refactor + collision (points 2):** chosen **split `origin` and a clean `id`
  into separate fields in `rules.toml`'s schema** (a data migration of the 7 seed rules), and
  **rescope per-scope self-id uniqueness to per-(scope, kind)** so the kind segment disambiguates
  `@/rule/coverage-preview` from `@/gate/coverage-preview`. The `namespace-unique:{param}` family
  becomes a colon-free slug (`namespace-unique-<param>`). No rule rename is needed for correctness
  once the kind segment is address-significant. Rejected: adding a transform capability to
  `TomlSourceDescriptor` (`config.rs:589-608` has none; a schema split is simpler and keeps the
  descriptor a verbatim reader); relying on a flat per-scope id space with prefix stripping (breaks
  on the `coverage-preview` collision, `DuplicateSelfId`).

- **D3 — Sugar + inference (point 3):** chosen **sugar `<short-id>/<self-id>` expands to
  `@/issue/<short-id>/<kind>/<self-id>` with kind inferred by id-pattern for issue-scoped items
  only; project-scoped rule/gate addresses require the explicit kind segment (no sugar)**; ambiguous
  inference is a clear error. Rationale: the four shipped kinds have visually distinct id-patterns
  (`REQ-\d+`, `D-\d+`, `RISK-\d+`, `[A-Z][A-Z0-9]*-\d+`) so issue-scoped inference is unambiguous,
  while rule/gate slugs (`label-format`, `cargo-ci`) carry no distinguishing shape and
  `id_pattern` is not enforced at index time for registry-first kinds
  (`load_toml_scope_items`/`project_toml_entry`, `domain/item.rs:1117-1122`; the markdown extractor
  `extract_raw_items` at `:870` is the path that applies it). Rejected: project-item sugar
  `@/<self-id>` without kind (collision-prone for rule/gate, per investigation §5.3).

- **D4 — `issue` segment status (point 4):** chosen **`issue` is a reserved, built-in first-class
  address segment, not an `[item_kinds]` entry; `@/issue/<short-id>/…` is a prefix for issue-scoped
  items**. A bare `@/issue/<id>` as a standalone resolvable "issue view" is not built this round
  (keeps scope minimal; not required by any REQ). Rejected: declaring `issue` as an item kind
  (issues are a separate storage substrate, `IssueStore`, with no `[item_kinds.issue]` today,
  investigation §5.4).

- **D5 — Project identity (point 5):** chosen **add a canonical `[project] name` field to
  `config.toml`, seeded by `jit init` (default: slugified directory basename), validated as
  `[a-z][a-z0-9-]*` on write**. Bare `@` is the local shorthand; `@<name>` where `name` equals the
  declared project resolves locally; any other `@<other>` is parse-valid and returns a
  not-resolvable error. Rejected: putting the name in `index.json` (machine metadata:
  `schema_version`/`all_ids`/`deleted_ids` only, not human-editable); reusing the server's
  display-only `project_name` (`crates/server/src/main.rs:83-90`, not read by `crates/jit`, not
  persisted). This is engineered, not deferred — greenfield per investigation §5.5.

- **D6 — Gate substrate migration (point 6):** chosen **migrate `gates.json` → `gates.toml` with a
  dedicated store mirroring `storage/ruleset_store.rs`, and declare `gate` as a registry-first kind
  over it (id-field = key, text-field = description)**; the typed `Gate`/`GateChecker` load path and
  the item-projection path both read `gates.toml`. Guard `Gate.reserved` against JSON null on TOML
  serialization. Rejected: adding a JSON source descriptor to the item-kind engine (would fork the
  descriptor away from its toml-only design, `config.rs:589-608`, and keep gates on JSON contrary to
  the no-legacy decision).

- **D7 — `enforced-by` mechanics (point 7):** chosen **`enforced-by` stays a typed single-string
  binding in `invariants.toml`, rebound to the new `@/rule/…`/`@/gate/…` addresses; it is not
  additionally surfaced as an `enforces:` item link**. The authoring path `enforces:@/…` (REQ-06) is
  the separate, work-item-side link. Rejected: double-wiring `enforced-by` as both a typed binding
  and an `enforces:` label (redundant; `enforced_by` is `Option<String>`, consumed by validation
  only, `projection.rs:165-169`).

- **D8 — Reference projection (point 8):** chosen **a new `render_rules_gates_markdown` function
  following the projection pattern, rendered into a config-declared target region using the existing
  `ProjectionStyle` field**; default target a dedicated reference doc region. Rejected: calling the
  existing `render_invariants_markdown` (it is `&InvariantRegistry`-typed, not generic,
  `projection.rs:143-199`).

- **D9 — Re-addressing migration approach (point 9):** chosen **manual migration**: the live blast
  radius is the four `enforced-by` strings (handled by the rebind item); doc updates are a hygiene
  sweep; acceptance is green `jit validate` plus a tree-wide legacy-address grep. Rejected: a
  migration script (over-engineered for four live strings; investigation §REQ-08 confirms
  `satisfies:REQ-NN` bare labels and all other link namespaces need no data migration).

- **D10 — `satisfies:`/coverage interaction (point 10):** chosen **confirm `satisfies:REQ-NN` is
  unaffected**; its bare-form path in `label_credits_id` (`validation/graph.rs:73-91`) is untouched,
  and its qualified path shares `split_qualified_id`, updated in lockstep by the REQ-01 item. No
  coverage-id remapping. Rejected: remapping coverage ids under the address scheme (they are
  container-criterion credits, not qualified-id links; zero qualified `satisfies:` labels exist).

- **D11 — Backward-compat window (point 11):** **clean cut, no shim** — settled by container REQ-08
  ("no legacy-form addresses remain"). The legacy-form set is exactly (a) the old kindless project
  form `@/<self-id>` (e.g. `@/INV-01`) and (b) colon-prefixed rule ids. `<short-id>/<self-id>`
  (e.g. `56ab0224/REQ-01`) is NOT legacy: container REQ-01 mandates it remains valid sugar for the
  canonical issue form. No dual-form/legacy-resolution scaffolding exists to preserve
  (investigation §5.11). Rejected: a compatibility window resolving old kindless `@/INV-*` forms
  during migration (contradicts REQ-08; no existing shim to build on).

- **D12 — Scope of one effort (point 12):** **one epic** — settled by the container's existence and
  its "this epic states the end-state requirements." The code dependency order (parser core →
  rule/gate kinds → enforcement/projection/migration; multi-jit off the parser) matches the §3
  grouping. Rejected: splitting into a milestone of several epics (unnecessary; the waves are
  internal groups, each independently landable).

- **Assumptions:** the rules/gates reference doc's exact target file/heading (D8) has no existing
  convention beyond CLAUDE.md's invariant region; it is config-declared so the target can be chosen
  at the REQ-07 item without reopening the plan. Risk if wrong: cosmetic, contained to that item.
