## 2. Technical soundness and architectural fit

- **Approach:** Keep release work at dependency, workflow, packaging, and documentation boundaries. The four product surfaces are already concrete workspace/package outputs (`Cargo.toml:1-8`, `crates/jit/Cargo.toml:14-16`, `crates/server/Cargo.toml:13-19`, `web/package.json:1-12`, `mcp-server/package.json:1-12`), so the plan adds no engine-level release or Docker concepts. This follows charter D-9's capability-preservation boundary (`dev/vision/9db27a3a-charter.md:151-162`) and the investigation's already-done/valid-and-open classification (`dev/active/8b05a612-investigation.md:9-21`).
- **Reuses / integrates with:** The exact-MSRV CI job already reads workspace `rust-version` and builds that compiler (`.github/workflows/ci.yml:82-134`); the new recency gate derives from the same manifest instead of adding another version literal. Rust 1.97 is the current researched baseline, and the stable-minor comparison algorithm is specified at `dev/active/8b05a612-research.md:34-41`.
- **Reuses / integrates with:** `jit-server` validates an existing data directory, watches it, and derives the project name from its parent (`crates/server/src/main.rs:61-90`). It already nests API routes under `/api` and serves either `--web-dir` assets or embedded assets (`crates/server/src/main.rs:104-129`); the health route is consequently `/api/health` (`crates/server/src/routes.rs:33-36,66-73`). The image therefore binds the repository at `/repo`, passes `/repo/.jit`, and uses that one server rather than introducing a proxy or storage adapter.
- **Grounding (from investigation):** Embedded web is **valid but build-order-sensitive**: `crates/server/build.rs:4-18` creates an empty `web/dist` stub if the web build has not run. Native packaging, Docker, and the clean-room rehearsal build web first and test both `/` SPA fallback and `/api/health` (`dev/active/8b05a612-investigation.md:20,47-50`).
- **Grounding (from investigation):** Security enforcement is **valid-and-open**: tool installation is currently suppressed and all three audits are advisory (`.github/workflows/security-audit.yml:37-57`), CI describes security as separate/manual (`.github/workflows/ci.yml:314-316`), and release does not depend on it (`.github/workflows/release.yml:128-132`). The reusable workflow uses the fail-closed commands justified at `dev/active/8b05a612-research.md:43-51` only after separate lock-domain remediation has made each boundary green.
- **Grounding (from investigation):** Release identity and publication are **valid-and-open**: current component versions disagree and every `v*` tag is accepted (`crates/jit/Cargo.toml:1-5`, `crates/server/Cargo.toml:1-5`, `mcp-server/package.json:1-4`, `web/package.json:1-5`, `.github/workflows/release.yml:3-7`). The existing workflow packages but does not install-smoke, publish npm, include license texts/SBOM, or prove normal/security suites (`.github/workflows/release.yml:12-179`). Reusable same-SHA dependencies, SPDX artifacts, and attestation follow the researched job graph and artifact contract (`dev/active/8b05a612-research.md:6-14`).
- **Grounding (from investigation):** npm trusted publication is **valid-and-open**, and the package channel does not yet exist. The current job stops at `npm pack` (`.github/workflows/release.yml:68-94`). Before version alignment, an owner-authorized bootstrap leaf publishes the exact smoked current pre-v1 tarball with a one-time scoped credential, configures the trusted publisher, then revokes the credential. The v1 candidate is subsequently packed and smoked without publication; only final acceptance runs `npm publish "$TARBALL"` through OIDC with no `NODE_AUTH_TOKEN` (`dev/active/8b05a612-research.md:16-23`).
- **Grounding (from investigation):** Docker consolidation is **valid-and-open**. The current runtime installs nginx and Node, copies unused MCP, runs as root, uses `/data`, and launches background processes followed by `tail` (`Dockerfile:39-88`, `docker/entrypoint.sh:4-19`); Compose exposes three services on a detached named volume (`docker-compose.yml:3-62`). The exhaustive active consumer roster is fixed at `dev/active/8b05a612-investigation.md:23-31`, and no removal lands before those consumers are migrated.
- **Grounding (from investigation):** Docker publication is **valid-and-open**. The current workflow skips pull requests, builds four image shapes, and publishes movable aliases with no runtime smoke (`.github/workflows/docker.yml:3-15,30-41,68-91,93-150`). The selected contract publishes only the consolidated image: PR smoke without push; `main` plus SHA development tags; and an exact attested OCI release archive copied to GHCR only by final acceptance. The release digest is authoritative; before assigning `:1.0.0`, the publisher rejects an existing tag with a different digest and treats the same digest as an idempotent resume (`dev/active/8b05a612-research.md:25-32`).
- **Grounding (from investigation):** Documentation deduplication is **valid-and-open**. Install, Docker, source, and MCP procedures overlap across `README.md:38-58`, `INSTALL.md:15-254`, `docs/how-to/deployment.md:1-186`, and `mcp-server/README.md:21-75`. ## 4. Risks and actionability

| Risk / open question | Severity | Mitigation or decision |
|---|---|---|
| A dependency has no advisory-free compatible version. | Critical | The owning lock-domain remediation removes or replaces the dependency path, migrates all affected consumers in the same change, and proves the complete component suite. Carrying or blanket-ignoring the advisory is not an option. |
| Blocking audits are enabled while the repository is still red. | High | All three remediation leaves precede the reusable enforcement leaf through explicit graph edges, so the first enforcement commit is green. |
| Rust, web, MCP, Docker, and GitHub publication race or validate different commits/artifacts. | Critical | Candidate assembly calls reusable jobs on the tagged SHA and records immutable artifact identities without publication. Only final acceptance may publish v1; it preflights all three channels, uses the same archive checksum, npm integrity, and OCI digest, and accepts only byte-identical resumptions. |
| npm package ownership or trusted publishing is not configured. | High | The bootstrap leaf uses an owner-authorized, narrowly scoped temporary credential to publish the exact smoked pre-v1 tarball, configures the exact repository/workflow/environment binding, proves OIDC, and revokes the credential before version alignment. v1 remains OIDC-only. |
| The server binary is built with the empty embedded-web stub. | High | Native and Docker producers build `web/dist` first and fail unless `/` plus SPA fallback serve real assets; final acceptance repeats that proof from published artifacts. |
| Docker consolidation loses repository-relative documents, persistence, or signal handling. | Critical | Runtime smoke exercises an initialized whole-repository `/repo` mount, linked document endpoints, host-visible `.jit` mutation, numeric non-root identity, PID 1, and bounded termination before any image is pushed. |
| Removing old Docker files leaves a script, fixture, example, or live guide on the old contract. | High | The removal leaf owns the exhaustive active consumer list and a tree-wide negative search, updates active docs in the same change, and explicitly excludes only historical archive evidence and unrelated storage-test strings. |
| Documentation pruning removes discovery along with repetition. | High | Canonical pages land before entry-point pruning; every removed walkthrough retains a context-bearing link, and navigation/link/support-matrix checks plus adversarial review are acceptance criteria. |
| Core-maintenance or profiles work changes a release-consumed contract late. | High | The final acceptance leaf directly depends on both external epics, verifies their delivered public behavior, and contains no implementation criteria for their internal scope. Independent readiness leaves can rebase without duplicating that work. |
| An action claims production readiness without network-verifying audits or public channels. | Critical | Security remediation begins with unrestricted fresh probes; final publication verifies registry/GitHub/GHCR metadata and records public URLs, integrity, digest, and audit output. Sandbox-only evidence cannot close those criteria. |
| Release workflow permissions become broader than required. | High | Each reusable producer receives only its necessary scoped permissions: contents/attestations/id-token for native provenance, id-token for npm OIDC, and packages for GHCR. Pull-request jobs have no write path, proven by workflow tests. |

Every load-bearing question is resolved or assigned to an item's observable criteria. Each leaf has a bounded file/consumer surface, independent green landing point, explicit dependency edges, and component-appropriate verification; no worker must choose a release topology, advisory policy, tag scheme, or documentation owner.

## Decisions

- **D1 — Capability boundary:** chosen **preserve the native CLI, Rust server/API, built web UI, and MCP server while cutting only redundant packaging, deployment, aliases already scheduled elsewhere, and repeated prose**. Rejected: broad feature cuts (would violate the v1 capability contract), retaining every delivery shape (multiplies support/security cost without a distinct outcome).
- **D2 — Advisory remediation shape:** chosen **three independent Rust, web, and MCP remediation leaves followed by one reusable blocking workflow**. Rejected: one cross-ecosystem dependency mega-change (unbounded regression attribution), enabling blocking automation before cleanup (lands the repository red), blanket ignores (contradicts zero-known-advisory policy).
- **D3 — Workflow reuse and same-SHA gating:** chosen **callable normal CI and security workflows assemble immutable same-SHA candidates without publication; one final leaf publishes v1 only after canonical docs and both external epics complete**. Rejected: copying suites into release YAML (drift), trusting branch protection or a previous main run (may validate a different commit), allowing component producers to publish independently (irreversible partial releases).
- **D4 — Version and MSRV authority:** chosen **derive product versions from manifests, accept only exact v1.0.0, derive MSRV from cargo metadata, and compare it with live stable using a one-minor window**. Rejected: workflow literals for product/MSRV/stable versions (duplicate and stale), unpinned stable-only builds (do not prove the declared minimum), conflating product and repository-format versions (different contracts).
- **D5 — Native artifact contract:** chosen **one Linux x86_64 musl archive containing jit and jit-server, both license texts, SHA-256 checksums, one SPDX JSON SBOM, extracted-binary smoke, and GitHub provenance/SBOM attestations**. Rejected: the current un-smoked binary/web archives (not an install proof), publishing a standalone web archive (the supported server already serves the built UI).
- **D6 — MCP bootstrap and publication:** chosen **owner-authorized one-time publication of the exact smoked existing pre-v1 tarball with a temporary scoped credential, followed by trusted-publisher setup and credential revocation; then pack/smoke v1 once and let only final acceptance publish that exact path through OIDC**. Rejected: pretending OIDC can create an absent package (unsupported bootstrap), retaining a long-lived npm token (unnecessary secret), publishing the source directory (can repack different bytes), treating `npm pack` as publication (no public channel).
- **D7 — Docker identity, ownership, and tags:** chosen **one exec-form jit-server image with numeric 10001:10001 default and explicit host-owner UID:GID override, one-service Compose, PR runtime smoke, `main`/SHA development tags, and an exact attested OCI release archive whose digest is authoritative; final acceptance refuses to move an existing full-version tag to another digest**. Rejected: split API/web/CLI or multi-process all-in-one images (redundant/incorrect supervision), root runtime or implicit host permissions (unsafe/unreliable writes), named `/data` volume (loses repository context), treating `latest`/major/minor/full-version tags themselves as immutable identities (tags are movable).
- **D8 — Documentation ownership:** chosen **one canonical home per install, deployment, MCP, release, compatibility, and MSRV fact with concise linked entry points**. Rejected: synchronizing repeated walkthroughs (known drift), deleting entry-point context (hurts discoverability), rewriting archive evidence (destroys historical record).
- **D9 — External dependency re-home (binding D-14):** chosen **remove the implementation-consumed broad `8b05a612 -> 6eb585bc` edge from the planning/container spine and attach both `6eb585bc` and profiles MVP `9b7b5f9c` directly to the final “Publish and run clean-room v1.0 release acceptance” child at breakdown**. Rejected: leaving core maintenance on planning/container scope (blocks independent planning/work and overstates ownership), omitting profiles from final acceptance (cannot prove the documented quickstart), duplicating either epic's implementation in readiness (parallel conflict and split authority). The broad edge removal is recorded by commit `b6d52011`; breakdown completes the re-home with both child edges.
- **D10 — Final publication and acceptance authority:** chosen **candidate producers never publish v1; after canonical docs and both external epics complete, one final fresh-checkout workflow preflights all identities, publishes exact candidate bytes once, accepts only byte-identical resumptions, and verifies every public channel and instruction**. Rejected: build-only release confidence (does not prove install/start/persistence), source-checkout-only smoke (can depend on unshipped assets), independent component publication (can strand immutable npm versions), or trusting a mutable OCI tag instead of the recorded digest.
- **Assumptions** (where intent stayed underspecified): the supported native binary target for v1.0 is Linux x86_64 musl, matching the current release scope — expanding operating-system/architecture coverage would require an owner criterion change; GitHub Release, npm package `@erankavija/jit-mcp-server`, and GHCR are the authorized public channels named by the current manifests/workflows and research — unavailable account-side configuration fails publication rather than selecting a substitute channel; external epics may evolve internally, but the final leaf consumes only their public delivered contracts and waits on their terminal states.
