## 2. Technical soundness and architectural fit

- **Approach:** Keep release work at dependency, workflow, packaging, and documentation boundaries. The four product surfaces are already concrete workspace/package outputs (`Cargo.toml:1-8`, `crates/jit/Cargo.toml:14-16`, `crates/server/Cargo.toml:13-19`, `web/package.json:1-12`, `mcp-server/package.json:1-12`), so the plan adds no engine-level release or Docker concepts. This follows charter D-9's capability-preservation boundary (`dev/vision/9db27a3a-charter.md:151-162`) and the investigation's already-done/valid-and-open classification (`dev/active/8b05a612-investigation.md:9-21`).
- **Reuses / integrates with:** The exact-MSRV CI job already reads workspace `rust-version` and builds that compiler (`.github/workflows/ci.yml:82-134`); the recency command derives from the same manifest instead of adding another version literal. Rust 1.97 is the current researched baseline, and the stable-minor comparison/pre-tag handoff is specified at `dev/active/8b05a612-research.md:36-43`. Candidate assembly and rehearsal identify a 40-hex SHA before any release tag exists; the protected tag-authorizer reruns the command as its final check and creates one annotated, non-force `v1.0.0` tag at that exact SHA as its immediately following command.
- **Reuses / integrates with:** `jit-server` validates an existing data directory, watches it, and derives the project name from its parent (`crates/server/src/main.rs:61-90`). It already nests API routes under `/api` and serves either `--web-dir` assets or embedded assets (`crates/server/src/main.rs:104-129`); the health route is consequently `/api/health` (`crates/server/src/routes.rs:33-36,66-73`). The image therefore binds the repository at `/repo`, passes `/repo/.jit`, and uses that one server rather than introducing a proxy or storage adapter.
- **Grounding (from investigation):** Embedded web is **valid but build-order-sensitive**: `crates/server/build.rs:4-18` creates an empty `web/dist` stub if the web build has not run. Native packaging, Docker, and the clean-room rehearsal build web first and test both `/` SPA fallback and `/api/health` (`dev/active/8b05a612-investigation.md:20,47-50`).
- **Grounding (from investigation):** Security enforcement is **valid-and-open**: tool installation is currently suppressed and all three audits are advisory (`.github/workflows/security-audit.yml:37-57`), CI describes security as separate/manual (`.github/workflows/ci.yml:314-316`), and release does not depend on it (`.github/workflows/release.yml:128-132`). The reusable workflow uses the fail-closed commands justified at `dev/active/8b05a612-research.md:45-53` only after separate lock-domain remediation has made each boundary green.
- **Grounding (from investigation):** Release identity and publication are **valid-and-open**: current component versions disagree and every `v*` tag is accepted (`crates/jit/Cargo.toml:1-5`, `crates/server/Cargo.toml:1-5`, `mcp-server/package.json:1-4`, `web/package.json:1-5`, `.github/workflows/release.yml:3-7`). The existing workflow packages but does not install-smoke, publish npm, include license texts/SBOM, or prove normal/security suites (`.github/workflows/release.yml:12-179`). Reusable exact-SHA dependencies, pre-tag authorization, SPDX artifacts, and attestation follow the researched job graph and artifact contract (`dev/active/8b05a612-research.md:6-14`).
- **Grounding (from investigation):** GitHub invocation identity is **valid-and-open**: a manually supplied checkout SHA can differ from `github.sha`, while reusable workflows, OIDC claims, and attestations continue to identify the caller event and workflow commit. The candidate path therefore begins with a protected, non-movable candidate-tag push; accepts no checkout-ref input; invokes same-repository workflows by local path; and verifies the event/ref/SHA, caller and called-workflow SHAs, repository IDs, OIDC claims, and exact attestation subjects before each producer or staging command (`dev/active/8b05a612-research.md:11-15`).
- **Grounding (from investigation):** npm trusted publication is **valid-and-open**, and the package channel does not yet exist. The current job stops at `npm pack` (`.github/workflows/release.yml:68-94`). Before version alignment, an owner-authorized bootstrap leaf publishes the exact smoked current pre-v1 tarball with a one-time scoped credential, configures a stage-only trusted publisher, disallows token publication, and revokes the credential. A GitHub-hosted Node 22.14+/npm 11.15+ producer then proves OIDC by running the only supported non-public verification primitive, `npm stage publish "$TARBALL"`; an owner reviews/downloads that stage, and only the final publication leaf may run `npm stage approve <stage-id>` with 2FA. `npm whoami` or a dry run is explicitly not an OIDC proof because OIDC is exchanged only for publish/stage-publish operations.
- **Grounding (from investigation):** Docker consolidation is **valid-and-open**. The current runtime installs nginx and Node, copies unused MCP, runs as root, uses `/data`, and launches background processes followed by `tail` (`Dockerfile:39-88`, `docker/entrypoint.sh:4-19`); Compose exposes three services on a detached named volume (`docker-compose.yml:3-62`). The exhaustive active consumer roster is fixed at `dev/active/8b05a612-investigation.md:23-31`, and no removal lands before those consumers are migrated.
- **Grounding (from investigation):** Server termination is **valid-and-open** and precedes Docker packaging. The current `axum::serve(listener, app).await` has no shutdown future (`crates/server/src/main.rs:135`), while an exec-form server becomes container PID 1 and cannot rely on the default SIGTERM disposition. A focused server leaf installs Tokio Ctrl-C/Unix SIGTERM handling, wires Axum graceful shutdown, and proves bounded successful process exit before the Docker leaf consumes that behavior (`dev/active/8b05a612-research.md:38-46`).
- **Grounding (from investigation):** Docker publication is **valid-and-open**. The current workflow skips pull requests, builds four image shapes, and publishes movable aliases with no runtime smoke (`.github/workflows/docker.yml:3-15,30-41,68-91,93-150`). The selected release transport is an OCI-layout tar produced by the Buildx `oci` exporter with attached max-provenance and SBOM manifests. `skopeo inspect --raw` plus `skopeo manifest-digest` records the top-level attested index `D_index` and its Linux/amd64 runnable manifest `D_run`; `skopeo copy --preserve-digests` copies only `D_run` to Podman's containers-storage for smoke without changing the source archive; final publication uses `skopeo copy --all --preserve-digests oci-archive:... docker://ghcr.io/...:1.0.0` and requires the resulting digest to remain `D_index`. The archive SHA-256 detects transport corruption, `D_run` is the attestation/runtime subject, and `D_index` is the GHCR release identity (`dev/active/8b05a612-research.md:26-34`).
- **Grounding (from investigation):** Documentation deduplication is **valid-and-open**. Install, Docker, source, and MCP procedures overlap across `README.md:38-58`, `INSTALL.md:15-254`, `docs/how-to/deployment.md:1-186`, and `mcp-server/README.md:21-75`. The active-consumer sweep at `dev/active/8b05a612-investigation.md:29-39` defines the blast radius; archive/session evidence remains unchanged, and all live entry points retain navigation to canonical pages under `@/inv/single-source-prose`.
- **Architecture boundary:** Dependency updates may require local API migrations, but those migrations stay with the affected Rust, web, or MCP consumer in the same remediation item. Packaging code does not enter `crates/jit/src/domain/`, graph, or storage. The one focused product-code prerequisite is server-process lifecycle at the existing `axum::serve` boundary; Docker consumes it without adding a supervisor or changing API/storage behavior. Release workflows derive versions from manifests and bind them to immutable GitHub invocation identity; documentation cites those maintained sources. The pre-publication rehearsal verifies, but never edits, contracts owned by external epics `6eb585bc` and `9b7b5f9c`.

## 4. Risks and actionability

| Risk / open question | Severity | Mitigation or decision |
|---|---|---|
| A dependency has no advisory-free compatible version. | Critical | The owning lock-domain remediation removes or replaces the dependency path, migrates all affected consumers in the same change, and proves the complete component suite. Carrying or blanket-ignoring the advisory is not an option. |
| Blocking audits are enabled while the repository is still red. | High | All three remediation leaves precede the reusable enforcement leaf through explicit graph edges, so the first enforcement commit is green. |
| Rust, web, MCP, Docker, and GitHub publication race or validate different commits/artifacts. | Critical | A protected non-movable candidate-tag push makes `github.sha` authoritative; all local reusable workflows verify event/ref, checkout, caller/called-workflow SHAs, repository IDs, OIDC claims, and exact attestation/provenance subjects before acceptance. npm staging proves OIDC without public visibility, rehearsal accepts the exact bytes, and publication permits only byte-identical resumptions. |
| A checkout override or reusable-workflow revision makes source bytes differ from GitHub/OIDC/attestation identity. | Critical | Candidate workflows accept no source-ref input and run only from the immutable candidate-tag event. Mismatch fixtures cover dispatch/branch invocation, tag movement, checkout override, caller/called path or SHA differences, claim differences, and foreign artifact/npm provenance; pre-action mismatches stop build/stage and post-action mismatches stop acceptance. |
| The stable-recency check fails only after v1.0.0 already exists. | Critical | Candidate assembly and full rehearsal occur by 40-hex SHA with the release tag absent. A protected serialized authorizer reruns recency as its final check, embeds the exact result/evidence in an annotated tag, and immediately creates the new tag without force. Failure creates no tag; later jobs reject any moved or mismatched tag. |
| OCI attestations or identity are lost between candidate build, runtime smoke, and GHCR publication. | Critical | Buildx emits an OCI-layout tar, not a Docker load archive. Evidence distinguishes transport hash, runnable subject D_run, and attested index D_index. Skopeo copies D_run to Podman only for smoke and uses --all --preserve-digests for a disposable-registry round trip and final GHCR copy; any digest/descriptor/subject change fails. |
| npm package ownership or trusted publishing is not configured. | High | The bootstrap leaf uses `npm publish <smoked-pre-v1-tarball> --access public` with an owner-authorized, narrowly scoped temporary credential, proves unauthenticated public visibility/integrity, configures stage-only trust plus 2FA/token prohibition, and revokes the credential. A real `npm stage publish` of the exact v1 tarball proves OIDC; `npm stage approve` remains an explicit owner-2FA step after rehearsal. |
| The server binary is built with the empty embedded-web stub. | High | Native and Docker producers build `web/dist` first and fail unless `/` plus SPA fallback serve real assets; the pre-publication rehearsal repeats that proof from exact candidate artifacts. |
| Docker consolidation loses repository-relative documents, persistence, or signal handling. | Critical | A prerequisite server leaf installs Tokio SIGTERM/Ctrl-C handling, wires Axum graceful shutdown, and process-tests successful bounded exit plus socket/repository reuse. Docker runtime smoke then exercises an initialized whole-repository `/repo` mount, linked document endpoints, host-visible `.jit` mutation, numeric non-root PID 1, and exit 0 before the stop timeout without SIGKILL/137. |
| Removing old Docker files leaves a script, fixture, example, or live guide on the old contract. | High | The removal leaf owns the exhaustive active consumer list and a tree-wide negative search, updates active docs in the same change, and explicitly excludes only historical archive evidence and unrelated storage-test strings. |
| Documentation pruning removes discovery along with repetition. | High | Canonical pages land before entry-point pruning; every removed walkthrough retains a context-bearing link, and navigation/link/support-matrix checks plus adversarial review are acceptance criteria. |
| Core-maintenance or profiles work changes a release-consumed contract late. | High | The pre-publication rehearsal directly depends on both external epics, verifies their delivered public behavior, and contains no implementation criteria for their internal scope. Independent readiness leaves can proceed without duplicating that work. |
| An action claims production readiness without network-verifying audits or public channels. | Critical | Security remediation begins with unrestricted fresh probes; final publication verifies registry/GitHub/GHCR metadata and records public URLs, integrity, digest, and audit output. Sandbox-only evidence cannot close those criteria. |
| Workflow YAML appears correct but caller failure or permission propagation is unproved. | High | A prerequisite shared harness combines pinned actionlint, parsed-YAML graph/permission assertions, and disposable GitHub PR/tag fixtures. Security, CI, Docker, candidate assembly, and publication all consume it; no worker invents a local fixture contract. |
| Release workflow permissions become broader than required. | High | Each reusable producer receives only its necessary scoped permissions: contents/attestations/id-token for native provenance, stage-only id-token for npm OIDC, and packages for GHCR. Pull-request jobs have no write path, proven through the shared harness. |

Every load-bearing question is resolved or assigned to an item's observable criteria. Each leaf has a bounded file/consumer surface, independent green landing point, explicit dependency edges, and component-appropriate verification; no worker must choose a release topology, advisory policy, tag scheme, or documentation owner.

## Decisions

- **D1 — Capability boundary:** chosen **preserve the native CLI, Rust server/API, built web UI, and MCP server while cutting only redundant packaging, deployment, aliases already scheduled elsewhere, and repeated prose**. Rejected: broad feature cuts (would violate the v1 capability contract), retaining every delivery shape (multiplies support/security cost without a distinct outcome).
- **D2 — Advisory remediation shape:** chosen **three ecosystem-scoped remediation leaves followed by one reusable blocking workflow; the Rust leaf waits for core build-efficiency child `73482aa1` because both own Cargo manifests/lock and dependency-feature shape**. Rejected: one cross-ecosystem dependency mega-change (unbounded regression attribution), parallel Rust/core lock-domain edits (shared-file and dependency-graph collision), enabling blocking automation before cleanup (lands the repository red), blanket ignores (contradicts zero-known-advisory policy).
- **D3 — Workflow reuse and immutable invocation identity:** chosen **a shared executable workflow-verification prerequisite; callable normal CI/security workflows; a protected, non-movable candidate-tag push whose `github.sha` is the only candidate SHA; local reusable workflow calls; pre-build/stage validation of event/ref, checkout, caller/called-workflow SHAs, repository IDs and OIDC claims; exact-subject attestation/provenance verification; and one public-channel leaf after rehearsal and tag authorization**. Rejected: unspecified per-leaf workflow tests, copying suites into release YAML, `workflow_dispatch` plus an arbitrary checkout SHA, branch-selected reusable workflows, branch protection/previous-main evidence for a different commit, moved refs, or publicly publishing component producers.
- **D4 — Version, MSRV, and tag authority:** chosen **derive product versions from manifests, build/rehearse proposed v1.0.0 by exact SHA while its tag is absent, derive MSRV from cargo metadata, and run the live one-minor comparison as the final command before one protected job creates an annotated non-force v1.0.0 tag whose evidence/SHA downstream jobs verify**. Rejected: a tag-triggered recency check (failure arrives after immutable identity exists), separate manual tag creation (evidence gap/race), workflow version literals, unpinned stable-only builds, tag movement after a fix, or conflating product and repository-format versions.
- **D5 — Native artifact contract:** chosen **one Linux x86_64 musl archive containing jit and jit-server, both license texts, SHA-256 checksums, one SPDX JSON SBOM, extracted-binary smoke, and GitHub provenance/SBOM attestations**. Rejected: the current un-smoked binary/web archives (not an install proof), publishing a standalone web archive (the supported server already serves the built UI).
- **D6 — MCP bootstrap, staging, and publication:** chosen **owner-authorized one-time `npm publish <exact-smoked-existing-pre-v1-tarball> --access public` with a temporary scoped credential; unauthenticated visibility/integrity proof; then stage-only trusted-publisher setup, token prohibition/revocation, one exact v1 pack/smoke/attestation, `npm stage publish <tarball> --provenance` under the immutable candidate event as the real non-public OIDC proof, owner review/download plus provenance-identity verification, clean-room rehearsal, and owner `npm stage approve <stage-id>` with 2FA in the final publication leaf**. Rejected: pretending OIDC can create an absent package, omitting scoped-package public access, a dry-run or `npm whoami` OIDC check, retaining a long-lived token, direct v1 publication before rehearsal, source-directory repacking, or treating `npm pack` as registry verification.
- **D7 — Server lifecycle, Docker identity, ownership, transport, and tags:** chosen **first add Tokio Ctrl-C/Unix SIGTERM handling and Axum graceful shutdown with real-process bounded-exit tests; then one exec-form jit-server PID-1 image with numeric 10001:10001 default and explicit host-owner UID:GID override; Buildx OCI-layout transport with attached max-provenance/SBOM; tar SHA-256 for transport, Linux/amd64 D_run for runtime/attestation subject, top-level D_index for publication; Skopeo `--preserve-digests` into Podman for smoke and `--all --preserve-digests` to a disposable registry/GHCR; `main`/SHA development tags and one full-version release tag**. Rejected: relying on PID-1 default SIGTERM behavior, an init shim or shell supervisor, Docker `load:true`/docker-archive, rebuild-after-smoke, copy without all/preservation, split/multi-process images, root runtime, detached `/data`, or mutable release aliases.
- **D8 — Documentation ownership:** chosen **one canonical home per install, deployment, MCP, release, compatibility, and MSRV fact with concise linked entry points**. Rejected: synchronizing repeated walkthroughs (known drift), deleting entry-point context (hurts discoverability), rewriting archive evidence (destroys historical record).
- **D9 — External dependency re-home (binding D-14):** chosen **remove the implementation-consumed broad `8b05a612 -> 6eb585bc` edge from the planning/container spine and attach both `6eb585bc` and profiles MVP `9b7b5f9c` directly to the “Run the pre-publication clean-room v1.0 rehearsal” child at breakdown**. Rejected: leaving core maintenance on planning/container scope (blocks independent planning/work and overstates ownership), attaching them only after public publication (too late to validate safely), omitting profiles from rehearsal (cannot prove the documented quickstart), duplicating either epic's implementation in readiness (parallel conflict and split authority). The broad edge removal is recorded by commit `b6d52011`; breakdown completes the re-home with both child edges. The targeted Rust-remediation dependency on core child `73482aa1` is a separate shared-lock-domain serialization edge, not a transfer or duplication of core scope.
- **D10 — Rehearsal, tag, then publication:** chosen **a full clean-room rehearsal by exact SHA that depends on all candidates, canonical docs, and both external epics while v1.0.0/public channels remain absent; then the pre-tag authorizer; then a narrow publication leaf limited to identity/evidence preflight, exact-byte/digest-preserving publication and owner npm-stage approval, and post-publication channel verification**. Rejected: tag or publication before full acceptance, combining rehearsal/publication, build-only confidence, source-checkout-only smoke, independent public component releases, or trusting mutable tags instead of recorded digests.
- **Assumptions** (where intent stayed underspecified): the supported native binary target for v1.0 is Linux x86_64 musl, matching the current release scope — expanding operating-system/architecture coverage would require an owner criterion change; GitHub Release, npm package `@erankavija/jit-mcp-server`, and GHCR are the authorized public channels named by the current manifests/workflows and research — unavailable account-side configuration fails publication rather than selecting a substitute channel; external epics may evolve internally, but the rehearsal consumes only their public delivered contracts and waits on their terminal states.
