## Primitive verification and architecture fit

- **Server serves web:** confirmed, but only when `--web-dir` exists or the `embed-web` build includes real assets (`crates/server/src/main.rs:110-129`; `crates/server/build.rs:4-18`). A Docker build must establish this ordering and smoke the SPA fallback.
- **Health:** confirmed at `/api/health`, not `/health`, because of router nesting (`main.rs:104-107`; `routes.rs:33-36`). It validates process responsiveness, while repository validity is established once at startup (`main.rs:61-72`).
- **PID1/signals:** contradicted for root all-in-one (`docker/entrypoint.sh:12-19`); confirmed design primitive is a single exec-form `jit-server` command, as the split API image already uses (`docker/Dockerfile.api:38-40`).
- **Repository root:** the server consumes a `.jit` directory, derives project name from its parent, and watches that directory (`main.rs:61-90`). Therefore `/repo/.jit` is the correct argument while `/repo` is the bind mount; `JIT_DATA_DIR=/repo` would be wrong.
- **Publication:** contradicted. `npm pack` is local packaging, not registry publication (`.github/workflows/release.yml:82-94`); GitHub release creation does not establish Docker immutability or npm availability.
- **Domain/layer invariants:** packaging/workflow/docs changes stay at boundaries. Do not add Docker/profile/release literals to `crates/jit/src/domain/` or graph/storage engine code. Reuse `jit-server`'s existing `JsonFileStorage`/router boundary (`main.rs:61-75,104-108`) and preserve config-driven repository semantics. D-13 and `@/inv/single-source-prose` require one maintained source per volatile command/version fact; workflow should derive versions from manifests rather than duplicate literals.
