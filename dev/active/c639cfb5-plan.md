## 2. Technical soundness and architectural fit

- **Frozen selector and input grammar:** Every selecting command uses one repeatable `--profile SOURCE`, where `SOURCE` is exactly `id:ID` or `path:DIR`. One ordered `ProfileSelector` collection is carried unchanged through CLI parsing, generated schema, MCP, command requests, results, and tests; separate ID/path vectors and index reconstruction are forbidden. Configuration accepts at most one `--values-file PATH`, whose document is exactly a TOML `[variables]` string map, plus repeatable `--set NAME=VALUE`. These are persistable, explicitly non-secret inputs; no secret flag, stdin/resupply channel, special redaction path, or alternate values-file shape exists.
- **Strict manifest wires, one model:** `decode_profile_package` privately dispatches on strict manifest v1 or strict manifest v2 wire structs and immediately returns one canonical semantic package. Manifest v2 `[[variable]]` entries have only `name`, `default`, and `env`; unknown manifest, variable, dependency, incompatibility, target, or contribution fields fail. The decoder, normalized model, resolver, graph, composer, variable resolver, planner, and records are introduced only as part of the complete cutover—none lands earlier as dead or alternate code.
- **One bounded template language:** `{{jit:var:NAME}}` is the sole reference syntax. Parsing produces one typed template representation. String semantic leaves may use placeholders without a separate flag. Manifest-v2 `AssetDeclaration` and `RegionDeclaration` each add `template: bool` with deserialization default false and canonical wire serialization `template = true|false`; their UTF-8 bodies reject placeholders unless `template = true`. V1 content, identity fields, profile/dependency IDs, versions/ranges, paths, marker IDs, modes, executable flags, and asset/region bodies with `template = false` reject references. Unknown variables, malformed references, duplicate declarations, non-string values, loops, conditionals, secret modes, indirection, and nested template languages fail closed.
- **Identity domains:** Package identity hashes unresolved raw package bytes, including the raw manifest and declared source bytes, with the existing v1 algorithm frozen and v2 domain-separated. Values files, environment values, and `--set` values never alter package identity. Aggregate plan and ownership-claim identities hash the resolved public-value map and exact final semantic/materialized bytes, so a changed input is visible even when the package is unchanged.
- **Complete applied closure:** Every operation loads the sole canonical record set and resolves selected candidates alongside every surviving unselected owner, dependency, dependent, and incompatibility. Equal resolved contribution fingerprints retain all owners; different selected or surviving bases conflict. An upgrade cannot invalidate an unselected dependent's range or introduce an incompatibility with a survivor. Records describe claims and provenance but never provide effective registry values.
- **One-way v1 record migration:** The sole current applied-record JSON wire has discriminator exactly `record_version: 2`. The private legacy-record decoder accepts only the released five-field version-1 applied record and authenticates it against the unchanged embedded pinned dogfood package and exact stored package/target hashes. It derives baseline-retained version-2 claims and writes every migrated record in the same transaction as the requested apply or upgrade. The one resulting `profile_lifecycle_changed` event retains that requested operation and adds sorted `record_migrations` entries with exactly the keys `{profile_id, from_version, to_version}` and values 1 and 2 for the version fields; migration is never an operation value or separate event. Mismatch fails closed. There is no `path:DIR` evidence option, local fallback, archived package copy, inferred base, serde union, optional legacy fields, events-derived state, or ordinary reader that returns both formats.
- **`cdc840ad` is a pending foundation, not work owned here:** `cdc840ad` is Backlog at planning time. This leaf cannot start until that issue reaches Done. Its plan specifies expected prerequisite postconditions—canonical declarations and repository image, one materializer, one strict managed-document engine, one exact delta/storage capability, and removal of its owned competing paths—but none is treated here as delivered or currently absent. After it is Done and before V1.1 coding begins, re-read the actual tree, completion evidence, public boundaries, and structural absence set; use those delivered facts to rebase this plan's imports and deletion inventory. Expected `cdc840ad` removals such as `PackageProjection`, `ProjectedFile*`, `profile/render.rs`, `RepositorySnapshot*`, snapshot capture, `profile::drift`, `PresetProjection`/duplicate inventory, `ProfileApplicationPlan`, `PlannedTarget*`, `plan_profile_application_against`, `InitScaffold` final-target inventory, and command-local profile/init transaction builders are prerequisite scope, never V1.1 deletion credit.
- **One complete implementation landing:** The sole implementation leaf introduces and immediately uses the final versioned decoder/model, source resolver, dependency graph, variable resolver, canonical record/migrator, ownership/three-way composer, and aggregate lifecycle planner. In that same change it migrates `commands/profile.rs`, profiled init, `main.rs`, CLI, output, schema, profile exports, storage record loading, current event construction/catalog/parser, server/direct callers, MCP curation/integration, exact tests, and current documentation. There is no intermediate exported type, lint-only guard, compatibility shim, temporary constructor, duplicate request/result, or uncalled engine.
- **Deletion inventory rebased after `cdc840ad`:** The names below are a provisional inventory of predecessor surface expected to remain after `cdc840ad`, not a claim about current or future absence: `EmbeddedProfilePackage` and its re-export; embedded-only package/resolver and list/show/plan/apply/validate command methods; `validate_profile_id`; the source-specific init/profile single-ID request and dispatch; the current `Event::new_profile_applied` constructor and profile event-image appender; and the surviving v1 public provenance/result family (`AppliedProfileRecord` as the ordinary current type, `ProfileApplicationStatus`, `ProfileApplicationWarning`, `ProfileApplyResult`, `ProfileListResult`, `ProfileShowResult`, `ProfileTargetAction`, `ProfileTargetChange`, `ProfilePlanStatus`, and `ProfilePlanResult`). Once `cdc840ad` is Done, inspect its actual delivered tree: remove already-deleted names from V1.1 accounting, add only surviving superseded V1.1 paths proven by that tree, and never reintroduce or claim the prerequisite's removals. Retain only the historical `ProfileApplied` tag/parser and the private version-1 migration input.
- **One current event wire:** Init delegates to the ordinary apply request; it has no distinct lifecycle operation. Dry-run emits no event. A mutating apply or upgrade emits exactly one `profile_lifecycle_changed` only when the aggregate changes. `requested_operation` is exactly `apply|upgrade`; sorted per-profile actions use exactly `installed|unchanged|reconfigured|upgraded`; sorted `record_migrations` entries have exactly the keys `{profile_id, from_version, to_version}`, with `from_version` 1 and `to_version` 2. An entirely unchanged aggregate emits no event. A version-1 record migration combined with apply/upgrade stays in that event and does not become a requested operation. Variable information is limited to sorted name/source-kind pairs (`default`, `values_file`, `environment`, or `set`) and contains no resolved values or rendered content. Historical `ProfileApplied` decoding remains solely for append-only history and torn-tail validation; no current constructor or emitter survives.
- **Layer fit:** Wire decoding, package normalization, graph resolution, variable resolution, applied-closure joins, ownership, and three-way decisions are pure domain logic. Storage owns bounded no-follow capture, the isolated migration input, persistence of records discriminated exactly by `record_version: 2`, and—once `cdc840ad` reaches Done—the actual shared mutation session it delivers. Commands orchestrate one aggregate final-view plan. CLI/output/schema/MCP present that result. All mutation and validation consume the canonical repository view/materializer proven present after the dependency completes and remain Git-optional.

## Decisions

- **D1 — Delivery shape:** chosen **one complete independently green vertical implementation task after `cdc840ad`, followed only by evidence expansion**. Rejected: separate decoder/model/resolver/variables/records/planner leaves (temporary or dead architecture), horizontal runtime/public migrations (dual contracts), later cleanup.
- **D2 — Selector contract:** chosen **one repeatable ordered `--profile id:ID|path:DIR` occurrence on every selecting command**. Rejected: `embedded:ID`, untagged values, separate ID/path options, index reconstruction, implicit search, and remote discovery.
- **D3 — Variable input contract:** chosen **strict manifest-v2 `[[variable]]` entries with only `name`, `default`, and `env`; one optional `--values-file PATH` containing a TOML `[variables]` string map; repeatable `--set NAME=VALUE`; all values persistable and non-secret**. Rejected: permissive fields, other value types/shapes, stdin/resupply, secret mode, or command-specific inputs.
- **D4 — Template contract:** chosen **only `{{jit:var:NAME}}`; semantic string leaves use it directly, while manifest-v2 `AssetDeclaration` and `RegionDeclaration` use `template: bool`, default false and canonically serialized `template = true|false`, to permit it in UTF-8 bodies**. Rejected: placeholders in false/unmarked bodies, templated identities/paths/modes, implicit body templating, multiple engines, loops, conditionals, indirection, and secret interpolation.
- **D5 — Identity:** chosen **unresolved raw bytes for package identity; resolved values and exact final bytes for plan/claim identities**. Rejected: invocation-dependent package identity or identities that hide resolved changes.
- **D6 — Package evolution:** chosen **strict durable v1 and strict v2 wires normalized immediately into one semantic model**. Rejected: rewriting the released dogfood package, permissive in-place v1 extension, or parallel semantic engines.
- **D7 — Applied closure and SSOT:** chosen **every operation joins selected candidates with every canonical applied record; claims record provenance/ownership only and declared repository state stays authoritative**. Rejected: selected-only planning, central duplicate ownership index, package reload as effective state, or record-backed configuration.
- **D8 — V1 migration:** chosen **one-way migration from record version 1 to the sole current JSON wire discriminated exactly by `record_version: 2`, authenticated only by the unchanged embedded pinned dogfood package and recorded inside the requested apply/upgrade event using entries with exactly `{profile_id, from_version, to_version}`**. Rejected: migration operation/event, local evidence fallback, copied inventory, inferred bases, dual ordinary readers, optional legacy fields, or events-derived current state.
- **D9 — Foundation boundary:** chosen **wait for currently Backlog `cdc840ad` to reach Done, then revalidate and consume its actual delivered image/materializer/marker/delta/session/publisher and actual absence set**. Rejected: treating its plan as present code, reimplementing or claiming its removals, compatibility wrappers, alternate publication, or pre-foundation live lifecycle work.
- **D10 — Current audit:** chosen **one `profile_lifecycle_changed` event for a changed mutation: requested operation exactly `apply|upgrade`, sorted per-profile action exactly `installed|unchanged|reconfigured|upgraded`, sorted record-migration entries with exactly `{profile_id, from_version, to_version}` and version values 1 and 2, and variable names/source kinds only; init delegates to apply, dry-run and entirely unchanged aggregates emit nothing, and historical `ProfileApplied` is decode-only**. - **D11 — Upgrade deletion:** chosen **only unchanged solely-owned non-baseline content may be removed during upgrade; no general removal command**. Rejected: uninstall/removal scope or deletion of adopted baseline/user drift.
- **D12 — Evidence boundary:** chosen **cross-platform, failure, recovery, and structural-absence evidence only after cutover, with no contract changes**. Rejected: deferred core tests, lint/export/wiring staging, compatibility scaffolding, or implementation cleanup in the evidence leaf.
